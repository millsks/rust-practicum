Pixi Codebase Map

Pixi is one Cargo workspace with sixty crates under crates/. This page groups them by job, shows how the main ones depend on each other, and tells you where to start reading when you have a question. Every link points at the frozen snapshot the course reads, so line numbers never drift.

The snapshot and the workspace

The course pins Pixi at commit 451aa9596402530f1a4d8a50b5fe137570ad42a5 (pixi 0.81.0 development, 2026-09-18). All permalinks have the form https://github.com/prefix-dev/pixi/blob/451aa959.../<path>#L<start>-L<end>.

A workspace is a set of Cargo packages built together with one Cargo.lock and one target/ directory. Pixi's root Cargo.toml declares members = ["crates/*"] and excludes crates/pixi_allocator (it is only pulled in by a feature), so 59 of the 60 directories are workspace members. The [workspace.package] table sets edition = "2024", rust-version = "1.90", and the BSD-3-Clause license for every crate, and [workspace.dependencies] pins every third-party version once, which each crate then uses with { workspace = true }. M01 teaches workspaces and M10 teaches why a project is split this way.

Directory names use underscores; seven backend packages use hyphens in their package name (for example the crates/pixi_build_python directory builds the package pixi-build-python). Cargo turns hyphens into underscores for the crate name in code, so use pixi_build_backend::... and the package pixi_build_backend match exactly.

The main dependency flow

An arrow means "depends on" in that crate's [dependencies]. Only the main crates are shown; every crate also uses small utility crates such as pixi_consts and pixi_utils. Read it top to bottom: the binary is a thin shell, the CLI turns arguments into calls, pixi_core orchestrates, and the manifest, the command dispatcher, and rattler do the work.

flowchart TD
  pixi[pixi binary] --> cli[pixi_cli]
  cli --> api[pixi_api]
  cli --> task[pixi_task]
  cli --> global[pixi_global]
  cli --> core[pixi_core]
  api --> core
  task --> core
  global --> core
  core --> manifest[pixi_manifest]
  core --> dispatcher[pixi_command_dispatcher]
  core --> pypi[pixi_install_pypi]
  core --> rlock[(rattler_lock)]
  dispatcher --> engine[pixi_compute_engine]
  dispatcher --> sources[pixi_compute_sources]
  dispatcher --> frontend[pixi_build_frontend]
  dispatcher --> rsolve[(rattler_solve and repodata gateway)]
  sources --> engine
  frontend --> btypes[pixi_build_types]
  manifest --> spec[pixi_spec]
  manifest --> ptoml[pixi_toml]
  manifest --> ptedit[pixi_toml_edit]
  spec --> ptoml
  backend[pixi_build_backend] --> btypes
  backends[pixi-build-python, -rust, -cmake, ...] --> backend

Rounded boxes are rattler crates from crates.io, not workspace members. The edges were read from each crate's Cargo.toml: for example pixi_core/Cargo.toml pulls in rattler_lock, rattler_solve, and rattler_repodata_gateway, and pixi_command_dispatcher/Cargo.toml enables the resolvo feature of rattler_solve.

Notice that pixi_manifest depends on nothing above it. That is a deliberate layering rule: the manifest crate can be tested, and reused, without the solver, the network, or the CLI. When you add code, put it in the lowest crate that has everything it needs.

Where to start reading

Each answer gives the first file to open and the item to look for. Read the function signature and doc comment first, then follow the calls one level down.

How is pixi.toml parsed?

  1. Discovery: WorkspaceLocator in pixi_core and its locate method, which uses WorkspaceDiscoverer in pixi_manifest to walk up the directory tree.
  2. Parsing: the FromTomlStr trait has a blanket implementation for every type that implements toml_span::Deserialize. It parses the text into a spanned value tree, then deserializes it.
  3. The raw shape: TomlManifest and its hand-written toml_span::Deserialize impl, with the other Toml* types in pixi_manifest/src/toml/. Helpers for maps, sets, and "one or many" values are in pixi_toml.
  4. The typed result: WorkspaceManifest::from_toml_str_with_base_dir calls TomlManifest::from_toml_str, then into_workspace_manifest, which validates features, environments, and targets and produces the struct the rest of Pixi uses.

Prepares you: M02 (structs and enums), M04 (errors and ?), M06 (blanket impls, FromStr), and Capstone 1, which builds a small version of exactly this.

How does pixi add work?

  1. pixi/src/main.rs starts a tokio runtime on a thread named main2 and awaits pixi_cli::execute().
  2. clap parses arguments into the Command enum, and execute_command matches Command::Add(cmd) to add::execute(cmd).
  3. add::execute locates the workspace with WorkspaceLocator::for_cli(), then for conda packages calls add_conda_deps on a pixi_api context.
  4. WorkspaceContext::add_conda_deps forwards to add_conda_dep, which calls WorkspaceMut::update_dependencies, then saves the manifest on success or reverts it on error.
  5. update_dependencies in pixi_core does three things, as its doc comment says: edit the manifest, update the lock file, and pin packages that were added without a version. The edit is self.manifest().add_dependency(...).
  6. In pixi_manifest, WorkspaceManifest::add_dependency changes the typed manifest and the TOML document together; the document side, ManifestDocument::add_dependency, uses the format-preserving helpers in pixi_toml_edit.
  7. The lock file: UpdateContext::builder receives a CommandDispatcher, the UpdateContext in pixi_core::lock_file re-solves the affected environments and platforms, and write_to_disk writes pixi.lock.
  8. The solve itself runs through the command dispatcher and the compute engine, which call rattler's repodata gateway and solver.

Prepares you: M08 (Arc and shared state), M06 (the Interface and Key traits), and Level 2 Stages 3-5 (clap, miette, toml_edit, async). Stage 7 of the roadmap walks this path in detail.

Where are tasks run?

  1. run::execute in pixi_cli is the entry point for pixi run. It builds the graph with TaskGraph::from_cmd_args.
  2. TaskGraph in pixi_task resolves names and depends-on edges into an ordered graph (from_cmd_args).
  3. ExecutableTask runs one task in its environment (execute_with_pipes); caching of up-to-date tasks lives in task_hash.rs.

Prepares you: M05 and M09 (graph building is iterator-heavy), M07 (TaskGraph<'p> borrows the workspace), and the task-ordering part of Capstone 1.

Building and testing Pixi with Pixi

Pixi is developed with Pixi. Its rust feature adds rust-src 1.95 and points CARGO_TARGET_DIR at target/pixi, and the rust-test environment defines the tasks you use day to day:

TaskRuns
pixi run build-debugcargo build --workspace --bin pixi
pixi run build-releasecargo build --workspace --bin pixi --release
pixi run test-fastcargo nextest run --workspace --all-targets with RUST_LOG="debug,resolvo=info"
pixi run test-slowThe same, plus the slow_integration_tests and online_tests features
pixi run instacargo insta (pass a subcommand, for example pixi run insta review)

The dev feature adds cargo-nextest and the insta-review task (cargo insta review --workspace). The default environment's tasks include cargo-clippy (cargo clippy --all-targets --workspace -- -D warnings) and cargo-fmt, and the lefthook environment defines pixi run lint, which runs every lefthook job on all files.

Before you open a pull request against Pixi, run pixi run lint and pixi run test-fast, and review any changed snapshots with pixi run insta-review. Those three commands are what CI and reviewers will check first.
