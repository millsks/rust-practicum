The two biggest differences are not syntax. First, every value in Rust has exactly one owner, so assignment and function calls move values unless you borrow them (M03). Second, errors are ordinary return values, so the type of a function tells you whether it can fail (M04).

Variables, numbers, and strings

Variables and mutability

Python names can be rebound and the objects they point to can usually be mutated. Rust bindings are immutable unless you write mut, which makes every place that changes state visible. M02

name = "pixi"
count = 0
count += 1
count = count * 2         # same name, rebound
MAX_JOBS = 8              # a constant by convention only
let name = "pixi";          // immutable by default
let mut count = 0;          // opt in to mutation
count += 1;
let count = count * 2;      // shadowing: a new binding, may change type
const MAX_JOBS: usize = 8;  // a real compile-time constant

Numbers and casts

Python has one unbounded int. Rust has sized integers (i8 to i128, u8 to u128, isize/usize) and never converts between them silently. Overflow panics in debug builds and wraps in release builds, so use checked_* when it can happen. M02

c = 7 + 2          # ints mix freely
d = 7 // 2         # 3
e = 7 / 2          # 3.5
f = -7 % 3         # 2
n = int("42")
small = 300 % 256  # 44, only if you ask for it
let a: i32 = 7;
let b: i64 = 2;
let c = a as i64 + b;                 // explicit cast; no silent widening
let d = 7 / 2;                        // 3: integer division for integers
let e = 7.0 / 2.0;                    // 3.5
let f = (-7_i32).rem_euclid(3);       // 2 (plain % gives -1)
let n: i32 = "42".parse().unwrap();   // parse returns a Result
let small = 300_u16 as u8;            // 44: `as` truncates
let checked = u8::try_from(300_u16);  // Err(..): checked conversion
let sum = 255_u8.checked_add(1);      // None instead of overflow

Strings, f-strings, and format!

Rust has two main string types. String owns a growable UTF-8 buffer; &str is a borrowed view into one (string literals are &'static str). Functions usually take &str and return String. Format strings capture variables by name, like f-strings. M02, M03

name = "pixi"
owned = "rattler"
owned += "-build"
msg = f"{name} has {n} deps"
padded = f"{n:>4}|{name:<6}|{3.14159:.2f}"
parts = "a,b,c".split(",")
joined = "-".join(parts)
"  x  ".strip(); name.startswith("pi"); name.upper()
let name = "pixi";                        // &str: borrowed text
let mut owned = String::from("rattler");  // String: owned, growable
owned.push_str("-build");
let msg = format!("{name} has {n} deps");
let padded = format!("{n:>4}|{name:<6}|{:.2}", 3.14159);
let parts: Vec<&str> = "a,b,c".split(',').collect();
let joined = parts.join("-");
"  x  ".trim(); name.starts_with("pi"); name.to_uppercase();

println! prints with a newline, eprintln! prints to stderr, and format! returns a String. {:?} uses Debug, {} uses Display, and {x:#?} pretty-prints.

Assignment, ownership, and borrowing

In Python, b = a makes a second name for the same list, and both can change it. In Rust, let b = a; moves the value: a can no longer be used (error E0382). To let a function look at a value without taking it, pass a reference. M03

a = ["linux-64"]
b = a              # same list, two names
b.append("osx-arm64")
print(a)           # both see the change

def count(platforms: list[str]) -> int:
    return len(platforms)
let a = vec![String::from("linux-64")];
let b = a;                     // move: `a` is no longer usable
// println!("{a:?}");          // error[E0382]: borrow of moved value
let c = b.clone();             // an explicit, independent copy

fn count(platforms: &[String]) -> usize {  // borrow, do not take
    platforms.len()
}
let n = count(&b);             // `b` is still usable afterwards
You want toParameter type
Read a value&T (&str for text, &[T] for a list)

Collections and iteration

Lists, dicts, and sets

Vec<T> is a list whose elements all have type T. HashMap is a dict with unspecified iteration order (it changes between runs); use BTreeMap for sorted keys, or IndexMap (a crate Pixi uses) to keep insertion order like a Python dict. M05

nums = [3, 1, 2]
nums.append(4); nums.sort()
first = nums[0]
deps = {"python": ">=3.12"}
spec = deps.get("python")          # None if missing
deps.setdefault("numpy", "*")
platforms = {"linux-64", "osx-arm64"}
"linux-64" in platforms; len(nums)
let mut nums = vec![3, 1, 2];
nums.push(4); nums.sort();
let first = nums[0];               // panics if out of range
let maybe = nums.get(10);          // Option: None instead of IndexError
let mut deps: HashMap<String, String> = HashMap::new();
deps.insert("python".to_string(), ">=3.12".to_string());
let spec = deps.get("python");     // Option<&String>
deps.entry("numpy".to_string()).or_insert("*".to_string());
let platforms: HashSet<&str> = ["linux-64", "osx-arm64"].into_iter().collect();
platforms.contains("linux-64"); nums.len();

Comprehensions and iterator chains

A comprehension becomes an iterator chain ending in a consumer such as collect, sum, or any. Adapters like map and filter are lazy: nothing runs until the consumer pulls values. iter() borrows the elements, iter_mut() borrows them mutably, and into_iter() takes them. M05, M09

squares = [n * n for n in nums]
even_squares = [n * n for n in nums if n % 2 == 0]
by_name = {s: len(s) for s in ["pixi", "uv"]}
total = sum(nums)
any_big = any(n > 4 for n in nums)
for i, n in enumerate(nums):
    print(f"{i}: {n}")
let squares: Vec<i32> = nums.iter().map(|n| n * n).collect();
let even_squares: Vec<i32> =
    nums.iter().filter(|n| *n % 2 == 0).map(|n| n * n).collect();
let by_name: HashMap<&str, usize> =
    ["pixi", "uv"].iter().map(|s| (*s, s.len())).collect();
let total: i32 = nums.iter().sum();
let any_big = nums.iter().any(|n| *n > 4);
for (i, n) in nums.iter().enumerate() {
    println!("{i}: {n}");
}

The iteration protocol and Iterator

Python's __iter__/__next__ (or a generator) becomes one trait method: next returns Some(item) or None when done, in place of raising StopIteration. Implementing next gives you every adapter for free. M09

def countdown(n: int):
    while n > 0:
        yield n
        n -= 1

list(countdown(3))   # [3, 2, 1]
struct Countdown { n: u32 }

impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.n == 0 { return None; }
        self.n -= 1;
        Some(self.n + 1)
    }
}

let v: Vec<u32> = Countdown { n: 3 }.collect();   // [3, 2, 1]

None, exceptions, and default arguments

None and Option

Any Python value might be None, and the type checker only helps if you annotate. In Rust a value that might be missing has type Option<T>, and you cannot use the T inside without handling None. M04

def find_env(name: str) -> int | None:
    return 0 if name == "default" else None

idx = find_env("test")
if idx is not None:
    print(idx)
idx = find_env("test") or 0
fn find_env(name: &str) -> Option<usize> {
    if name == "default" { Some(0) } else { None }
}

if let Some(idx) = find_env("test") {
    println!("{idx}");
}
let idx = find_env("test").unwrap_or(0);
let label = find_env("test").map(|i| i.to_string()).unwrap_or_else(|| "none".to_string());

Exceptions and Result with ?

A function that can fail returns Result<T, E>: Ok(value) or Err(error). The ? operator is the "let it propagate" of Rust: on Err it returns the error from the current function (converting it with From), on Ok it unwraps the value. panic!, unwrap(), and expect() are for bugs, not for expected failures. M04

class ManifestError(Exception): ...

def read_version(text: str) -> int:
    if not text.startswith("version="):
        raise ManifestError("missing key `version`")
    try:
        return int(text.removeprefix("version="))
    except ValueError:
        raise ManifestError("bad version on line 1")

def caller() -> None:
    v = read_version("version=3")   # exceptions propagate implicitly
#[derive(Debug)]
enum ManifestError {
    Missing(String),
    BadVersion { line: usize },
}
// plus `impl Display` and `impl std::error::Error` (M04)

fn read_version(text: &str) -> Result<u32, ManifestError> {
    let raw = text
        .strip_prefix("version=")
        .ok_or(ManifestError::Missing("version".into()))?;
    raw.trim().parse().map_err(|_| ManifestError::BadVersion { line: 1 })
}

fn caller() -> Result<(), Box<dyn std::error::Error>> {
    let v = read_version("version=3")?;   // propagation is explicit: `?`
    Ok(())
}

Pixi derives these impls with thiserror and reports errors to the user with miette, so most Pixi functions return miette::Result<T>. M04 shows what those crates generate; Level 2 teaches them.

None-default arguments, Option parameters, and builders

Rust has no default or keyword arguments. For one optional value, take an Option. For many, take an options struct that implements Default and use struct update syntax (..Default::default()), or write a builder with chained setter methods (Pixi's WorkspaceLocator::for_cli().with_search_start(..) is one). M04, M06

def install(name: str, version: str | None = None,
            no_install: bool = False) -> str: ...

install("numpy")
install("numpy", version="2.0")
install("numpy", no_install=True)
#[derive(Default)]
struct InstallOptions {
    version: Option<String>,
    no_install: bool,
}

fn install(name: &str, opts: InstallOptions) -> String { /* ... */ }

install("numpy", InstallOptions::default());
install("numpy", InstallOptions { version: Some("2.0".into()), ..Default::default() });
install("numpy", InstallOptions { no_install: true, ..Default::default() });

Classes, protocols, and generics

Classes vs structs, impl, and traits

A Python class bundles data, methods, and inheritance. Rust splits these: a struct holds data, an impl block adds methods, and traits share behavior between types. There is no inheritance. Methods say how they use self: &self reads, &mut self changes, and self consumes. new is a convention, not a keyword. M02

class Workspace:
    def __init__(self, name: str) -> None:
        self.name = name
        self.platforms: list[str] = []

    def add_platform(self, p: str) -> None:
        self.platforms.append(p)

    def platform_count(self) -> int:
        return len(self.platforms)
struct Workspace {
    name: String,
    platforms: Vec<String>,
}

impl Workspace {
    fn new(name: &str) -> Self {
        Workspace { name: name.to_string(), platforms: Vec::new() }
    }
    fn add_platform(&mut self, p: &str) {
        self.platforms.push(p.to_string());
    }
    fn platform_count(&self) -> usize {
        self.platforms.len()
    }
}

ABCs and Protocols vs traits

A trait is a named set of methods a type promises to have, like an ABC (explicit implementation) with the checking of a Protocol (at compile time). A trait can have default methods. Use a generic or impl Trait when the type is known at compile time; use dyn Trait (behind a pointer such as Box or &) when you need a list of different types. M06

from abc import ABC, abstractmethod

class Backend(ABC):
    @abstractmethod
    def name(self) -> str: ...

    def describe(self) -> str:
        return f"backend {self.name()}"

class Python(Backend):
    def name(self) -> str:
        return "python"

backends: list[Backend] = [Python()]
trait Backend {
    fn name(&self) -> String;
    fn describe(&self) -> String {        // default method
        format!("backend {}", self.name())
    }
}

struct Python;
impl Backend for Python {
    fn name(&self) -> String { "python".into() }
}

fn print_backend(b: &impl Backend) { println!("{}", b.describe()); }  // static
let backends: Vec<Box<dyn Backend>> = vec![Box::new(Python)];       // dynamic

Dataclasses vs derive

@dataclass generates __init__, __repr__, and __eq__. #[derive(...)] generates trait implementations the same way, and you choose exactly which ones. M02, M06

from dataclasses import dataclass

@dataclass(frozen=True)
class Package:
    name: str = ""
    version: str = ""
#[derive(Debug, Clone, PartialEq, Eq, Hash, Default)]
struct Package {
    name: String,
    version: String,
}
// Debug: {:?}   Clone: .clone()   PartialEq/Eq: ==
// Hash: usable as a HashMap key   Default: Package::default()

__str__ and __repr__ vs Display and Debug

Display is the user-facing text used by {} and .to_string(); you write it by hand. Debug is the developer-facing text used by {:?}; you almost always derive it. M06

class Version:
    def __init__(self, major: int, minor: int) -> None:
        self.major, self.minor = major, minor

    def __str__(self) -> str:
        return f"{self.major}.{self.minor}"

    def __repr__(self) -> str:
        return f"Version(major={self.major}, minor={self.minor})"
use std::fmt;

#[derive(Debug)]                 // Version { major: 1, minor: 2 }
struct Version { major: u32, minor: u32 }

impl fmt::Display for Version {  // 1.2
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}.{}", self.major, self.minor)
    }
}

Typing generics vs Rust generics

Python type parameters are hints a checker reads; at runtime one function handles every type. Rust generics are checked by the compiler, and each concrete type gets its own compiled copy (monomorphization), so they cost nothing at runtime. A trait bound (T: PartialOrd) says what the code needs from T. M06

def largest[T: (int, float)](items: list[T]) -> T:
    return max(items)

class Stack[T]:
    def __init__(self) -> None:
        self.items: list[T] = []
    def push(self, item: T) -> None:
        self.items.append(item)
    def pop(self) -> T | None:
        return self.items.pop() if self.items else None
fn largest<T: PartialOrd + Copy>(items: &[T]) -> T {
    let mut best = items[0];
    for &item in items {
        if item > best { best = item; }
    }
    best
}

struct Stack<T> { items: Vec<T> }
impl<T> Stack<T> {
    fn push(&mut self, item: T) { self.items.push(item); }
    fn pop(&mut self) -> Option<T> { self.items.pop() }
}

Cleanup and concurrency

with vs Drop and RAII

Python needs with to guarantee cleanup because objects live until the garbage collector frees them. In Rust, a value is dropped the moment its owner goes out of scope, and its Drop impl runs then. This pattern is called RAII (resource acquisition is initialization): files close, locks release, and temporary directories disappear at the closing brace, on every path out of the scope. M03, M08

with open("pixi.toml") as f:
    text = f.read()
# closed here

with lock:
    counter += 1
# released here
struct TempDir { path: String }

impl Drop for TempDir {
    fn drop(&mut self) {
        println!("removing {}", self.path);
    }
}

fn work() {
    let dir = TempDir { path: "/tmp/x".into() };
    println!("using {}", dir.path);
}   // `dir` is dropped here, even on an early return

Threads and the GIL vs Send and Sync

Python threads take turns holding the GIL, so pure-Python code does not run in parallel, and data races are prevented only for single bytecode steps. Rust threads run truly in parallel, and the compiler prevents data races with two marker traits: Send (safe to move to another thread) and Sync (safe to share by reference between threads). Arc shares ownership across threads; Mutex gives one thread at a time mutable access. M08

import threading

counter = 0
lock = threading.Lock()

def work() -> None:
    global counter
    with lock:
        counter += 1

threads = [threading.Thread(target=work) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = Vec::new();
for _ in 0..4 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        *counter.lock().unwrap() += 1;
    }));
}
for h in handles { h.join().unwrap(); }
// Using Rc instead of Arc here is a compile error (E0277: not Send)

Pixi is async (tokio) rather than thread-per-task, but the same rules apply: values shared between tasks are wrapped in Arc, and a future must be Send to be spawned. Level 2 Stage 5 teaches async.

Projects, dependencies, and tests

Modules and packages vs mod and crates

A Python package is a directory with modules you import. A Rust crate is one compilation unit (a library or a binary); inside it, mod declares modules, which map to files. Everything is private unless marked pub, and pub use re-exports, like names in an __init__.py. M01, M10

# manifest/__init__.py
from .parse import parse

# manifest/parse.py
def parse() -> None: ...

# elsewhere
from manifest import parse
// src/lib.rs
mod manifest;               // loads src/manifest.rs (or src/manifest/mod.rs)

// src/manifest.rs
pub mod parse;              // loads src/manifest/parse.rs
pub use parse::parse;       // re-export

// src/manifest/parse.rs
pub fn parse() {}

// elsewhere in the crate
use crate::manifest::parse;

pytest vs cargo test

Rust tests are functions marked #[test], usually in a mod tests at the bottom of the file they test (so they can see private items). Integration tests go in tests/, like a pytest directory. Pixi uses insta for snapshot tests and cargo nextest as its runner. M11

import pytest

def test_parses_version() -> None:
    assert read_version("version=3") == 3

def test_rejects_missing() -> None:
    with pytest.raises(ManifestError):
        read_version("name=x")
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_version() {
        assert_eq!(read_version("version=3").unwrap(), 3);
    }

    #[test]
    fn rejects_missing() {
        assert!(matches!(read_version("name=x"), Err(ManifestError::Missing(_))));
    }
}
