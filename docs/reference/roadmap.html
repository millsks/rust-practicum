Roadmap: Levels 1-3

The practicum is eight stages in three levels, each level ending in a capstone. Level 1 teaches you to read Rust: any function in Pixi, who owns what, and why it compiles. Level 2 teaches the libraries the Pixi codebase is built on. Level 3 puts you inside the Pixi codebase itself, ending with a realistic change on a fork. This page shows the whole path, how long each part takes, and the gate you should pass before moving on.

Hours are for a developer who already writes Python every day and does every exercise, mini-project, and quiz. They include the capstone. Reading alone is much faster, but Rust is learned by fighting the compiler, so the exercises are where the hours go and where the learning happens.

Level 1 runs in your browser on the Rust Playground, with mini-projects and the capstone run locally through Pixi (pixi add rust, then pixi run cargo ...). Levels 2 and 3 move to local Cargo projects, because the libraries they teach (tokio, reqwest, rattler) need the network, the filesystem, or crates the Playground does not carry. See M00 for how the course works.

Every lesson reads one frozen commit of Pixi, 451aa959 (pixi 0.81.0 development). The Pixi codebase map describes its crates; Level 3 is a guided tour of the same snapshot, so links never drift while you learn.

Level 1 · Reading Rust available

Outcome: you can open any function in Pixi and explain what it does, who owns each value, why each borrow is allowed, and how errors flow out of it. You can also write a small, well-tested crate from a blank file.

Orientation (about 1 h)

  • M00 How This Practicum Works: why Rust for a Pixi maintainer, the Playground, installing Rust with Pixi, reading a compiler error, the frozen snapshot

Stage 1 · The core language (12-14 h)

Enough syntax and semantics to read any function body in Pixi. Ownership is the center of the stage: the rest of Rust is built on it.

  • M01 Cargo, Crates & Modules: cargo commands, Cargo.toml, packages and crates, mod and use, workspaces
  • M02 Types, Structs & Enums: scalars, String vs &str, impl blocks, enums with data, exhaustive match
  • M03 Ownership & Borrowing: moves, Copy and Clone, &T and &mut T, slices, borrow-checker errors
  • M04 Option, Result & ?: absence and failure as values, combinators, the ? operator, custom error enums
  • M05 Collections & Iterators: Vec, HashMap, BTreeMap, the entry API, adapters and collect

Stage 2 · Idiomatic Rust (12-14 h)

The patterns that fill the Pixi codebase: traits everywhere, Arc passed between threads, long iterator chains, and nearly 400 insta snapshot files.

  • M06 Traits & Generics: traits, bounds, impl Trait, dyn Trait, derive, conversion traits
  • M07 Lifetimes in Practice: what 'a means, elision, structs that borrow, 'static
  • M08 Smart Pointers & Shared State: Box, Rc/Arc, RefCell/Mutex, Cow, OnceLock/LazyLock
  • M09 Closures & Iterator Chains: Fn/FnMut/FnOnce, your own iterator, itertools
  • M10 Visibility, Features & Crate Design: pub(crate), re-exports, Cargo features, cfg, doc comments
  • M11 Testing Like Pixi Does: unit, integration and doc tests, insta snapshots, cargo nextest

Capstone 1 · Manifest reader (5-6 h)

Build a crate that turns a simplified pixi.toml into typed structs with clear errors, resolves each environment's dependencies from its features, and orders tasks by depends-on. It is graded by cargo test with pixi run grade c1.

Gate 1: ready for Level 2?

Before moving on, you should be able to do all of these without looking anything up:

  • Create, build, test, lint, and format a crate with pixi run cargo ..., and split it into modules
  • Say for any variable in a function whether it is owned, borrowed shared, or borrowed mutably, and when it is dropped
  • Read E0382, E0499, E0502, E0505, and E0106 and fix the code without adding .clone() blindly
  • Write a custom error enum with Display, std::error::Error, and From, and propagate it with ?
  • Choose between a generic, impl Trait, and dyn Trait, and explain the trade-off
  • Explain why Pixi passes Arc<...> between tasks instead of references
  • Read a ten-step iterator chain in Pixi and say what it produces
  • Write unit tests, an integration test, and an insta snapshot test, and review a snapshot change
  • Pass all of Capstone 1's graded checks

Level 2 · The Pixi stack planned

Outcome: you know the third-party crates every Pixi file imports well enough to change code that uses them: error reporting, command-line parsing, logging, (de)serialization, format-preserving TOML edits, and async I/O.

Stage 3 · Errors and the CLI (9-11 h)

Pixi's errors are a product feature: a bad pixi.toml produces a message that points at the exact span. This stage teaches the crates behind that, and the CLI layer around it.

  • thiserror: deriving Display, Error, and From for error enums (what you wrote by hand in M04)
  • miette: diagnostics with codes, labels, source spans, and help text; miette::Result and IntoDiagnostic; when to use thiserror and when miette
  • clap derive: #[derive(Parser)], subcommands as an enum, flattened argument groups, as in pixi_cli's Command enum
  • tracing: spans and events, levels, RUST_LOG filters, and how pixi -v maps to a level filter
  • Lab: a small CLI with two subcommands whose errors render as miette diagnostics

Stage 4 · serde and TOML (9-11 h)

Every manifest, lock file, and config file Pixi touches goes through one of these crates, and Pixi uses three different TOML crates for three different jobs.

  • serde derive: Serialize/Deserialize, field attributes (rename, default, flatten, untagged), serde_json and serde_yaml
  • Custom deserializers: visitors, deserialize_with, and accepting "a string or a table" for one field
  • toml-span: parsing with spans kept on every value, so an error can point at a line and column (Pixi's pixi_toml and pixi_manifest crates)
  • toml_edit: changing a document while keeping comments, order, and formatting, which is what pixi add does to your pixi.toml (Pixi's pixi_toml_edit crate)
  • Lab: rewrite part of Capstone 1 with serde, then report errors with spans

Stage 5 · Async (10-13 h)

Pixi downloads repodata and packages concurrently, so most of its code is async. This stage teaches enough to read and change that code with confidence.

  • Futures: what async fn returns, .await, and why nothing runs until a future is polled
  • tokio: the runtime, #[tokio::main] and #[tokio::test], spawning tasks, JoinSet, channels, spawn_blocking
  • Send and Sync in async code: why a future that holds a non-Send value across an .await cannot be spawned
  • Bounded concurrency: futures::stream, buffer_unordered, and semaphores
  • async-trait and native async fn in traits, and why Pixi uses both
  • reqwest: HTTP clients, streaming bodies, middleware, and retries
  • Enough Pin to read the errors it produces, and why Pixi writes Box::pin(...) around large futures

Capstone 2 · mini-pixi (7-10 h)

A small command-line tool that reads a pixi.toml, fetches conda-forge repodata for one platform (from a recorded fixture in tests, so the grader never hits the network), checks that a requested package exists, and adds it to the manifest with toml_edit without disturbing comments or formatting. Errors render as miette diagnostics, and behavior is pinned with insta snapshot tests.

Gate 2: ready for Level 3?

  • Define an error type with thiserror and turn it into a miette diagnostic with a labeled span
  • Add a subcommand with clap derive and log its work with tracing
  • Deserialize a TOML table with serde, including one field that needs a custom deserializer
  • Explain when Pixi uses toml-span, toml_edit, and toml, and why it needs all three
  • Run a bounded number of HTTP requests concurrently with tokio and reqwest, and test it without the network
  • Read a "future is not Send" error and fix it
  • Pass Capstone 2

Level 3 · Working in the Pixi codebase planned

Outcome: you can find where a behavior lives in Pixi, change it, test it the way the maintainers do, and open a pull request that passes review.

Stage 6 · The rattler ecosystem (7-9 h)

Rattler is the set of Rust crates that implement conda: package names, versions, specs, repodata, solving, and lock files. Pixi is mostly orchestration over rattler.

  • rattler_conda_types: PackageName, Version and VersionSpec, MatchSpec, Platform, RepoDataRecord
  • rattler_repodata_gateway: fetching and caching repodata, sharded repodata, and querying only the records a solve needs
  • rattler_solve: turning specs and records into a solution with the resolvo solver
  • rattler_lock: reading and writing pixi.lock
  • Lab: parse match specs and versions, then solve a tiny environment from fixture repodata

Stage 7 · Architecture tour (8-10 h)

Follow one command, pixi add, from the terminal to the lock file, and meet each layer on the way. The codebase map has the first version of this trace.

  • pixi and pixi_cli: the binary, the tokio runtime, the clap Command enum, and add::execute
  • pixi_api and pixi_core: locating the workspace, WorkspaceMut, and update_dependencies
  • pixi_manifest: the parsed manifest and the TOML document edited in place
  • pixi_command_dispatcher and pixi_compute_engine: the graph of deduplicated, cached work behind solving and building
  • Updating the lock file: pixi_core::lock_file, satisfiability checks, and writing pixi.lock
  • Build backends: pixi_build_frontend, pixi_build_types, and backends such as pixi_build_python and pixi_build_rust

Stage 8 · Contributing (6-8 h)

  • Building and testing Pixi with Pixi: the rust-test environment, pixi run build-debug, pixi run test-fast
  • cargo nextest: filtering tests, reading failures, and the slow test features
  • insta review: pixi run insta-review, accepting and rejecting snapshots, and keeping snapshot diffs reviewable
  • House rules: clippy.toml (no std::fs, use fs-err), lefthook.yaml hooks, typos, cargo deny
  • Approaching an issue: reproducing it, finding the code with the codebase map, writing the failing test first, and writing a pull request description

Capstone 3 · A realistic change on a fork (9-13 h)

On a fork of Pixi pinned to the frozen snapshot 451aa959, make a realistic change: a bug fix or a small feature in a CLI command, with a failing test written first, snapshot tests updated and reviewed, and pixi run lint and pixi run test-fast passing. You finish with a branch and a pull request description that a Pixi maintainer could review.

Gate 3: maintainer-ready

  • Build Pixi from source with pixi run build-debug and run its fast test suite
  • Trace any CLI command to the crate and function that does the work
  • Explain how a MatchSpec in pixi.toml becomes a locked package in pixi.lock
  • Change behavior behind a snapshot test and review the snapshot diff
  • Pass the lefthook checks (formatting, clippy, typos) without help
  • Pass Capstone 3

Five to eight hours a week finishes Level 1 in about five weeks. Do not skip the gates: Level 2 assumes ownership and traits are automatic, and Level 3 assumes you can read async code without stopping.

You do not need to finish Level 3 to start reading Pixi pull requests. After Level 1, pick a merged PR that touches one crate, read the diff with the codebase map open, and note every crate or idiom you do not recognize. That list is your personal Level 2 syllabus.
