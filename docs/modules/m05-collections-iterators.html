Collections & Iterators

Almost every function in Pixi takes a collection of something (features, platforms, channels, dependency specs) and turns it into another collection. In Python you do that with lists, dicts, sets, and comprehensions. In Rust you do it with Vec, maps, sets, and iterator chains. This module teaches you the collection types, the three ways to walk them, and the iterator vocabulary that makes up a large share of the Pixi source.

  • Use the entry API to count, group, and insert-if-missing with a single lookup

  • Read and write iterator chains with map, filter, filter_map, enumerate, zip, chain, flat_map, take, and skip

  • Sort, deduplicate, and filter collections in place, including types that are not Ord
  • Treat strings as collections of characters, lines, and fields without indexing them by number

Vec: the growable list

In Python, list is the default container: it grows, it shrinks, and it can hold anything. Rust's equivalent is Vec<T> (say "vector of T"). Two differences matter from the first line you write:

  • Every element has the same type T. A Vec<String> holds only Strings. When you need a mix, you use an enum (M02) or a trait object (M06).
  • The Vec owns its elements. The vector is a small value on the stack (a pointer, a length, and a capacity) that owns a buffer on the heap. When the Vec is dropped, every element is dropped with it. Everything you learned in M03 about moves and borrows applies to it.
deps = ["python", "numpy"]
deps.append("pandas")
last = deps.pop()          # "pandas"
print(len(deps), deps[0])  # 2 python
deps[5]                    # IndexError
let mut deps = vec!["python", "numpy"];
deps.push("pandas");
let last = deps.pop();          // Some("pandas"): pop returns an Option
println!("{} {}", deps.len(), deps[0]);
deps[5];                        // panics: index out of bounds
let maybe = deps.get(5);        // None: no panic

The vec! macro builds a vector from a list of values. Vec::new() builds an empty one (you then need let mut and usually a type annotation such as Vec<String> if nothing tells the compiler what goes in it). Vec::with_capacity(n) reserves room for n elements up front, which avoids repeated reallocations when you know the final size.

Notice where M04's lessons show up. pop returns Option<T> because the vector might be empty. Indexing with v[i] panics when i is out of range, just as Python raises IndexError, while v.get(i) returns Option<&T> so you can handle the missing case. Use v[i] when an out-of-range index would be a bug in your program; use get when it is a normal possibility, such as reading user input.

The last line takes a slice, &deps[1..]: a borrowed view of part of the vector, of type &[&str]. M03 introduced slices; this is where they earn their keep. Functions that only read a sequence should take &[T], not &Vec<T>, because a &Vec<T> converts to &[T] automatically and the slice type also accepts arrays and sub-ranges.

The borrow rules still apply

A Python habit that does not survive: holding on to an element while you change the list. In Python that is harmless. In Rust, push may need a bigger buffer, move every element to it, and free the old one. A reference into the old buffer would then point at freed memory, so the borrow checker forbids it.

The compiler reports E0502: cannot borrow `deps` as mutable because it is also borrowed as immutable. Read the three labels in order: the immutable borrow starts at &deps[0], the mutable borrow is deps.push(...), and the immutable borrow is "later used here" in println!. Any of three fixes works: print first before pushing, copy the value out (let first = deps[0]; works because &str is Copy), or clone it when the element is an owned type like String.

Remember: Vec<T> owns its elements; index with [i] when out-of-range is a bug and with get(i) when it is expected; take &[T] in functions that only read; never hold a reference into a vector while you change it.

Maps: HashMap, BTreeMap, and IndexMap

Python has one mapping type, dict, and since Python 3.7 it remembers insertion order. Rust's standard library has two, and neither remembers insertion order:

TypeKey requirementIteration orderUse it when
HashMap<K, V>K: Hash + EqUnspecified; it can change between runsYou look things up by key and never print or compare the order
BTreeMap<K, V>K: OrdSorted by keyYou need deterministic output, sorted keys, or range queries
IndexMap<K, V> (crate indexmap)K: Hash + Eq Insertion order, like a Python dictThe order the user wrote things in matters

Hash, Eq, and Ord are traits, which M06 covers properly. For now: String, &str, integers, char, bool, and tuples of those all qualify for both maps. Floating-point numbers do not, because NaN != NaN breaks the rules a map relies on.

The basic operations mirror dict, with M04's types in the return values:

use std::collections::HashMap;

let mut versions: HashMap<String, String> = HashMap::new();
versions.insert("python".to_string(), "3.14".to_string());  // returns None: no previous value
versions.insert("python".to_string(), "3.13".to_string());  // returns Some("3.14"): the old value
let v: Option<&String> = versions.get("python");       // look up with a &str, no allocation
let present: bool = versions.contains_key("numpy");
let removed: Option<String> = versions.remove("python"); // the removed value, now owned by you

Two details surprise Python developers. First, get returns Option<&V>, a reference into the map, not a copy; the map still owns the value. Second, a map with String keys can be searched with a &str. That works because String implements a trait called Borrow<str>, which promises that a String and the &str it contains hash and compare the same way. You will see Pixi implement Borrow<str> for its own name types so they can be looked up the same way.

Iteration is where the choice of map shows. Run this cell twice on the Playground: the HashMap line can come out in a different order each time, while the BTreeMap line is always sorted.

Pixi reads a manifest the user wrote by hand, and users expect pixi list, error messages, and the rewritten pixi.toml to keep their order. That is why so many Pixi types use IndexMap and IndexSet from the indexmap crate: a Feature's platforms field is an Option<IndexSet<PixiPlatformName>>, and the workspace's platform list is an IndexSet<PixiPlatform>. Their API is almost identical to HashMap/HashSet, so everything in this module transfers. You do not need them for the exercises.

Course rule, and a real-world one: never print a HashMap or HashSet directly in output someone will compare, such as a test expectation or a snapshot. Use a BTreeMap, or collect and sort first. A test that passes only on lucky hash orders is a flaky test.

Remember: HashMap for fast lookup with no order, BTreeMap for sorted and deterministic, IndexMap (Pixi) for insertion order. insert returns the old value, get returns a reference, remove gives the value back to you.

The entry API: one lookup, no double work

In Python, counting and grouping use a few idioms you probably know by heart:

counts = {}
for word in words:
    counts[word] = counts.get(word, 0) + 1

groups = {}
for name, platform in packages:
    groups.setdefault(platform, []).append(name)   # or collections.defaultdict(list)

Rust's version of setdefault is the entry API. map.entry(key) looks the key up once and returns an Entry, a value that is either occupied (the key is there) or vacant (it is not). Methods on the entry then say what to do in each case, and give you back a &mut V pointing at the value inside the map:

MethodIf the key is missingPython equivalent
.or_insert(v)Insert vd.setdefault(k, v)
.or_insert_with(|| make())Call the closure and insert its result (only when missing)defaultdict(make)
.or_default()Insert V::default(): 0, empty String, empty Vecdefaultdict(int) / defaultdict(list)
.and_modify(|v| ...)Do nothing; when present, change the value firstno direct equivalent

Two things to read carefully in *counts.entry(word).or_insert(0) += 1. or_insert returns &mut usize, a mutable reference to the count stored in the map, so you need the * to change the number it points at. And the whole statement does one hash lookup, where the Python version does two (get, then the assignment).

Why not just write it the Python way? You can (if let Some(c) = counts.get_mut(word) { *c += 1 } else { counts.insert(word, 1); }), and it compiles. But the entry API is shorter, does one lookup, and states the intent: "make sure this key exists, then work on its value." That intent is why it is idiomatic and why you will see .entry(...).or_default() all through Pixi.

When Pixi adds a dependency to a target, the first line is let deps = self.dependencies.entry(spec_type).or_default(); (crates/pixi_manifest/src/target.rs#L394): "get the dependency map for run, host, or build dependencies, creating an empty one if this target has none yet," then it inserts into that map.

Remember: map.entry(k).or_default() is setdefault/defaultdict. It returns &mut V, so you either call a method on it (.push(x)) or dereference it (*... += 1).

Sets: HashSet and BTreeSet

A set is a map with keys and no values, and Rust's two sets follow the same split as the maps: HashSet<T> (needs Hash + Eq, unordered) and BTreeSet<T> (needs Ord, sorted). Pixi adds IndexSet for insertion order.

insert returns a bool: true if the value was new, false if it was already there. That makes "have I seen this before?" a one-liner, which Python can only do with a separate membership check.

The set operations do not build new sets. a.union(&b), intersection, difference, and symmetric_difference return iterators of references into the two sets, because often you only want to loop over the result or count it. When you do want a set, finish with .cloned().collect() or .copied().collect(), which the next sections explain.

Look at the type Vec<&&str>. The set holds &str values, and difference yields references to them, so each item is a reference to a reference. Printing does not care, but storing a &&str is awkward, which is why the first line uses .copied() to turn each &&str back into a &str. Double references come up constantly with iterators; the next section explains where they come from.

Remember: insert on a set returns whether the value was new. Set operations return iterators of references; collect them when you need a new set.

iter, iter_mut, into_iter: who owns the items?

In Python, for x in items always gives you the same thing: a name bound to each object, which is shared with the list. Rust has to answer a question Python never asks: while you loop, does the loop borrow each element, mutably borrow it, or take ownership of it? There is one method for each answer:

MethodItem type for Vec<T>The collection afterwardsfor loop shorthand
v.iter()&TUnchanged and still usablefor x in &v
v.iter_mut()&mut TPossibly changed, still usablefor x in &mut v
v.into_iter()TGone: moved into the loopfor x in v

The shorthand column is the key. A for loop calls into_iter() on whatever you give it. Give it v and it consumes the vector. Give it &v and the "into iterator" of a reference is the borrowing iterator, the same as v.iter(). This is the most common ownership error Python developers hit in their first week:

E0382: borrow of moved value: `names`. The note under it names the culprit precisely: "names moved due to this implicit call to .into_iter()", and the help: line suggests the fix, iterating over &names. Take that suggestion whenever you only need to read. Use for name in names on purpose when you are done with the vector and want to move each String somewhere else without cloning it.

iter_mut is how you change elements in place. Each item is a &mut T, so you write through it with *, or call methods that take &mut self:

Under the hood: the Iterator trait

All three methods return an iterator: a value with a next method that returns Option<Item>, Some(item) while there are items and None at the end. Python's iterator protocol is the same idea, with StopIteration where Rust uses None. A for loop is just "call next until it returns None."

Note let mut it: calling next advances the iterator, which changes it, so the binding must be mutable. And each item is Some(&"conda-forge"), a reference to the &str in the vector, which prints the same as the value itself.

Remember: iter() borrows (&T), iter_mut() borrows mutably (&mut T), into_iter() takes ownership (T). for x in v consumes v; write for x in &v to keep it.

Adapters: map, filter, and friends

Python gives you comprehensions and a few built-ins (map, filter, enumerate, zip, itertools.chain). Rust puts all of these on the iterator itself as adapters: methods that take an iterator and return a new iterator that transforms the items. You chain them left to right, and the chain reads like the steps of a recipe.

pinned = [name.upper() for name in names if name.startswith("py")]
let pinned: Vec<String> = names
    .iter()
    .filter(|name| name.starts_with("py"))
    .map(|name| name.to_uppercase())
    .collect();

The |name| ... parts are closures, Rust's lambdas: |args| expression. M09 covers them in depth; for now read |x| x * 2 as lambda x: x * 2.

filter_map(f)Call f, keep only the Some values, unwrappedy for x in it if (y := f(x)) is not None
enumerate()Pair each item with its index: (usize, item)enumerate(it)
zip(other)Pair items from two iterators, stopping at the shorterzip(a, b)

flat_map(f)Map each item to an iterable and flatten the resultsy for x in it for y in f(x)

filter_map and flat_map

filter_map is the adapter you will see most in Pixi after map. It combines "try something that might not produce a value" with "keep only the successes." The closure returns an Option; Nones disappear and Some(x) becomes x. A classic use is parsing and silently skipping what does not parse, using .ok() from M04 to turn a Result into an Option:

Where the double references come from

filter's closure receives a reference to each item, because filtering only needs to look, and it must give the item back unchanged if it passes. If the items are already references (as with names.iter(), which yields &&str from an array of &str), the closure sees &&&str. Method calls see through any number of references (this is called auto-deref), so |n| n.starts_with("py") just works. Comparisons with == and arithmetic do not; there you either dereference (|n| **n == "rich") or destructure in the parameter (|&&n| n == "rich"). Calling .copied() early, as the first cell did, removes one layer and keeps the closures simple.

Iterators are lazy

An adapter does no work when you call it. It only builds a new iterator that remembers what to do. Nothing runs until something consumes the iterator by calling next. Python's generator expressions behave the same way; Python's list comprehensions do not. The compiler warns you if you build a chain and drop it unused:

Laziness is why long chains are cheap: there are no intermediate lists. A chain of filter, map, and take(3) handles one item at a time from start to finish and stops after the third, however long the input is. The compiler turns the chain into a loop as fast as one you would write by hand.

Remember: adapters return new iterators and do nothing on their own. filter sees &Item; use .copied()/.cloned() to strip a layer of references. filter_map is map-then-keep-the-Somes.

Consumers: getting an answer out

A consumer (the std docs also say "a method that consumes the iterator") calls next until it has its answer, and returns something that is not an iterator. You already used collect and count. The rest of the everyday set:

ConsumerReturnsPython

Notice how often Option appears. Where Python raises (min([]), list.index), Rust returns None, and M04's tools take over.

Read the closure parameters closely, because they differ for a reason. any, all, and position receive each item (&u32 here), so |&s| destructures one reference. find, like filter, receives a reference to the item so it can hand the item back, so it needs |&&s|. If you get the number of &s wrong, the compiler says so with E0308 mismatched types and shows the expected type.

sum needs a type

sum can produce many types (you can sum &i32s into an i32, or Durations, or Options), so the compiler cannot guess which one you want:

E0283: type annotations needed, with the note "cannot satisfy _: Sum<&i32>". The help: line shows the fix: let total: i32 = .... Another spelling is the turbofish, sizes.iter().sum::<i32>(), which puts the type on the method instead of the variable. It is named for its shape, ::<>, and you will see it constantly with collect.

Remember: consumers drive the iterator and return a plain value. Lookups (min, max, find, position) return Option. sum and collect need to be told the result type.

collect: one method, many result types

collect is the most flexible consumer: it builds any collection that knows how to be built from an iterator (the trait is called FromIterator). The type you ask for decides what you get, which is why collect almost always needs an annotation or a turbofish.

You ask forThe iterator must yieldYou get

You can leave the item type as _ and let the compiler fill it in: .collect::<Vec<_>>() means "a vector of whatever the items are."

Collecting that into Result<Vec<T>, E> gives you Ok(vec) if every parse succeeded, and otherwise the first Err, and it stops reading the input at that error. Sorting, deduplicating, and retaining

Python's list.sort(key=...) and sorted() map onto a family of methods on slices (so they work on vectors and arrays). They all sort in place and return nothing, like list.sort(); there is no built-in sorted() that returns a new vector. (The itertools crate adds one, which Pixi uses heavily; that is M09.)

MethodPythonNotes
v.sort()v.sort()Needs T: Ord; stable (equal items keep their order)
v.sort_unstable()noneFaster and uses no extra memory; equal items may swap
v.sort_by_key(|x| key)v.sort(key=...)The key must be Ord and owned
v.sort_by(|a, b| a.cmp(b))functools.cmp_to_keyFull control; b.cmp(a) sorts descending
v.reverse()v.reverse()In place
v.dedup()noneRemoves consecutive duplicates, so sort first
v.retain(|x| keep)v[:] = [x for x in v if keep]Filter in place

A comparison function returns std::cmp::Ordering, an enum with three variants: Less, Equal, Greater. a.cmp(&b) produces one, and .then(...) or .then_with(|| ...) breaks ties, which is how you sort by several keys.

Two things to notice. Plain sort on strings compares bytes, so the capitalized "Pandas" sorts before every lowercase name, as in Python. And dedup only removed the second "numpy" because sorting had put the two next to each other.

Floats are not Ord

Python happily sorts a list of floats. Rust refuses, because f64 has NaN, which is neither less than, equal to, nor greater than anything, including itself. A type is Ord only when every pair of values has an answer.

E0277: the trait bound `{float}: Ord` is not satisfied, "required by a bound in slice::<impl [T]>::sort". E0277 always means "this type does not implement a trait that something requires"; M06 is about exactly that. The fix is to say how to compare: timings.sort_by(|a, b| a.total_cmp(b)). total_cmp defines an order for every float, including NaN.

In pixi search, the JSON output groups records by platform and then sorts each group newest first with records.sort_unstable_by(|a, b| b.cmp(a)), swapping a and b to reverse the order. You will read that function in full in Reading Pixi.

Remember: sorting is in place and needs Ord; sort_by_key is Python's key=; b.cmp(a) reverses; dedup needs sorted input; floats need sort_by with total_cmp.

Strings as collections

A String is a Vec<u8> that is guaranteed to hold valid UTF-8, and a &str is a slice of one. That has a consequence Python hides from you: characters take one to four bytes, so "the third character" cannot be found without walking from the start. Rust refuses to pretend otherwise, and does not let you index a string by number:

E0277: the type `str` cannot be indexed by `{integer}`, with the note "you can use .chars().nth() or .bytes().nth()." Byte ranges do work (&name[0..2]), but they panic if a range boundary falls inside a multi-byte character, so use them only on text you know is ASCII or on positions you got from a search such as find.

Instead of indexing, you iterate. Strings offer several iterators, and everything from the previous sections works on them:

MethodYieldsPython
s.chars()char (a Unicode scalar value)iter(s)
s.bytes()u8s.encode()
s.split(','), s.split(", ")&str pieces (empty pieces included)s.split(",")
s.split_whitespace()Non-empty &str wordss.split()
s.lines()Lines without their \n or \r\ns.splitlines()
s.split_once('=')Option<(&str, &str)>s.partition("=")

And the non-iterator helpers you use with them: trim, trim_start, trim_end, strip_prefix (returns Option), starts_with, contains, find (returns Option<usize>, a byte index), to_lowercase, replace, and parse. Every one that returns a piece of the input returns a &str borrowed from it, with no allocation. Call .to_string() when you need to keep a piece after the input is gone.

split_once splits at the first =, which is why rich=>=13 gives rich and >=13. And len() counts bytes: the ï in "naïve" takes two, so the word is 6 bytes and 5 characters. Python's len would say 5.

Remember: no s[i]; iterate with chars, split, split_whitespace, lines. len() is bytes. Pieces are borrowed &strs; .to_string() them to keep them.

Reading Pixi

Two short functions from the snapshot, both built entirely from this module's ideas. Read the code first, then the explanation.

Grouping search results by platform

pixi search --json prints the matching package records grouped by platform, newest first. This helper builds that grouping (crates/pixi_cli/src/search.rs#L75-L85):

fn build_json_output(packages: &[RepoDataRecord]) -> IndexMap<String, Vec<&RepoDataRecord>> {
    let mut result: IndexMap<String, Vec<&RepoDataRecord>> = IndexMap::new();
    for pkg in packages {
        let platform = pkg.package_record.subdir.clone();
        result.entry(platform).or_default().push(pkg);
    }
    for records in result.values_mut() {
        records.sort_unstable_by(|a, b| b.cmp(a));
    }
    result
}
  • Signature. It borrows a slice of records (&[RepoDataRecord], not a Vec) and returns a map from platform name (subdir, such as "linux-64") to a vector of references into that slice. Nothing is copied except the platform strings.
  • for pkg in packages iterates a &[RepoDataRecord], so pkg is a &RepoDataRecord. That is exactly the type the vectors store.
  • .subdir.clone(): the map needs to own its String keys, and the record only lends its subdir, so the function clones it.
  • entry(platform).or_default().push(pkg) is the grouping idiom from this module: setdefault(platform, []).append(pkg).
  • values_mut() iterates the map's values as &mut Vec<_>, the map version of iter_mut, so each group can be sorted in place.
  • sort_unstable_by(|a, b| b.cmp(a)) sorts each group in descending order. Unstable sorting is fine because two equal records are interchangeable.
  • IndexMap keeps platforms in the order they first appeared in the search results, so the JSON output is deterministic, which a HashMap would not be.

Which platforms can an environment run on?

An environment is a set of features, and a platform is usable only if every feature supports it. This is the ordinary (non-composition) path of FeaturesExt::platforms (crates/pixi_manifest/src/features_ext.rs#L205-L227):

        let exact_names: HashSet<&PixiPlatformName> = self
            .features()
            .filter_map(|feature| feature.platforms.as_ref())
            .flatten()
            .collect();
        let exact_subdirs: HashSet<Platform> = workspace
            .platforms
            .iter()
            .filter(|platform| exact_names.contains(platform.name()))
            .map(PixiPlatform::subdir)
            .collect();
        workspace
            .platforms
            .iter()
            .filter(|platform| {
                self.features()
                    .all(|feature| feature.supports_platform(Some(platform)))
            })
            .filter(|platform| {
                exact_names.contains(platform.name()) || !exact_subdirs.contains(&platform.subdir())
            })
            .map(|platform| platform.name().clone())
            .collect()
  • self.features() returns an iterator over the environment's &Features. (How a trait method can return "some iterator" is M06.)
  • filter_map(|feature| feature.platforms.as_ref()): each feature's platforms is an Option<IndexSet<PixiPlatformName>>; features that do not restrict platforms have None. as_ref() turns &Option<IndexSet> into Option<&IndexSet> (borrowing instead of moving, M04), and filter_map keeps only the features that do restrict.
  • .flatten() turns the iterator of &IndexSets into one iterator of &PixiPlatformNames, and collect builds a HashSet for fast contains checks. The type annotation on let selects the collection.
  • .map(PixiPlatform::subdir) passes a method by name instead of writing |p| p.subdir(). Any function with the right signature can stand in for a closure.
  • The final chain walks the workspace's platforms in manifest order, keeps those that all features support, applies a second rule about exact names, clones the surviving names, and collects. The function's return type, HashSet<PixiPlatformName>, chooses what collect builds, so the last line needs no annotation.
Why does build_json_output clone subdir but not the record?

The map's key type is String, an owned value, so the map must own each key; the record only lends its subdir. The values are &RepoDataRecord, references that borrow from the input slice, so no clone is needed. The cost is that the returned map cannot outlive packages, a relationship M07 teaches you to read from the signature.

If no feature restricts its platforms, what is exact_names, and what does the final chain return?

exact_names is empty: every filter_map call returned None. So is exact_subdirs. The second filter then passes everything (!exact_subdirs.contains(...) is always true), and the result is every workspace platform that all features support, which with no restrictions is every workspace platform.

Could the first statement use flat_map instead of filter_map plus flatten?

Yes: .flat_map(|feature| feature.platforms.iter().flatten()), or even .flat_map(|feature| feature.platforms.as_ref()).flatten(), since an Option is itself iterable. Each spelling is equivalent. The Pixi version reads as two plain steps, "keep the features that have a list, then flatten the lists," which is a reasonable choice for code people review.

Practice

Five exercises, from a warm-up to a small parser. Each is graded by cargo test. Use BTreeMap in your answers wherever the result is a map, so output is deterministic.

Write word_counts(text: &str) -> BTreeMap<String, usize>. Split on whitespace, lowercase each word, and count how often each appears. Use the entry API.

Hint

for word in text.split_whitespace(), then *counts.entry(word.to_lowercase()).or_insert(0) += 1;. to_lowercase already returns an owned String.

use std::collections::BTreeMap;

fn word_counts(text: &str) -> BTreeMap<String, usize> {
    let mut counts = BTreeMap::new();
    for word in text.split_whitespace() {

}

A simplified build_json_output. Write group_by_platform(records: &[(&str, &str)]) -> BTreeMap<String, Vec<String>>. Each record is (package_name, platform). Return a map from platform to the package names on that platform, each list sorted and with duplicates removed.

Hint

Two loops, like the Pixi function: first groups.entry(platform.to_string()).or_default().push(name.to_string()), then for names in groups.values_mut() { names.sort(); names.dedup(); }.

Show solution
use std::collections::BTreeMap;

fn group_by_platform(records: &[(&str, &str)]) -> BTreeMap<String, Vec<String>> {
    let mut groups: BTreeMap<String, Vec<String>> = BTreeMap::new();
    for (name, platform) in records {
        groups.entry(platform.to_string()).or_default().push(name.to_string());
    }
    for names in groups.values_mut() {
        names.sort();
        names.dedup();
    }
    groups
}

Write parse_versions(input: &str) -> Result<Vec<u32>, ParseIntError> for input like "3, 12,, 14 ". Split on commas, trim each piece, skip empty pieces, and parse the rest as u32. If any piece fails to parse, return that error. Use a single iterator chain that ends in collect; no explicit loop.

Hint

input.split(',').map(str::trim).filter(|s| !s.is_empty()).map(|s| s.parse::<u32>()).collect(). The function's return type tells collect to build a Result.

Show solution
use std::num::ParseIntError;

fn parse_versions(input: &str) -> Result<Vec<u32>, ParseIntError> {

        .split(',')
        .map(str::trim)
        .filter(|s| !s.is_empty())

A small version of FeaturesExt::platforms. Write common_platforms(workspace: &[&str], features: &[Vec<&str>]) -> Vec<String>. workspace lists the workspace's platforms in manifest order. Each entry of features is one feature's platform list; an empty list means "no restriction" (the feature supports every platform). Return the workspace platforms that every feature supports, in workspace order.

Hint

Filter the workspace platforms. A platform p passes when features.iter().all(|f| f.is_empty() || f.contains(p)). Then .map(|p| p.to_string()).collect().

Show solution
fn common_platforms(workspace: &[&str], features: &[Vec<&str>]) -> Vec<String> {
    workspace
        .iter()
        .filter(|p| features.iter().all(|f| f.is_empty() || f.contains(p)))
        .map(|p| p.to_string())
        .collect()
}

Write parse_deps(text: &str) -> Result<BTreeMap<String, String>, String> for a tiny [dependencies] body, one name = spec per line:

  • Trim each line. Skip blank lines and lines starting with #.
  • Split each remaining line at the first =; trim the name and the spec. Strip one pair of surrounding double quotes from the spec if present (">=3.12" becomes >=3.12).
  • A line with no =, or with an empty name, is an error: return Err(format!("line {n}: expected name = spec")), where n is the 1-based line number in the original text.
  • A name that appears twice is an error: Err(format!("line {n}: duplicate dependency {name}")).
Hint

Loop over text.lines().enumerate() so you have the index (add 1 for the line number). let Some((name, spec)) = line.split_once('=') else { return Err(...) }; handles the missing =. For quotes, spec.strip_prefix('"').and_then(|s| s.strip_suffix('"')).unwrap_or(spec). For duplicates, insert returns Some(old) when the key was already there.

Show solution
use std::collections::BTreeMap;

fn parse_deps(text: &str) -> Result<BTreeMap<String, String>, String> {
    let mut deps = BTreeMap::new();
    for (index, raw) in text.lines().enumerate() {
        let n = index + 1;
        let line = raw.trim();
        if line.is_empty() || line.starts_with('#') {
            continue;
        }
        let Some((name, spec)) = line.split_once('=') else {
            return Err(format!("line {n}: expected name = spec"));
        };
        let name = name.trim();
        if name.is_empty() {
            return Err(format!("line {n}: expected name = spec"));
        }
        let spec = spec.trim();
        let spec = spec.strip_prefix('"').and_then(|s| s.strip_suffix('"')).unwrap_or(spec);
        if deps.insert(name.to_string(), spec.to_string()).is_some() {
            return Err(format!("line {n}: duplicate dependency {name}"));
        }
    }
    Ok(deps)
}

Mini-project: a dependency report

Mini-projectdep-report: summarize the features of a manifest

Build a small command-line tool that reads a simplified manifest and prints a report about its features. It exercises every collection in this module, and its input looks like the [feature.*] tables you know from Pixi.

pixi init dep-report && cd dep-report
pixi add rust
pixi run cargo init --name dep_report
# write src/main.rs, then:
pixi run cargo run -- sample.toml
pixi run cargo test
pixi run cargo clippy --all-targets -- -D warnings

Input (sample.toml; do not use a TOML crate yet, parse lines by hand):

[feature.default]
python = "3.14.*"
numpy = ">=2"

[feature.test]
pytest = ">=8"
numpy = ">=2"

[feature.docs]
mkdocs = "*"

Output: one line per feature in the order the file defines them, with its dependency count and sorted names; then every package used by more than one feature, sorted, with the features that use it.

default (2): numpy, python
test (2): numpy, pytest
docs (1): mkdocs
shared: numpy in default, test

Suggested design

  • fn parse(text: &str) -> Result<Vec<(String, BTreeMap<String, String>)>, String>: a Vec of pairs keeps the feature order without IndexMap. Reuse your exercise 5 parser for the bodies.
  • fn shared(features: &[(String, BTreeMap<String, String>)]) -> BTreeMap<String, Vec<String>>: build package to features with the entry API, then retain the entries with more than one feature.
  • main reads the file named by the first argument with std::env::args().nth(1) and std::fs::read_to_string, and returns Result<(), Box<dyn std::error::Error>> as in M04.
  • Features print in file order; dependency names within a feature print sorted
  • The shared section is computed with entry(...).or_default() and retain
  • A dependency line outside any [feature.*] header is reported as an error with its line number
  • No HashMap appears in printed output
  • Unit tests cover parsing, an empty feature, and the shared computation
  • pixi run cargo clippy --all-targets -- -D warnings is clean

Stretch goals: add a --platform section using [feature.x.target.linux-64] headers; print the features that share no packages with any other; report a dependency whose spec differs between features (numpy = ">=2" in one, "<2" in another) as a warning.

Quiz

Recap

  • Vec<T> owns its elements. v[i] panics out of range, v.get(i) returns Option. Functions that only read take &[T].
  • HashMap/HashSet are unordered; BTreeMap/BTreeSet are sorted; Pixi's IndexMap/IndexSet keep insertion order.
  • The entry API (entry(k).or_insert(v), .or_default(), .and_modify) counts, groups, and inserts with one lookup.
  • iter borrows, iter_mut borrows mutably, into_iter moves. for x in v consumes v; for x in &v does not.
  • Adapters (map, filter, filter_map, enumerate, zip, chain, flat_map, take, skip) are lazy; consumers (collect, sum, count, any, all, find, position, fold) run them.
  • collect builds whatever type you ask for, including Result<Vec<_>, _>, which stops at the first error.
  • Sorting is in place and needs Ord; dedup needs sorted input; floats sort with total_cmp.
  • Strings cannot be indexed by number. Iterate with chars, split, lines; len counts bytes.
