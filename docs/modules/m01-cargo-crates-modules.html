Cargo, Crates & Modules

Before you can read a single Pixi function you need to know where it lives: which crate, which module, which file, and how the name you see in a use line finds it. This module teaches Cargo, the tool that builds every Rust project, and the module system that organizes code inside a crate. It ends with Pixi's own workspace of 59 crates, which you will be able to navigate by the end.

Cargo: one tool for building, testing, and dependencies

In Python you use several tools for one project: Pixi (or pip) installs dependencies, the interpreter runs code, pytest runs tests, ruff lints and formats, and a build backend such as hatchling makes a wheel. In Rust, Cargo does almost all of that. It reads the project's Cargo.toml, downloads the libraries it needs from crates.io (Rust's PyPI), calls the compiler rustc with the right options, and runs the result.

You still get Cargo itself from Pixi, as in M00. Here is a full session:

pixi init envtool && cd envtool
pixi add rust
pixi run cargo init --name envtool    # Cargo.toml + src/main.rs in the current directory
pixi run cargo run                    # build (if needed) and run: Hello, world!

cargo init sets up a project in the current directory, which is what you want inside a Pixi workspace. cargo new name does the same in a new directory called name. Either way you get two files:

[package]
name = "envtool"
version = "0.1.0"
edition = "2024"

[dependencies]
fn main() {
    println!("Hello, world!");
}

The commands you will use every day:

CommandWhat it does
pixi run cargo buildCompile into target/debug/. Only changed code is recompiled.
pixi run cargo runBuild, then run the program. Arguments after -- go to your program: cargo run -- --verbose.
pixi run cargo checkType-check and borrow-check, but do not produce a program. Much faster than build; use it while you edit.
pixi run cargo testCompile a test build and run every #[test] function.
pixi run cargo clippy --all-targets -- -D warningsLint all code including tests, and fail on any warning.
pixi run cargo fmtReformat every file with rustfmt. cargo fmt --check only reports.
pixi run cargo build --releaseOptimized build into target/release/. Slower to compile, much faster to run.

Why are there two build modes? A debug build (the default, also called the dev profile) compiles quickly, keeps debugging information, and checks integer overflow at run time. A release build spends much longer optimizing. Pixi's binaries on GitHub are release builds; while working on Pixi you use debug builds (pixi run build-debug in Pixi's own workspace).

A test in Rust is a function marked with the attribute #[test]. Attributes are annotations in #[...] that tell the compiler something about the item that follows, a little like Python decorators. Tests usually live in the same file as the code, in a module that is only compiled for tests:

fn subdir(os: &str, arch: &str) -> String {
    format!("{os}-{arch}")
}

fn main() {
    println!("{}", subdir("linux", "64"));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn joins_os_and_arch() {
        assert_eq!(subdir("osx", "arm64"), "osx-arm64");
    }
}

#[cfg(test)] means "only compile this when testing", and mod tests is a module, which the rest of this page explains. M11 covers testing in depth. For now: pixi run cargo test finds and runs joins_os_and_arch.

Pixi treats clippy and rustfmt as part of "done": its pixi run lint task runs both, through lefthook, along with other checks. Get used to running cargo fmt and cargo clippy --all-targets -- -D warnings before you consider any change finished. Clippy's suggestions are also a good way to learn idiomatic Rust.

Remember: check while editing, test to verify, clippy and fmt before you are done, run to try it. Output goes in target/, which you never commit.

Cargo.toml: package and dependencies

Cargo.toml is the manifest of a Rust project, the counterpart of the [project] table in a pyproject.toml, or of pixi.toml. It is TOML, the same format as pixi.toml. The three tables you will meet in every crate are:

  • [package]: the name, version, and edition (the set of language rules; 2024 for everything in this course). Optional fields such as description and license matter when you publish.
  • [dependencies]: libraries your code uses, available everywhere in the crate.
  • [dev-dependencies]: libraries used only by tests, examples, and benchmarks, like a Pixi test feature. They are not compiled into your program.

You add a dependency with cargo add, which edits Cargo.toml for you (Pixi's own pixi add plays the same role for pixi.toml):

pixi run cargo add itertools                       # a normal dependency
pixi run cargo add serde --features derive         # with an optional feature turned on
pixi run cargo add --dev tempfile                  # a dev-dependency
[package]
name = "envtool"
version = "0.1.0"
edition = "2024"

[dependencies]
itertools = "0.15.0"
serde = { version = "1.0.218", features = ["derive"] }

[dev-dependencies]
tempfile = "3.20.0"

(The versions you get will be whatever is newest on crates.io when you run the command.)

Version requirements mean "compatible with"

A plain version in Cargo.toml is a caret requirement. itertools = "0.15.0" means "0.15.0 or any later version that is semver-compatible with it", that is >=0.15.0, <0.16.0. For a version 1.0 or later, serde = "1.0.218" means >=1.0.218, <2.0.0. Semver (semantic versioning) is the rule that breaking changes bump the leftmost non-zero number, so these ranges accept bug fixes and new features but not breaking changes.

This is not how pixi.toml reads versions. In Pixi, numpy = "1.26" is a conda match spec meaning 1.26.*, and ">=1.26" has no upper bound. In Cargo.toml, "1.26" means >=1.26.0, <2.0.0. Same file format, different meaning: read version strings in the context of the tool that owns the file.

Crate names and the hyphen rule

Package names on crates.io may contain hyphens, but Rust identifiers may not. Cargo converts them: the package fs-err is used in code as fs_err. Pixi depends on fs-err and writes use fs_err as fs; (in pixi_docs/src/main.rs), which also renames it locally to fs.

In Cargo.toml, regex = "1.11". Will Cargo accept regex 1.12.0? 1.11.0? 2.0.0? (Yes; yes; no. A caret requirement allows any compatible version at or above the one written.)

Remember: [package] says what you are, [dependencies] what you use, [dev-dependencies] what only tests use. A bare version is a caret requirement: "this or any compatible later version".

Packages and crates; libraries and binaries

Python uses "package" loosely: a directory with an __init__.py, or a thing you pip install. Rust has two precise words.

  • A crate is the unit the compiler builds: one tree of modules compiled together into either a library or a program. Every crate has a crate root, the file where compilation starts.
  • A package is a directory with a Cargo.toml. It contains one or more crates: at most one library crate, and any number of binary crates.
KindCrate rootProducesPython analogy
Library cratesrc/lib.rsCode other crates can use; no mainAn importable package
Binary cratesrc/main.rsAn executable named after the packageA console script entry point
Extra binariessrc/bin/name.rsAn executable called nameMore entry points

Cargo finds these by convention, so most Cargo.toml files have no [lib] or [[bin]] sections. A package with both src/lib.rs and src/main.rs is very common: the library holds the logic and the tests, and main.rs is a thin layer that calls it. The binary uses the library by the package name, like any other dependency:

Why split them? Integration tests (files in tests/) and other crates can only use a library. Keeping main.rs thin means almost all of your code is testable. Pixi takes this to the extreme: the pixi package's main.rs sets up a thread and an async runtime and then calls pixi_cli::execute(), a function in a separate library crate. You will read it in the Reading Pixi section.

People often say "crate" when they mean "package", especially for things on crates.io ("the serde crate"). That is fine in conversation. When it matters, as in "the library crate of the pixi_manifest package", the precise words help.

Remember: a package is a Cargo.toml; a crate is one compiled unit. src/lib.rs is the library root, src/main.rs the binary root, and the binary reaches the library through the package name.

Modules: organizing code inside a crate

In Python every file is a module automatically, and import finds it by searching paths at run time. Rust is explicit. A module is a named scope declared with mod, and every module lives in a tree rooted at the crate root. A file that is not declared with mod somewhere is not part of the crate at all: the compiler never reads it.

Three things to notice. platform::current() is a path: module name, then ::, then the item, much like platform.current() after import platform. The pub keyword makes a function visible outside its module. And &'static str is the type of a string literal (a borrowed string that lives for the whole program); M02 explains it.

Private by default

Python's privacy is a convention: a leading underscore says "please do not use this", but nothing stops you. Rust's is enforced. Every item (function, struct, constant, module) is private unless marked pub, and a private item can be used only inside the module that defines it and that module's descendants. Compile this:

The error is E0603: function `detect` is private. The primary span points at detect in main, and a note: points at its definition. Inside platform, current calls detect with no problem, because both are in the same module. From main, which is in the crate root, it is off limits. Change the call to platform::current() and it compiles.

Why enforce this? Privacy is what lets a maintainer change the inside of a module without breaking the code that uses it. In a 59-crate codebase like Pixi, "nothing outside this module can call this" is a promise you can rely on when you refactor. M10 adds the finer levels pub(crate) and pub(super); you will already see pub(crate) in Pixi below.

Remember: declare modules with mod; reach items with :: paths; everything is private unless pub, and privacy is checked by the compiler (E0603).

Modules in files: foo.rs, foo/, and mod.rs

Inline modules are fine for a few lines. Real crates put each module in its own file. You still write the mod declaration in the parent, but end it with a semicolon instead of a body:

pub mod platform;   // the body is in src/platform.rs (or src/platform/mod.rs)
mod environment;    // the body is in src/environment.rs

mod platform; means "there is a module called platform; load its body from a file". Cargo does not scan the directory for .rs files. If you create src/environment.rs and forget mod environment;, the file is silently ignored, which surprises Python developers.

For a module that itself has child modules there are two layouts, and both are in Pixi:

Newer style: foo.rs next to a foo/ directory

src/
  lib.rs          // mod platform;
  platform.rs     // pub mod host;
  platform/
    host.rs

Older style: foo/mod.rs

src/
  lib.rs          // mod manifests;
  manifests/
    mod.rs        // mod document;
    document.rs

In both, the module platform has a child platform::host. The mod.rs style is the Rust 2015 convention, the counterpart of Python's __init__.py. The 2018 edition added the foo.rs + foo/ style, so that an editor with ten tabs open does not show ten files all called mod.rs. Both are fully supported; a crate should pick one, though large old codebases such as Pixi contain both. You may not use both for the same module.

flowchart TD
    R["crate root: src/lib.rs"] --> P["mod platform: src/platform.rs"]
    P --> H["mod host: src/platform/host.rs"]
    R --> M["mod manifests: src/manifests/mod.rs"]
    M --> D["mod document: src/manifests/document.rs"]
    R --> T["mod tests (inline, #[cfg(test)])"]

The module tree, not the directory tree, is what paths follow. The files are just where the bodies are stored.

If you see error[E0583]: file not found for module `foo`, the compiler looked for foo.rs and foo/mod.rs next to the declaring file and found neither. Check the file name and that you declared the module in the right parent: a child of platform must be declared in platform.rs, not in lib.rs.

Remember: every module is declared by its parent with mod name;. Its body is in name.rs or name/mod.rs; its children live in the name/ directory.

use and paths: crate::, super::, self::

Writing crate::manifests::document::ManifestDocument everywhere would be tiring. A use declaration creates a shorter local name for a path, like from x import y. Unlike Python's import, it runs no code and loads nothing; it is only a name binding, resolved at compile time.

A path can start in four ways:

Path starts withMeaningPython analogy
crate::The root of the current crateAn absolute import of your own package
super::The parent of the current modulefrom .. import x
self::The current modulefrom . import x
A name, such as std:: or itertools::An external crate, or a name already in scope hereimport itertools

A child module may use its parent's private items (cli::add could call super::version() even though version is not pub), because privacy flows downward: a module's descendants are "inside" it. The reverse is not true: cli cannot call a private function of cli::add.

Forms of use you will see in Pixi

use std::collections::BTreeMap;                  // one item
use std::fmt::{self, Display, Formatter};        // several, plus the module itself as `fmt`
use fs_err as fs;                                // rename
use crate::{FeatureName, solve_group::SolveGroupIdx};  // nested paths from the crate root
use super::*;                                    // everything from the parent (common in tests)
pub use environment::{Environment, EnvironmentName};  // re-export (next section)

When a path is wrong, you get E0432 (unresolved import) for a use or E0433 (failed to resolve) for a path in code. Compile this and find the typo from the label.

The span sits under tasks with the label "could not find `tasks` in `manifest`". The module is task. Errors about paths always name the segment where resolution stopped, so read the label for the exact word.

rustfmt sorts the use lines within each block (a block ends at a blank line), and most Pixi files group them as std, then external crates, then crate::/super::. When you read a Pixi file, the use lines at the top are a map of what the file depends on.

Remember: crate:: is absolute from your crate root, super:: is the parent, self:: is here. use only creates a name. Children see their ancestors' private items; parents do not see their children's.

Re-exports: a public face over private files

A crate's internal file layout and its public API do not have to match. pub use makes an item available at a new path: it is a use that other crates can see. The usual pattern is to keep the modules private and re-export the important types from the crate root:

mod environment;                                    // private module
pub use environment::{Environment, EnvironmentName}; // public names at the root

Users of the crate write use pixi_manifest::EnvironmentName; and never need to know the file it is in. The maintainer is then free to move EnvironmentName to another file without breaking anyone. Python packages do the same thing when __init__.py imports names from submodules.

A private use at the crate root also has a useful effect: the name becomes part of the root module, so code anywhere in the crate can reach it with crate::name. Pixi's pixi_manifest has use pixi_consts::consts; in lib.rs line 170, and then environment.rs line 14 writes:

use crate::{FeatureName, consts::DEFAULT_ENVIRONMENT_NAME, solve_group::SolveGroupIdx};

FeatureName is a re-export at the root, consts is the root's import of another crate's module, and solve_group is a private module of the crate. All three are reached the same way.

Remember: pub use re-exports; it decouples the public API from the file layout. When you look for where a type is defined, the pub use lines in lib.rs tell you which module to open.

Cargo.lock: the exact versions

Cargo.toml says which versions are acceptable. The first time you build, Cargo picks one exact version of every crate in the whole dependency graph and records it in Cargo.lock, along with a checksum. Every later build uses exactly those versions until you change them. This is the same job pixi.lock does for your conda and PyPI packages.

Here is a real excerpt from Pixi's Cargo.lock, lines 4169-4185 (the header is lines 1-3):

# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 4
# ...
[[package]]
name = "itertools"
version = "0.14.0"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "2b192c782037fadd9cfa75548310488aabdbf3d2da73885b31bd0abd03351285"
dependencies = [
 "either",
]

[[package]]
name = "itertools"
version = "0.15.0"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "8b4baf93f58d4425749ca49a51c50ebab072c5df6994d08fed93541c331481dc"
dependencies = [
 "either",
]

Two versions of the same crate? Yes. Pixi's own crates ask for itertools = "0.15.0", but some of the crates Pixi depends on ask for 0.14 (and others for older versions still). Those ranges do not overlap, so Cargo compiles each version separately and links both in. Python cannot do this, since one environment holds one version of each package; Rust can, because each crate's dependencies are resolved by name and version at compile time. It costs compile time and binary size, which is why maintainers try to keep the duplicates few.

  • pixi run cargo update picks newer versions within your requirements and rewrites the lock file (like pixi update). cargo update -p itertools updates one crate.
  • --locked makes Cargo fail instead of changing the lock file. CI and release builds use it so the build is exactly what was reviewed. Pixi's own install task runs cargo install --path crates/pixi --locked.
  • Commit Cargo.lock. For programs it is essential for reproducible builds; current Cargo guidance is to commit it for libraries too. Pixi commits its Cargo.lock at the workspace root.

A Pixi-managed Rust project has two lock files: pixi.lock pins the toolchain (the rust conda package and anything else from conda-forge), and Cargo.lock pins the crates. Commit both.

Remember: Cargo.toml is the range, Cargo.lock is the exact choice. Commit the lock file; update it on purpose with cargo update.

Workspaces: many crates, one build

A workspace is a set of packages developed together. They share one Cargo.lock and one target/ directory, so a crate used by ten members is compiled once, and every member agrees on its version. You turn a directory into a workspace with a root Cargo.toml that has a [workspace] table:

[workspace]
resolver = "3"
members = ["crates/*"]

[workspace.package]
edition = "2024"
license = "BSD-3-Clause"

[workspace.dependencies]
itertools = "0.15.0"
envtool_core = { path = "crates/envtool_core" }
[package]
name = "envtool_cli"
version = "0.1.0"
edition.workspace = true     # inherit edition = "2024"
license.workspace = true

[dependencies]
itertools = { workspace = true }       # the version comes from the root
envtool_core = { workspace = true }    # a sibling crate, by path

The pieces:

  • members lists the packages, with globs. exclude removes some. default-members chooses what a bare cargo build at the root builds.
  • resolver = "3" selects the newest dependency resolver behavior (the default for edition 2024 packages, written explicitly at a workspace root).
  • [workspace.package] holds fields that members inherit with field.workspace = true.
  • [workspace.dependencies] declares each dependency's version once. Members say { workspace = true } and may add features or optional = true on top. Upgrading a crate everywhere is then a one-line change.
  • A path dependency ({ path = "..." }) points at a crate on disk instead of crates.io. That is how workspace members depend on each other.

Commands at the root act on the default members; -p (--package) selects one, and --workspace selects all:

pixi run cargo test -p envtool_core       # test one crate
pixi run cargo build --workspace          # build every member
pixi run cargo clippy --workspace --all-targets -- -D warnings

Why split a project into many crates at all? The crate is Rust's unit of compilation and of privacy. Smaller crates compile in parallel and recompile less when one changes, and a crate boundary is a hard API boundary: only pub items cross it. Pixi has 59 member crates for exactly these reasons.

A Cargo workspace and a Pixi workspace are different things that happen to share a name. Pixi's repository is both: its pixi.toml is a Pixi workspace that provides the toolchain and tasks, and its Cargo.toml is a Cargo workspace that lists the crates.

Remember: one root Cargo.toml with [workspace]; members inherit with .workspace = true; versions live once in [workspace.dependencies]; one lock file and one target/ for all.

4. The binary: almost nothing

The pixi package's [dependencies] are just four crates, and its src/main.rs hands everything to the library crate pixi_cli:

        // Box the large main future to avoid stack overflows.
        runtime.block_on(Box::pin(pixi_cli::execute()))

That is the "thin main.rs, logic in libraries" pattern from earlier, at the scale of a real tool. You do not need to understand Box::pin or block_on yet (they come in M08 and Level 2); the point is the path pixi_cli::execute: crate name, then function.

Question: a crate outside pixi_manifest writes use pixi_manifest::environment::EnvironmentName;. Does it compile?

No. mod environment; is private, so the path through it is rejected with E0603 ("module `environment` is private"). The crate must use the re-export: use pixi_manifest::EnvironmentName;.

Question: you want to bump itertools to 0.16 for all of Pixi. How many files do you edit?

One: the root Cargo.toml's [workspace.dependencies] line, plus the regenerated Cargo.lock. Members say itertools = { workspace = true }, so they pick up the new version automatically (and then you fix whatever the breaking changes broke).

Question: where would you open the source of pixi_manifest::platform::host?

crates/pixi_manifest/src/platform/host.rs. The module platform is src/platform.rs, and its child host lives in the platform/ directory.

Practice

Exercises run as one file, so modules are inline (mod name { ... }), but the rules are the same as for modules in files.

The tests call platform::subdir(os, arch) from outside the module. The starter compiles on its own, but the first Check will show an E0603 error because the function is private. Make subdir public. Leave bits private: it is a helper, and subdir can call it because they are in the same module.

Expected: subdir("linux", "x86_64") is "linux-64" and subdir("osx", "arm64") is "osx-arm64".

Hint

Add pub in front of one fn. The tests live in a module that is a sibling of platform, not inside it.

Show solution 
mod platform {
    pub fn subdir(os: &str, arch: &str) -> String {
        format!("{os}-{}", bits(arch))
    }

    fn bits(arch: &str) -> &str {
        if arch == "x86_64" { "64" } else { arch }
    }
}

Only the entry point is pub. Keeping bits private means you could rename or delete it later without checking any code outside platform.

Implement the two functions in environment:

  • env_dir(name) returns "<ENVS_DIR>/<name>", using the constant ENVS_DIR defined at the crate root. env_dir("test") is ".pixi/envs/test".
  • default_env_dir() returns the directory of the environment named by the module's own DEFAULT constant, by calling env_dir. It returns ".pixi/envs/default".

Use crate:: to reach ENVS_DIR and self:: for the items in the same module (plain names also work for those; the point is to practice the paths).

Hint

format!("{}/{name}", crate::ENVS_DIR) builds the first. The second is one call: self::env_dir(self::DEFAULT).

Show solution 
const ENVS_DIR: &str = ".pixi/envs";

mod environment {
    pub const DEFAULT: &str = "default";

    pub fn env_dir(name: &str) -> String {
        format!("{}/{name}", crate::ENVS_DIR)
    }

    pub fn default_env_dir() -> String {
        self::env_dir(self::DEFAULT)
    }
}

ENVS_DIR is private, but environment is a child of the crate root, so it may use it. A plain ENVS_DIR inside environment would not resolve: names from the parent are not automatically in scope in a child module, which is why crate:: (or super::) is needed.

Inside cli there is a private helper binary() and two child modules. Implement:

  • cli::add::command(packages): "pixi add numpy pandas" for &["numpy", "pandas"]. With no packages it returns just "pixi add" (no trailing space).
  • cli::run::command(task): "pixi run test" for "test".

Get the word "pixi" by calling the parent's private binary() with super::, not by writing it again.

Hint

A slice of strings has a join method: packages.join(" ") gives "numpy pandas". Check packages.is_empty() first to handle the no-package case with an if/else whose branches both produce a String.

Show solution 
mod cli {
    fn binary() -> &'static str {
        "pixi"
    }

    pub mod add {
        pub fn command(packages: &[&str]) -> String {
            if packages.is_empty() {
                format!("{} add", super::binary())
            } else {
                format!("{} add {}", super::binary(), packages.join(" "))
            }
        }
    }

    pub mod run {
        pub fn command(task: &str) -> String {
            format!("{} run {task}", super::binary())
        }
    }
}

binary is private to cli, and add and run are inside cli, so they may call it. The if/else is an expression: the function returns whichever branch runs.

Write workspace_deps(section: &str) -> Vec<String>. It receives the text of a [dependencies] table from a member crate's Cargo.toml and returns, in order, the names of the dependencies that inherit from the workspace. A dependency inherits if its line is either form Pixi uses:

  • serde = { workspace = true }, possibly with more keys, such as strum = { workspace = true, features = ["derive"] }
  • once_cell.workspace = true

Skip blank lines, comment lines (starting with #), table headers (starting with [), and dependencies with their own version such as regex = "1.11". Lines may have surrounding spaces.

Hint

Loop with for line in section.lines() and let line = line.trim();. Skip with continue when line.is_empty(), line.starts_with('#'), or line.starts_with('[').

line.split_once('=') returns Some((before, after)) at the first =, or None. Use if let Some((key, value)) = line.split_once('=') { ... }, trim both parts, then check key.strip_suffix(".workspace") (which returns Some(name) if the suffix is there) or value.contains("workspace = true"). name.to_string() turns a &str into a String to push.

Show solution 
fn workspace_deps(section: &str) -> Vec<String> {
    let mut names = Vec::new();
    for line in section.lines() {
        let line = line.trim();
        if line.is_empty() || line.starts_with('#') || line.starts_with('[') {
            continue;
        }
        if let Some((key, value)) = line.split_once('=') {
            let key = key.trim();
            let value = value.trim();
            if let Some(name) = key.strip_suffix(".workspace") {
                if value == "true" {
                    names.push(name.to_string());
                }
            } else if value.contains("workspace = true") {
                names.push(key.to_string());
            }
        }
    }
    names
}

let line = line.trim(); reuses the name for the trimmed version (shadowing, covered in M02). split_once and strip_suffix return an Option, Rust's "maybe a value" type from M04, and if let runs its block only when there is a value. In Level 2 you will parse TOML properly with a real parser instead of by line.

Mini-project: a multi-file crate, then a workspace

Mini-projectenvtool: a library and a binary with modules in files

Build a small package with a library crate split into modules, a thin binary, and tests, using the file layouts from this module. Then turn it into a two-crate workspace the way Pixi is organized.

pixi init envtool && cd envtool
pixi add rust
pixi run cargo init --name envtool
pixi run cargo add itertools

What to build

  • src/lib.rs declares pub mod platform; and mod environment;, and re-exports pub use environment::env_dir;.
  • src/platform.rs (newer layout) with pub fn subdir(os: &str, arch: &str) -> String from exercise 1, and a child module pub mod host; in src/platform/host.rs with pub fn current() -> String that builds the subdir from std::env::consts::OS and std::env::consts::ARCH using super::subdir.
  • src/environment/mod.rs (older layout) with env_dir from exercise 2.
  • src/main.rs only calls the library: it prints envtool::platform::host::current() and envtool::env_dir("default").
  • A #[cfg(test)] mod tests in platform.rs and one in environment/mod.rs, each with at least two #[test] functions.
  • Use itertools somewhere small, for example use itertools::Itertools; and ["a", "b"].iter().join(", "), so that you see a crate dependency resolved into Cargo.lock.
  • pixi run cargo run prints your platform subdir and .pixi/envs/default
  • pixi run cargo test runs at least four tests, all passing
  • Removing mod environment; from lib.rs breaks the build with an error you can explain
  • main.rs cannot call a private function of the library (try it, and read the E0603)
  • Cargo.lock lists itertools with an exact version
  • pixi run cargo clippy --all-targets -- -D warnings and pixi run cargo fmt --check both pass

Stretch goals: convert the project into a Cargo workspace with crates/envtool_core (the library) and crates/envtool (the binary), a root Cargo.toml with [workspace.package] and [workspace.dependencies], and members that use edition.workspace = true and { workspace = true }; then run pixi run cargo test -p envtool_core. Add Pixi tasks test, lint, and fmt to pixi.toml that run the Cargo commands.

Quiz

Recap

  • Cargo builds, runs, tests, lints, and formats. Run it as pixi run cargo ...; use check while editing and clippy + fmt before you are done.
  • Cargo.toml has [package], [dependencies], and [dev-dependencies]. A bare version is a caret requirement. Hyphens in crate names become underscores in code.
  • A package is a Cargo.toml; a crate is a compiled unit. src/lib.rs is the library root, src/main.rs the binary root. Keep main.rs thin.
  • Modules are declared by their parent with mod. Bodies live inline, in name.rs, or in name/mod.rs; children go in name/.
  • Everything is private unless pub. Children see their ancestors' private items.
  • Paths start from crate::, super::, self::, or an external crate's name. use only creates names; pub use re-exports them.
  • Cargo.lock pins exact versions; commit it. A workspace shares one lock file and one target/, and declares versions once in [workspace.dependencies].
