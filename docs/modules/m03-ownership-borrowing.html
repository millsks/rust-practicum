Ownership & Borrowing

Every value in Rust has exactly one owner, and every reference is checked before the program runs. This is the idea that makes Rust different from Python, and it is the idea you will use on every line of Pixi you read. This module builds it from the ground up: where values live, what let b = a; really does, how borrowing works, and how to read the compiler when it says no.

Names in Python, owners in Rust

Start from something you already know well. In Python, a variable is a name that refers to an object. Assignment never copies the object; it adds another name for it.

deps = ["python", "numpy"]
alias = deps            # a second name for the same list
alias.append("pandas")  # mutate through one name...
print(deps)             # ...and the other name sees it
# ['python', 'numpy', 'pandas']

Python keeps the list alive as long as any name refers to it. It does that with a reference count on every object (plus a cycle collector for the cases counting misses). When the count reaches zero, the object is freed. This design is convenient: you never think about who frees what. It has two costs. First, the runtime does bookkeeping on every assignment. Second, and more important for correctness, any part of the program that holds a name can change the object behind every other name's back. That is how a function that "only reads" a list you passed it ends up appending to it, and how a default argument def f(x=[]) leaks state between calls.

Rust takes a different deal. Each value has exactly one owner: the variable (or struct field, or collection slot) responsible for it. When the owner goes out of scope, the value is freed, right there, with no reference count and no garbage collector. Other code can borrow the value through a reference, but the compiler checks every borrow against two rules you will learn below. The result: no use-after-free, no double free, and no data changing behind your back, all proven before the program runs.

Python would print ['python', 'numpy'] twice. Why can Rust not allow two owners of one Vec? Think about what happens at the end of main if both deps and alias tried to free the same buffer.

Remember: in Python, assignment adds a name. In Rust, assignment of a non-Copy value transfers ownership, and the old name stops working. One owner means one free, at a point you can see in the source.

The stack and the heap

To understand why moves exist, you need a picture of where values live. A running Rust program uses two regions of memory.

  • The stack holds each function call's local variables in a frame. A frame is pushed when the function is called and popped when it returns. Everything on the stack has a size known at compile time. Pushing and popping is just moving a pointer, so it is extremely fast.
  • The heap holds data whose size is decided at run time, such as the characters of a string read from a file. You ask the allocator for a block, get back a pointer, and must give the block back exactly once.

An i32 is four bytes and lives entirely on the stack. A String is split in two: a small fixed-size header on the stack with three words (a pointer to the bytes, the length in use, and the capacity allocated), and the bytes themselves on the heap. Vec<T> has the same shape.

You can ask the compiler how big each stack part is. Predict the four numbers before you run this. The Playground runs on 64-bit Linux, where a pointer and a usize are 8 bytes each.

The answers are 4, 24, 24, and 8. A String holding a megabyte of text still has a 24-byte stack part; the megabyte is on the heap. The element type of a Vec does not change its header size either. A reference, &String, is one pointer.

Now the reason moves exist. When you write let b = a; for a String, Rust copies the 24-byte header from a's slot to b's slot. That is cheap. But now two headers point at the same heap bytes. If both were still valid owners, both would free the buffer at the end of the scope (a double free, a classic memory-corruption bug in C), and a change through one would surprise the other. Rust resolves this by declaring the old header dead: the value moved. Python avoids the same problem with reference counting; Rust avoids it with a compile-time rule, so there is no run-time cost at all.

Python has a stack and a heap too, but you never see the difference: every Python object, even the integer 42, is a heap object, and a variable is always a pointer to one. Rust lets you choose, and puts small fixed-size values directly in the stack frame.

Remember: types like String and Vec are a small stack header that owns a heap buffer. A move copies the header and invalidates the old one, so the buffer still has exactly one owner.

Where moves happen

A move is not only let b = a;. Any time a non-Copy value is used by value, it moves. The common places:

let b = a;a into b
consume(a) where fn consume(s: String)a into the parameter s
return s; or a tail expression ss out to the caller
v.push(a)a into the vector, which now owns it

Function calls are the move you will hit most often. Passing a String to a function that takes String gives the function ownership; when the function returns, its parameter goes out of scope and the string is freed. The visualizer shows the two stack frames.

A for loop over a vector by value is the move Python developers trip on most, because in Python iterating never consumes the list.

The error says channels was moved by "channels moved due to this implicit call to .into_iter()". A for loop calls IntoIterator::into_iter on what you give it, and on a Vec by value that hands each String to the loop body, leaving nothing behind. The help: line gives the fix: "consider iterating over a slice of the Vec<String>'s content to avoid moving into the for loop": write for channel in &channels. Then channel is a &String and the vector survives the loop. (M05 covers iter, iter_mut, and into_iter in depth.)

Moves go the other way too: a function can hand ownership back by returning a value. This is how constructors and builders work.

with_channel takes the string by value, changes it, and returns it, so no new allocation is needed for a copy. The caller rebinds the result to the same name with shadowing (from M02). Notice mut spec in the parameter list: once the function owns the value, it can decide to make its binding mutable. Ownership, not the original let, decides who may change a value.

A move is checked at compile time and costs nothing at run time beyond copying the stack header. It is not a deep copy. Python developers sometimes avoid moves because they "feel expensive". They are the cheapest way to pass a String to someone who needs to keep it.

Remember: using a non-Copy value by value moves it: assignment, passing to a function, returning, pushing into a collection, putting in a struct, and for x in v. After a move, the old name is unusable until you assign it a new value.

Copy and Clone

Some types do not move. Run this and notice that a is still usable after let b = a;.

These types implement the Copy trait. A trait is a named set of behaviour a type can have (M06 covers traits fully). Copy means "a bitwise copy of the stack bytes is a complete, independent copy of the value". That is true for a u32: the four bytes are the number. It is false for a String: copying the header would leave two owners of one heap buffer. So for Copy types, using a value by value copies it and the original stays valid; for every other type, it moves.

Copy

All integers and floats, bool, char, shared references &T, and tuples and arrays made only of Copy types. Also your own small structs if you #[derive(Clone, Copy)] and every field is Copy.

Not Copy

String, Vec<T>, HashMap, Box<T>, &mut T, any type with a destructor, and any struct containing one of these. Using them by value moves them.

Clone is the explicit, possibly expensive copy. Calling .clone() on a String allocates a new heap buffer and copies the bytes into it, giving you a second, independent owner. It is the Rust equivalent of Python's list(a) or copy.deepcopy(a) (for nested owned data, clone is deep: cloning a Vec<String> clones every string).

Why does Rust make you write .clone() instead of copying silently? Because the cost is real and should be visible in code review. A .clone() inside a loop over ten thousand packages is ten thousand allocations. When you see one in Pixi, it is a deliberate choice, and reviewers sometimes ask "can this borrow instead?"

You can opt your own types into Copy, but only if every field is Copy. Try it with a field that is not.

This is E0204, "the trait Copy cannot be implemented for this type". The span underlines Copy in the derive and labels the culprit field: "this field does not implement Copy". The fix depends on what you want. Remove Copy and keep Clone, then call p.clone() when you need a second value. Or, if the struct really is small plain data, change the field to a Copy type. (Note that Copy also requires Clone; every Copy type is also Clone, where clone just does the bitwise copy.)

In Pixi you will see .clone() on values of type Arc<T> all over the place. That clone does not copy the data: it bumps a reference count, Python style, and gives you a second handle to the same shared value. That is a deliberate, opt-in use of shared ownership, covered in M08. For now, read .clone() on a String, Vec, or plain struct as "a full copy".

Remember: Copy types are duplicated implicitly and never move; they are small, fixed-size, and own nothing on the heap. Everything else moves, and .clone() is how you ask for an explicit, independent copy, at a cost you can see.

Drop: cleanup at a known point

When an owner goes out of scope, Rust drops its value: it runs the type's cleanup code (its destructor), then frees the memory. For a String, cleanup frees the heap buffer. For a file, it closes the file descriptor. For a lock guard, it releases the lock. The rule is simple and fully deterministic:

  • A value is dropped when its owner goes out of scope, at the closing }.
  • Locals are dropped in reverse order of declaration (last declared, first dropped), so a value never outlives something declared before it that it might depend on.
  • A value that was moved out of a variable is not dropped there; its new owner drops it.
  • You can drop early with drop(value), which is just a function that takes ownership and does nothing, so the value dies at the end of drop.

You can watch this happen by implementing the Drop trait yourself. Predict the order of the four lines before running.

b is dropped first because drop(b) moves it into the drop function. Then main prints, then the remaining locals drop in reverse order: c, then a. (The leading underscore in _a tells the compiler the variable is intentionally unused, without dropping it early. A bare let _ = Noisy("x"); would drop immediately, because _ does not bind at all.)

with open("pixi.toml") as f:
    text = f.read()
# f is closed here because of `with`.

f2 = open("pixi.lock")
# f2 is closed... eventually, when the
# reference count hits zero. __del__ timing
# is an implementation detail.
{
    let text = std::fs::read_to_string("pixi.toml")?;
    let f2 = std::fs::File::open("pixi.lock")?;
    // use f2...
} // f2 is closed here, every time: it is dropped
  // at the end of its scope. No `with` needed.

This pattern, where a value's lifetime controls a resource, is called RAII ("resource acquisition is initialization"). It is why Rust has no with statement and no finally: the scope is the with block, for every value, automatically.

Pixi uses Drop to report progress. A ScopedTask marks a task finished when it goes out of scope, so the progress bar is correct even if the code returns early with an error (crates/pixi_progress/src/lib.rs):

impl Drop for ScopedTask {
    fn drop(&mut self) {
        if let Some(state) = self.state.take() {
            state
                .lock()
                .notify(Operation::Finished(std::mem::take(&mut self.name)));
        }
    }
}

drop receives &mut self, not self, so it cannot move self.name out directly. std::mem::take swaps an empty String in and hands back the old one, which is the standard trick for that. You will meet it again in the error section.

Remember: values drop at the end of their owner's scope, in reverse declaration order, or earlier with drop(x). Moved-out values are dropped by their new owner. Cleanup is deterministic, so files, locks, and progress bars are released exactly where the scope ends.

Shared references: &T

If every function call moved its arguments, you would spend your life returning values back to callers. Instead, you borrow. &value creates a shared reference: a pointer that lets you read the value without owning it. The owner keeps ownership; when the reference is no longer used, nothing is freed.

Two things to see. The type &String in the signature says "I borrow a String; I do not own it". And the caller writes &name at the call site, so a reader of main can see that describe cannot keep or free the string. That visibility is a big part of why reviewing Rust is easier than reviewing Python: the signature tells you what a function can do to its arguments.

A few mechanics you will use constantly:

  • Any number of shared references can exist at once. Reading from many places at the same time is always safe.
  • Shared references are Copy. Passing r to a function copies the pointer; you still have r.
  • Method calls borrow automatically. name.len() is really String::len(&name). The method's first parameter, &self, tells the compiler to borrow, so you do not write the &. This is called auto-referencing.
  • *r dereferences. It means "the value r points to". You need it for operators on Copy values (*count + 1); for method calls and field access, Rust dereferences for you.
  • A reference cannot outlive its owner. The compiler rejects any reference that would still be used after the owner is dropped. Python cannot have a dangling reference because the reference keeps the object alive; Rust cannot because the compiler refuses to compile one.

A shared reference is read-only. Trying to change the value through it fails with E0596.

E0596 reads "cannot borrow *channels as mutable, as it is behind a & reference". push needs &mut self, and you only have &. The help: line proposes the fix: "consider changing this to be a mutable reference: &mut Vec<String>". That leads to the next section.

Remember: &T borrows for reading. The owner keeps ownership, many shared borrows may coexist, and the borrow can never outlive the owner. The & at the call site tells readers the callee cannot keep or change the value.

Mutable references: &mut T

To change a value you do not own, you need a mutable reference, &mut T. It comes with a stronger promise: while it is in use, it is the only way to reach that value. Nobody else may read or write it. For that reason it is often called an exclusive reference, which is a better name than "mutable".

Three places say "mutable" here, and each is required. let mut channels makes the binding mutable, which is needed before anyone can borrow it mutably. &mut Vec<String> in the signature declares that the function may change its argument. And &mut channels at the call site makes the caller say so too. Compare a Python function: def add_channel(channels, name) gives you no way to tell, from the call, whether channels will be changed.

If you forget let mut, the compiler tells you exactly where to add it.

E0596 again, this time "cannot borrow deps as mutable, as it is not declared as mutable", with help: consider changing this to be mutable: mut deps. In Rust, immutability is the default and mutation is something you opt in to at each level.

A mutable reference can also replace the whole value, using * to assign through it:

*label = String::from("fresh"); drops the old string ("stale") and moves the new one into the caller's variable. The caller still owns label; the function only changed what it holds.

Remember: &mut T is an exclusive loan. It needs a mut binding, it shows up in both the signature and the call, and while it is live it is the only access path to the value.

The borrowing rules, and why they exist

Everything so far comes down to two rules that the compiler's borrow checker enforces:

  1. At any moment, a value may have either any number of shared references (&T) or exactly one mutable reference (&mut T). Never both.
  2. Every reference must be valid for as long as it is used: it cannot outlive the value it points to.

The short form is aliasing XOR mutation: data can be shared, or it can be changed, but not both at once. To see why, take the bug that Python lets you write.

deps = ["python", "numpy", "numpy-base"]
for d in deps:
    if d.startswith("numpy"):
        deps.remove(d)     # mutating the list while iterating it
print(deps)
# ['python', 'numpy-base']  -- "numpy-base" was skipped

The loop holds a position in the list while the body changes the list underneath it. Python gives you a wrong answer silently (for a dict, a RuntimeError: dictionary changed size during iteration at run time). In Rust the stakes are higher: Vec::push may need more capacity, so it allocates a bigger buffer, copies the elements over, and frees the old one. Any reference into the old buffer would then point at freed memory. Here is the smallest version.

This is E0502, "cannot borrow deps as mutable because it is also borrowed as immutable". Read the three labels in order: (1) "immutable borrow occurs here" under &deps[0], (2) "mutable borrow occurs here" under deps.push(...) (because push takes &mut self), and (3) "immutable borrow later used here" under the println!. Label 3 is the key: the shared borrow is still needed after the push, so the two overlap. Two fixes, depending on what you need. If you only need first before the push, move the println! up. If you need it after, take an owned copy: let first = deps[0].clone();. Then first owns its own string and is not a borrow of deps at all.

Two mutable borrows: E0499

Rule 1 also forbids two &mut to the same value at once, even if neither is a "reader".

E0499, "cannot borrow name as mutable more than once at a time". Again three labels: first mutable borrow, second mutable borrow, and "first borrow later used here". The fix is to let the first borrow end before the second starts: do all the work through a, then take b. In real code this error usually shows up as "I called a &mut self method while holding a &mut to one of my fields"; the fix is the same: shorten one of the borrows, or split the work so each borrow is used and finished in turn.

Borrows end at their last use

A borrow does not last until the closing brace. It lasts from where it is created to where it is last used. This is called non-lexical lifetimes (NLL), and it is why the following compiles even though first is still "in scope" when push runs.

first is last used on line 4, so its borrow is over before the push on line 5. count is last used on line 7, so by line 8 deps can be read again. When you get a borrow error, the question to ask is not "which variables are in scope?" but "which borrows are still going to be used?". The compiler's "later used here" label answers it for you.

Python's list mutation during iteration and C's use-after-free are the same bug at different levels: a reader and a writer touching the same data at once. Rust forbids that combination everywhere, at compile time. The same rule is what makes Rust's threads safe: a value that two threads can read cannot be written by either, unless you use a type designed for it (M08).

Remember: many &T or one &mut T, never both, and no reference outlives its owner. A borrow lasts until its last use. When the checker complains, find the "later used here" label: that is the use that keeps the conflicting borrow alive.

Slices: &str and &[T]

A slice is a borrowed view of a contiguous run of elements owned by something else. It is a reference with two words instead of one: a pointer to the first element and a length. Rust has two slice types you will use daily:

  • &str, a string slice: a view of UTF-8 bytes. It can point into a String's heap buffer, or into the program's read-only data (every string literal like "pixi" is a &'static str, a slice that lives for the whole program).
  • &[T], a slice of T: a view of some elements of a Vec<T>, an array [T; N], or another slice.

You make slices with range indexing. Like Python, the end is exclusive; unlike Python, there are no negative indexes, and indexes are byte offsets for strings.

The last line prints 16: a slice reference is two words, the pointer and the length. Python's spec[0:5] copies the characters into a new string; Rust's &spec[0..5] copies nothing, it points into spec. That is why slices are borrows, and why the borrow rules apply to them: while name is in use, spec cannot be changed.

String slice indexes are byte offsets and must fall on character boundaries. &"café"[0..4] panics at run time with "byte index 4 is not a char boundary", because é takes two bytes. Prefer methods that find boundaries for you: split_once, find, strip_prefix, trim, split. Most of them return &str slices of the original, with no allocation.

Take &str, not &String

Earlier, describe took &String. That works but is too strict: a caller holding a string literal, or a slice of a bigger string, cannot call it without allocating a String first. Take &str instead. A &String converts to &str automatically at the call site (this is deref coercion: String knows how to present itself as a str), so you lose nothing.

The same rule applies to sequences: take &[T] instead of &Vec<T>. A &Vec<T> coerces to &[T], and arrays and sub-slices work too. Clippy, the Rust linter, flags &String and &Vec<T> parameters with its ptr_arg lint, and Pixi runs clippy with warnings as errors.

When to take ownership instead

Borrowing is the default, but not always right. Use this table when you design a signature:

The function...Parameter typeExample
only reads the text&strfn is_direct_url(url_scheme: &str) -> bool
only reads the elements&[T]fn total(sizes: &[u64]) -> u64
changes the caller's value in place&mut T / &mut Vec<T>fn dedup_matches(results: &mut Vec<Match>)
stores the value (in a struct, a collection, a thread)String / Vec<T>fn new(name: String) -> Self

If a function will store a string, taking String is better than taking &str and calling .to_string() inside: the caller may already have a String it no longer needs, and can move it in for free. Taking ownership makes the cost visible to the caller instead of hiding an allocation.

Pixi's reporter wraps long notice lines without copying them, by repeatedly re-slicing a &str (crates/pixi_reporters/src/repodata_reporter.rs, trimmed):

fn push_wrapped_notice_line(rendered: &mut String, line: &str, width: usize) {
    let mut remainder = line;
    loop {
        // ...
        rendered.push_str("  │ ");
        rendered.push_str(remainder[..split].trim_end());
        rendered.push('\n');
        remainder = remainder[split..].trim_start();
        // ...
    }
}

The output buffer is borrowed mutably (&mut String) because the function appends to the caller's string. The input is borrowed shared (&str). remainder is a &str that starts as the whole line and is re-pointed at smaller and smaller tails of it. No allocation happens except the appends to rendered.

Remember: a slice is a borrowed (pointer, length) view into data owned elsewhere. Take &str and &[T] for read-only parameters; take owned String/Vec when the function keeps the value.

Reading borrow-checker errors

Borrow errors look intimidating at first, but they all have the same shape, and once you can read the shape you can fix most of them in seconds. Every one has:

  1. An error code in brackets, like error[E0505]. Run pixi run rustc --explain E0505 for a full explanation with examples.
  2. A headline that names the variable and the conflict.
  3. Labelled spans, usually three: where the first thing happened (a borrow or a move), where the conflicting thing happened, and where the first thing is later used. Read them in source order.
  4. help: and note: lines, often with a concrete suggested edit.

You have already met E0382, E0499, E0502, and E0596. Two more are common in real code.

E0505: moving out while borrowed

E0505, "cannot move out of name because it is borrowed". The labels: "borrow of name occurs here" (line 7), "move out of name occurs here" (line 8), "borrow later used here" (line 9). Moving name into archive would free it when archive returns, and then r would dangle. Fixes: use r before the move; pass a clone (archive(name.clone())); or, best, make archive borrow (&str) if it does not need to own.

E0507: moving out of a borrow

You cannot take ownership of something you only borrowed, or of an element inside a collection, by plain assignment. The owner would be left with a hole.

E0507, "cannot move out of index of Vec<String>", with "move occurs because value has type String, which does not implement the Copy trait". names[0] is a place inside a vector you only borrowed. The help: line offers two fixes: borrow it (let first = &names[0];, then return &str or clone at the end) or clone it (names[0].clone()). If you own the vector and really want to take the element out, the standard tools are:

  • v.remove(i) or v.swap_remove(i): take the element out, shrinking the vector.
  • std::mem::take(&mut v[i]): take the value and leave its type's default (an empty String) in its place. Works through any &mut, which is why Pixi's Drop impl above uses it.
  • std::mem::replace(&mut v[i], new_value): same, with a replacement you choose.
  • opt.take() on an Option: take the value and leave None (more in M04).

A fix strategy that works

When you hit a borrow error, try these in order. Each step costs a little more than the one before it.

  1. Reorder. Finish using the first borrow before the conflicting action (NLL does the rest).
  2. Borrow instead of move. Change a parameter from String to &str or from Vec<T> to &[T]; iterate with for x in &v.
  3. Shrink the borrow. Copy out the small thing you need (let n = v.len();, or an index instead of a reference) and drop the reference.
  4. Take with a placeholder. mem::take, mem::replace, Option::take.
  5. Clone. It is a fine answer for small values or code that is not hot. Measure before you worry.
  6. Restructure ownership. Shared ownership (Rc/Arc) or interior mutability (RefCell/Mutex), covered in M08. Reach for these when the data really is shared, not to silence the checker.

Reveal a fix

E0502: the loop holds a shared borrow of deps (from &deps) for its whole body, and clear needs &mut. This is exactly the Python "mutate while iterating" bug. Strategy 3: record what you need during the loop, act after it.

let mut saw_numpy = false;
for d in &deps {
    if d == "numpy" {
        saw_numpy = true;
    }
    println!("{d}");
}
if saw_numpy {
    deps.clear();
}

Maintainers read borrow errors from the bottom label up: "later used here" tells you which use keeps the first borrow alive, and that is almost always the line you need to move or change. Do not sprinkle .clone() until the error goes away without reading it; reviewers on Pixi will ask why each clone is there.

Remember: code, headline, labelled spans, help. Find the two conflicting actions and the "later used" line, then reorder, borrow, shrink, take, or clone, in that order.

Reading Pixi

Two short functions from the frozen snapshot show the ideas of this module in real code. Both deal with virtual packages: entries like __glibc or __cuda that describe the machine, which the solver treats as installed packages.

Borrow a slice, return an owned copy

From crates/pypi_modifiers/src/pypi_tags.rs:

/// Look up an exact-name declaration on `declared`.
fn declared_version(declared: &[GenericVirtualPackage], name: &str) -> Option<Version> {
    declared
        .iter()
        .find(|virtual_package| virtual_package.name.as_normalized() == name)
        .map(|virtual_package| virtual_package.version.clone())
}
  • declared: &[GenericVirtualPackage]: the function reads a list of packages it does not own. It takes a slice, not &Vec, so callers can pass any contiguous list.
  • name: &str: the name to look for is only compared, so it is borrowed.
  • -> Option<Version>: the result is owned. Either there is a matching package, and you get its version, or there is none (Option is M04).
  • .iter() walks the slice by shared reference; .find(...) returns a reference to the first match. Both are borrows of declared.
  • .map(|virtual_package| virtual_package.version.clone()): the found item is a &GenericVirtualPackage. Returning virtual_package.version directly would be moving a field out of a borrow (E0507). So the function clones the version, giving the caller an independent value that does not borrow declared.

Mutate through &mut Vec, with borrows that end in time

From crates/pixi_manifest/src/platform.rs:

/// Insert any subdir default that is not already present in `declared` (by
/// virtual-package name). Entries already in `declared` win, so a user-set
/// `__linux = "5.10"` is preserved untouched. ...
pub(crate) fn merge_subdir_defaults(declared: &mut Vec<GenericVirtualPackage>, subdir: Platform) {
    let has_libc = declared
        .iter()
        .any(|gvp| matches!(gvp.name.as_normalized(), "__glibc" | "__musl" | "__eglibc"));
    for default in subdir_default_virtual_packages(subdir) {
        if default.name.as_normalized() == "__glibc" && has_libc {
            continue;
        }
        if declared.iter().any(|gvp| gvp.name == default.name) {
            continue;
        }
        declared.push(default);
    }
}
  • declared: &mut Vec<GenericVirtualPackage>: the function adds to the caller's list, so it needs an exclusive borrow. It takes &mut Vec, not &mut [T], because a slice cannot grow: push is a Vec method.
  • subdir: Platform is taken by value. Platform is a small Copy enum, so "by value" just copies it.
  • let has_libc = declared.iter().any(...) borrows declared shared, but only for that expression. The result is a plain bool, which does not borrow anything, so by the next line the shared borrow is over.
  • for default in subdir_default_virtual_packages(subdir): the function returns owned packages and the loop consumes them, so each default is owned by the loop body.
  • declared.iter().any(|gvp| gvp.name == default.name) is another short shared borrow that ends when any returns, so the following declared.push(default) may take &mut. That push also moves default into the vector.
Why does declared_version return Option<Version> instead of Option<&Version>?

Returning a reference would also work (the reference would borrow declared, which the compiler allows via lifetime elision, M07). But the caller then could not change the list while holding the result. Cloning a version is cheap and frees the caller from that constraint. Owning the result is often the simplest API.

What would go wrong if has_libc were computed inside the loop, after a push?

It would still compile (each borrow is short), but the meaning would change: after pushing a default __glibc, the check would see it and skip later libc entries. Computing it once, before any push, captures the user's original declarations. Borrow rules keep the code memory-safe; you still have to think about the order of reads and writes for correctness.

Could the second check be written as let exists = declared.iter().find(...); declared.push(default); with exists used after the push?

No. find returns Option<&GenericVirtualPackage>, a borrow into declared. Using it after push keeps the shared borrow alive across a mutable one: E0502, for exactly the reallocation reason shown in the visualizer. any returns a bool, which is why Pixi's version is fine.

Write first_word(s: &str) -> &str that returns the part of s before the first space, or all of s if there is no space. Return a slice of the input; do not allocate a String. Leading spaces are not trimmed: first_word(" x") is "".

count_pinned counts the specs that contain "==" (an exact pin). As written, it takes the vector by value, so the caller loses it. Change the signature so it borrows a slice, count_pinned(specs: &[String]) -> usize, and write the body.

The tests call count_pinned(&specs) and then use specs again, so the starter will not compile against them: the first Check shows a type error (E0308, expected Vec<String>, found &Vec<String>). That is your clue.

Hint

Loop with for s in specs (on a slice, each s is a &String) and test s.contains("==").

Show solution 
fn count_pinned(specs: &[String]) -> usize {
    let mut n = 0;
    for s in specs {
        if s.contains("==") {
            n += 1;
        }
    }
    n
}

Write ensure_channel(channels: &mut Vec<String>, name: &str) -> bool. If name is not already in channels, append it and return true. If it is already there, leave the list alone and return false. Calling it twice with the same name must not create a duplicate.

Hint

Check first with a short shared borrow (channels.iter().any(|c| c == name), which gives a plain bool), then push name.to_string(). That is the same shape as Pixi's merge_subdir_defaults.

Show solution 
fn ensure_channel(channels: &mut Vec<String>, name: &str) -> bool {
    if channels.iter().any(|c| c == name) {
        return false;
    }
    channels.push(name.to_string());
    true
}

A dependency spec looks like "numpy >=2.1": a name, optional spaces, then an optional constraint. Write split_spec(spec: &str) -> (&str, &str) returning the name and the constraint, both trimmed of surrounding spaces. The name ends at the first space or at the first of the characters <, >, =, !, ~. If there is no constraint, the second part is "". Both parts must be slices of the input.

Hint

Trim first: let spec = spec.trim(); (that is also a slice). Then find the split point with spec.find(|c: char| c == ' ' || "<>=!~".contains(c)). Slice before and after it, and trim the second part.

Show solution 
fn split_spec(spec: &str) -> (&str, &str) {
    let spec = spec.trim();
    match spec.find(|c: char| c == ' ' || "<>=!~".contains(c)) {
        Some(i) => (&spec[..i], spec[i..].trim()),
        None => (spec, ""),
    }
}

You are given a mutable slice of packages. Write drain_names(pkgs: &mut [Package]) -> Vec<String> that moves every package's name out into the returned vector, in order, and leaves an empty string in each package's name. Versions are untouched. Do not clone: the tests check that the returned strings are the original allocations.

The naive names.push(p.name) fails with E0507 ("cannot move out of p.name which is behind a mutable reference"). Use the tool from the error section that takes a value and leaves a placeholder.

Hint

Loop with for p in pkgs.iter_mut() (or for p in pkgs, which on a &mut [T] gives &mut T) and push std::mem::take(&mut p.name).

Show solution 
#[derive(Debug, PartialEq)]
struct Package {
    name: String,
    version: String,
}

fn drain_names(pkgs: &mut [Package]) -> Vec<String> {
    let mut names = Vec::with_capacity(pkgs.len());
    for p in pkgs {
        names.push(std::mem::take(&mut p.name));
    }
    names
}

Mini-project

Mini-projectA dependency list that owns its specs

Build a small library type that stores dependency specs and hands out borrows of them, the way a manifest type in Pixi owns its data and lends it to the rest of the program. The point is to design each method's signature deliberately: who owns, who borrows, who mutates.

Set up the project with Pixi:

pixi init deplist && cd deplist
pixi add rust
pixi run cargo init --lib --name deplist
pixi run cargo test

In src/lib.rs, write:

  • pub struct DepList { specs: Vec<String> } with pub fn new() -> Self.
  • pub fn add(&mut self, spec: String) -> bool: stores the spec unless one with the same name (the part before the first space or operator, as in exercise 4) is already present; returns whether it was added. It takes String because it keeps the value.
  • pub fn get(&self, name: &str) -> Option<&str>: the stored spec for a name, borrowed. (You can write the body with a for loop and return Some(s); None means not found. M04 covers Option.)
  • pub fn names(&self) -> Vec<&str>: every name, as slices of the stored specs.
  • pub fn remove(&mut self, name: &str) -> Option<String>: takes the spec out and gives ownership to the caller.
  • pub fn into_specs(self) -> Vec<String>: consumes the list and returns its contents.

Write tests in a #[cfg(test)] mod tests block at the bottom of lib.rs (you will see this layout properly in M11).

Acceptance criteria

  • pixi run cargo test passes with at least six tests, one per method plus a duplicate-name test
  • No method clones a spec except where you can explain why in a comment
  • A test shows that after let n = list.names(); you cannot call list.add(...) while n is still used (write it, see the E0502, then comment it out with a note)
  • A test shows into_specs consumes the list (using list afterwards is E0382; again comment it out with a note)
  • pixi run cargo clippy --all-targets -- -D warnings is clean

Stretch goals

  • Add pub fn rename(&mut self, old: &str, new: &str) -> bool that edits the stored spec in place without removing and re-adding it.
  • Add pub fn constraints(&self) -> Vec<(&str, &str)> returning (name, constraint) pairs that borrow the stored data.
  • Implement Drop for DepList that prints how many specs were dropped, and write a small main in examples/ that shows when it runs.

Quiz

Recap

  • Python names share one object; Rust values have exactly one owner, which frees the value when it goes out of scope.
  • String and Vec are a stack header (pointer, length, capacity) owning a heap buffer. A move copies the header and invalidates the old name.
  • Values move on assignment, function calls, returns, pushes, struct construction, and for x in v. Copy types (scalars, &T, tuples of them) are copied instead.
  • .clone() is an explicit, visible copy. On Arc it is a cheap reference-count bump.
  • Values drop at the end of scope, in reverse declaration order, or early with drop(x).
  • &T is a shared, read-only borrow; &mut T is an exclusive borrow. Many readers or one writer, never both, and never past the owner's life. Borrows end at their last use.
  • Slices (&str, &[T]) are borrowed (pointer, length) views. Take them as parameters for read-only data; take owned values when you store them.
  • Read errors by code, headline, the three labels, and help:. Fix by reordering, borrowing, shrinking, mem::take, or cloning, in that order.
