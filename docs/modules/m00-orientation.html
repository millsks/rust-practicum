Why Rust, and why Pixi is written in it

Pixi is a package manager and task runner for conda packages and PyPI packages. You type pixi add numpy, and Pixi reads pixi.toml, downloads channel metadata, runs a dependency solver, writes pixi.lock, downloads and unpacks packages, and links them into .pixi/envs/default. All of that is written in Rust, a compiled language from the same family as C and C++ that adds strong guarantees about memory and threads. If you want to fix a bug in Pixi, review a pull request, or add a feature, you need to read and write Rust.

It is worth knowing why the Pixi authors chose Rust, because the same reasons explain most of the rules you will meet in this course. There are four.

Speed

Rust compiles to native machine code, with no interpreter and no garbage collector pausing the program. Solving an environment means checking hundreds of thousands of package records; installing one means hashing and unpacking thousands of files, many at once on several threads. That work is often ten to a hundred times faster in Rust than in Python, and it is the reason pixi install feels quick.

A single binary

A Rust program builds into one executable file with its dependencies compiled in. Pixi is one pixi file that you download and run. It does not need Python to be installed, which matters for a tool whose job is to install Python. A package manager written in Python has a chicken-and-egg problem: which Python runs the tool that installs Python?

Correctness

The Rust compiler rejects whole classes of bugs before the program ever runs: using a value after it was freed, two threads writing the same data at once, forgetting that a value can be missing, or ignoring an error. For a tool that rewrites files in your project and your environments, "the compiler will not let you forget the error case" is worth a lot.

The conda/rattler ecosystem

Pixi is built on rattler, a family of Rust crates (libraries) from the same team that implement the conda ecosystem: package records and match specs (rattler_conda_types), the solver (rattler_solve, using the resolvo solver), lock files (rattler_lock), and more. For PyPI packages Pixi reuses crates from uv, which is also written in Rust. Choosing Rust means using these libraries directly instead of shelling out to other programs.

Each of these benefits has a price, and you will pay it while learning. The compiler is strict. You must say what type each value has, who is responsible for freeing it, and what happens when something fails. The course is designed so that each strict rule arrives with the reason it exists and the Pixi code that depends on it.

Here is your first Rust program. Press Run. The code is sent to the official Rust Playground, compiled, and run; the output appears below the cell.

Even this tiny program shows three things you will see on every page. fn main() is where a program starts (Python runs a file top to bottom; Rust starts at main). let creates a variable. println! prints a line, and the {tool} inside the string is filled in from the variable of that name, just like a Python f-string. The ! marks println! as a macro, code that the compiler expands into more code before compiling it; for now, read it as "a function with a !".

Remember: Pixi is written in Rust for speed, for a single binary that needs no Python, for compile-time correctness, and to use the rattler crates directly. The strict rules you are about to learn are what buy those properties.

Code cells: the Rust Playground in your browser

You do not need anything installed to follow the lessons. Code cells send their code to the official Rust Playground (play.rust-lang.org), which compiles it with Rust stable, edition 2024, in debug mode. An edition is a named set of language rules (2015, 2018, 2021, 2024); new editions can change small details, and every crate says which edition it uses. Pixi uses edition 2024, and so does this course. You can edit any cell and run it again; reloading the page restores the original.

There are four kinds of cell.

Run

A plain cell, like the one above. Press Run and read the output. If the code has fn main, it runs; if it has no main, the Playground compiles it as a library and reports that it compiled.

Predict the output

A predict cell asks you to type what you think the program will print before it lets you run it. Then it compares your prediction with the real output. Predicting is the fastest way to find out whether your mental model is right, so take the prediction seriously. Try this one: enumerate() pairs each item with its position, counting from 0, and len() is the number of items.

vec![...] builds a Vec, Rust's growable list (Python's list). The for loop and the tuple unpacking (i, channel) work much as they do in Python. The last line uses {} with an expression after the string, because format strings can only capture plain variable names, not method calls such as channels.len().

Compiler says no

A cell labelled "Compiler says no" is meant to fail. Its button reads Compile, and the point is the error message, which the text around the cell then explains. You will see many of these. In Python you learn what a program does by running it; in Rust you also learn by reading why the compiler refused to build it. The next section takes one of these errors apart in detail.

The error is E0384, "cannot assign twice to immutable variable". In Rust, a variable created with let cannot be changed. If you mean to change it, you say so with let mut count = 0;. The compiler even suggests that fix in its help: line. Edit the cell, add mut, and press Compile again.

Run locally

Some code cannot run on the Playground: code that uses Pixi's own crates, reads files from your disk, or is split over several files. Those cells say why, and tell you to run them on your own machine in a Cargo project (the next section shows how to make one).

The Playground also offers the most popular crates from crates.io, the public Rust package registry (think PyPI). Level 1 sticks to the standard library, std, so everything you write also works with nothing but a compiler.

Remember: Run to see, predict to check your model, "Compiler says no" to learn the rules, run-locally for real files and Pixi crates.

Installing Rust with Pixi

In Python you would install an interpreter, create an environment, and add packages to it. You already do that with Pixi. Rust works the same way: conda-forge publishes the Rust toolchain as a conda package named rust, so you add it to a Pixi workspace like any other dependency. The toolchain is the set of programs you need:

  • rustc, the compiler, which turns .rs source files into a program.
  • cargo, the build tool and package manager. It reads Cargo.toml, downloads crates, calls rustc for you, and runs tests. You will almost never call rustc directly.
  • clippy, a linter with several hundred checks, run as cargo clippy (think ruff's lint rules).
  • rustfmt, the formatter, run as cargo fmt (think ruff format).
pixi init hello-rust && cd hello-rust
pixi add rust                    # rustc, cargo, clippy and rustfmt from conda-forge
pixi run cargo init --name hello # creates Cargo.toml and src/main.rs in this directory
pixi run cargo run               # compiles, then runs: Hello, world!

Every Rust command goes through pixi run, the same way you run pixi run python or pixi run pytest. That keeps the toolchain version recorded in pixi.lock: everyone who clones your project gets the same compiler. This is also how Pixi itself is developed. Pixi's own pixi.toml has a rust feature and tasks such as pixi run build-debug (which runs cargo build --workspace --bin pixi) and pixi run test-fast.

Use a version range to pin the compiler, the same way this course does. In this repository's pixi.toml the line is rust = ">=1.95,<1.96", which matches the 1.95.0 that Pixi pins in its rust-toolchain file. You can do the same in your own workspaces: pixi add "rust>=1.95,<1.96".

Rust's own website suggests a tool called rustup. You do not need it for this course, and mixing two toolchain managers is a common source of "it works on my machine". Pixi already manages the toolchain per project.

Just enough Cargo to run things (M01 covers it properly):

CommandWhat it doesPython analogy

Reading a compiler error

Python reports most mistakes at run time, as a traceback, often far from where the mistake was made. Rust reports most mistakes at compile time, before the program runs, and the messages are unusually helpful. Reading them well is the single most useful skill in this course. Compile this cell.

The compiler prints this (the file name will differ on the Playground):

error[E0382]: borrow of moved value: `a`
 --> src/main.rs:4:16
  |
2 |     let a = String::from("conda-forge");
  |         - move occurs because `a` has type `String`, which does not implement the `Copy` trait
3 |     let b = a;
  |             - value moved here
4 |     println!("{a} and {b}");
  |                ^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let b = a.clone();
  |              ++++++++

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0382`.

Read it in this order:

  1. The headline and error code. error[E0382]: borrow of moved value: `a`. Every error has a code of the form E plus four digits. The code is stable across compiler versions, so it is what you search for, and each one has a long explanation with examples.
  2. The location. --> src/main.rs:4:16 is the file, line 4, column 16. Editors make this clickable.
  3. The primary span. The ^ marks under the code show the exact place the error happened: a inside the println!, labelled "value borrowed here after move".
  4. The secondary spans. The - marks show the related places, in line order, each with a label. Read them as the story of how you got here: line 2 says a is a String and is not Copy; line 3 says the value moved into b; line 4 is where you used a anyway.
  5. help: and note: lines. help: suggests a change, often as a small diff where + marks what to add. note: gives background. A suggestion is a way to make the code compile, not always the right design; here cloning works, but borrowing (M03) is often better.
  6. The footer. rustc --explain E0382 prints the long explanation for the code.
pixi run rustc --explain E0382    # the long explanation, with examples
pixi run rustc --explain E0308

The same explanations are online in the Rust error codes index.

Why did this fail at all? In Python, b = a makes two names for one object. In Rust, let b = a; moves the string into b, and a can no longer be used. That rule is how Rust knows exactly when to free memory without a garbage collector. Step through it with the ownership visualizer, which you will use often in M03: press the step buttons and watch the owner arrow move from a to b.

Here is one more error to read on your own. It is the most common one in Rust code written by Python developers.

How to read this error

The headline is error[E0308]: mismatched types. The primary span points at the return type String and says "expected String, found ()". The type (), pronounced "unit", means "no value", like a Python function that falls off the end and returns None. A secondary label on greeting says the function "implicitly returns () as its body has no tail or return expression", and the help: label on line 3 says "remove this semicolon to return this value".

In Rust, the last expression in a function body, written without a semicolon, is the return value. message; with a semicolon is a statement that throws the value away. Remove the semicolon and it compiles. You will fix exactly this in the first exercise.

When a build prints many errors, fix the first one and compile again. Later errors are often caused by the first. Run pixi run cargo check instead of cargo build while you fix errors; it skips producing a program and is much faster.

Remember: headline and code, location, primary span (^), secondary spans (-) in order, then help:/note:. When in doubt, rustc --explain the code.

Exercises, quizzes, and capstones

Exercises are graded by cargo test

Each module has three to six graded exercises. An exercise gives you starter code, usually with function bodies written as todo!(), a macro that compiles anywhere and panics (crashes with a message) if it runs. You replace each todo!() with real code and press Check.

Check sends your code to the Playground with a hidden test module appended, and runs cargo test. Each test is an ordinary Rust test function, marked #[test], like a pytest function. A test passes if it returns normally and fails if it panics. The tests use assert_eq!(actual, expected, "message"), Rust's version of assert actual == expected, "message", and the message is written for you. Here is the shape:

#[test]
fn greets_by_name() {
    assert_eq!(greeting("pixi"), "Hello, pixi!", "greeting(\"pixi\") should be \"Hello, pixi!\"");
}

Only return values and state are graded, not what you print. Each exercise also has a hint and a solution; try for a while before you open them. Some exercises start with code that does not compile, because the task is to fix it; the prompt always says so. Your progress is saved in your browser.

Quizzes

Each module ends with a quiz of 10 to 15 questions. There are four kinds: pick one answer, pick all correct answers, type the exact output of a program, and type a short answer such as an error code. Every question has an explanation; read it even when you are right. Many questions ask "does this compile?", which is the best test of whether you understand the rules.

Mini-projects

Each module has a mini-project that you build on your own machine, in a Cargo project inside a Pixi workspace you create yourself. Mini-projects are not graded; they come with acceptance criteria as a checklist you tick off. They are where you get used to the real loop of editing, cargo check, cargo test, cargo clippy, and cargo fmt.

Capstones

Each level ends with a capstone: a whole crate you build from a starter, graded by integration tests. Level 1 ends with Capstone 1: Manifest Reader, which reads a simplified pixi.toml into Rust types. Capstones live in this course's repository and run through its Pixi tasks:

git clone https://github.com/millsks/rust-practicum.git
cd rust-practicum
pixi install          # includes Rust 1.95 from conda-forge
pixi run projects     # list the capstones and whether you have started them
pixi run start c1     # copy the starter crate into work/
pixi run grade c1     # run the capstone's cargo tests against your crate in work/

The grading tests are copied next to your code only while grading runs, so your working copy in work/ never contains them and you cannot edit them by accident. Run pixi run grade c1 as often as you like; read the first failing test, fix it, and grade again.

Remember: exercises and capstones are graded by real cargo test runs; quizzes and flashcards check understanding; mini-projects build the local habit.

The frozen Pixi snapshot

Pixi changes every day. Files are renamed, functions move, and line numbers shift with every merged pull request. A course that linked to "the current" Pixi would have broken links and quotes that no longer match within weeks. So every reference to Pixi in this course points at one commit:

commit 451aa9596402530f1a4d8a50b5fe137570ad42a5   (pixi 0.81.0 development, 2026-09-18)

A permalink is a GitHub link that includes a commit hash, so it always shows the file exactly as it was at that commit. Every "Reading Pixi" link in this course has the form:

https://github.com/prefix-dev/pixi/blob/451aa9596402530f1a4d8a50b5fe137570ad42a5/<path>#L<start>-L<end>

Here are two small files from the snapshot that this course relies on. The first is Pixi's rust-toolchain file, which pins the compiler that Pixi builds with:

1.95.0

The second is the shared package settings in Pixi's top-level Cargo.toml, which every crate in the workspace inherits:

[workspace.package]
authors = ["pixi contributors <hi@prefix.dev>"]
edition = "2024"
rust-version = "1.90"
readme = "README.md"
homepage = "https://github.com/prefix-dev/pixi"
repository = "https://github.com/prefix-dev/pixi"
license = "BSD-3-Clause"

edition = "2024" is why this course teaches edition 2024. rust-version = "1.90" is the oldest compiler that may build Pixi, while rust-toolchain says which one Pixi's developers actually use (1.95). The course uses 1.95 everywhere. license = "BSD-3-Clause" is what allows the course to quote Pixi's code, with attribution.

When the course says "Pixi does X", it means "Pixi did X at commit 451aa959". The current Pixi may have changed since then. Why is that still the right thing to teach from? (Because the goal is to learn to read the code; the patterns change far more slowly than the details, and a frozen copy lets you check every claim yourself.)

If you want the snapshot on your own machine, so you can search it and open files in your editor:

git clone https://github.com/prefix-dev/pixi.git
cd pixi
git checkout 451aa9596402530f1a4d8a50b5fe137570ad42a5

In Level 1 you only read Pixi's code. In Level 3 you will build it and make a change on a copy of this same snapshot, so that the instructions keep working.

Remember: one commit, 451aa959, for every quote and link, so nothing drifts. Pixi uses Rust 1.95, edition 2024.

Python habits that change in Rust

Most of what you know transfers: functions, loops, modules, tests, and good naming. Some habits do not, and they cause most of the early frustration. Here is the map. You do not need to understand the right-hand column yet; come back to this table as you go.

In Python you...In Rust you...Where
Never write types, or write optional hints that nothing enforcesEvery value has one type, checked at compile time; local types are usually inferred, function signatures are always writtenM02
Reassign any variableVariables are immutable unless declared let mut; you can also shadow a name with a new letM02
Return with return, or get None by falling off the endThe last expression without a semicolon is the return valueThis module, M02
Write b = a to get two names for one objectlet b = a; moves the value; you borrow with &a or copy with .clone()M03
Rely on the garbage collectorEach value has one owner and is freed when the owner goes out of scopeM03
Use None for "missing" and check (or forget to)Use Option<T>; the compiler makes you handle the missing caseM04
Raise and catch exceptionsReturn Result<T, E> and pass errors up with ?M04
Use dicts as ad-hoc recordsDefine a struct with named, typed fieldsM02
Use strings or class hierarchies for "one of several kinds"Define an enum whose variants carry data, and match on itM02
Rely on duck typing and inheritanceUse traits and generics; there is no class inheritanceM06
Write list comprehensionsChain iterator adapters such as .map() and .filter(), then .collect()M05
pixi add a PyPI or conda packageAdd a crate to Cargo.toml with cargo addM01
Run pytest, ruff, and mypyRun cargo test, cargo clippy, cargo fmt; the type checker is the compilerM01, M11
Use indentation for blocksUse braces; indentation is for humans, and cargo fmt maintains itEverywhere

Two of these are visible right now. In this cell, total is mut because it changes, and double returns its last expression without a return keyword.

def double(n: int) -> int:
    return n * 2

total = 0
for n in [1, 2, 3]:
    total += double(n)
print(f"total = {total}")
fn double(n: i32) -> i32 {
    n * 2
}

fn main() {
    let mut total = 0;
    for n in [1, 2, 3] {
        total += double(n);
    }
    println!("total = {total}");
}

Delete mut from the cell above and compile it. Which error code do you get, and what does its help: line suggest?

Remember: immutable by default, last expression is the return value, values move, missing values and errors are types. Everything else you know about writing clear code still applies.

Practice

Three short exercises to try the Check button. The first and third start with code that does not compile, on purpose: the first Check shows the compiler error, which is your clue.

This starter does not compile. Press Check first and read the E0308 error. Then fix greeting so that greeting("pixi") returns "Hello, pixi!". Change one character.

Hint

Read the help: label in the error. The last expression of a function body is its return value only if it has no semicolon.

Show solution 
fn greeting(name: &str) -> String {
    let message = format!("Hello, {name}!");
    message
}

Removing the semicolon turns message; (a statement, value discarded) into message (the tail expression, which is returned). You could also write format!("Hello, {name}!") as the whole body.

Write run_command(task: &str) -> String that returns the command a person would type to run a Pixi task. For example, run_command("test") returns "pixi run test".

Hint

format! works like println! but returns the String instead of printing it: format!("pixi run {task}").

Show solution 
fn run_command(task: &str) -> String {
    format!("pixi run {task}")
}

This starter does not compile. countdown(n) should return the numbers from n down to 1, so countdown(3) is [3, 2, 1]. Press Check, read the errors (there are two, with codes E0596 and E0384), and fix them by changing only the let lines.

Hint

Both out (you push to it) and i (you subtract from it) change after they are created. Each needs let mut.

Show solution 
fn countdown(n: u32) -> Vec<u32> {
    let mut out = Vec::new();
    let mut i = n;
    while i > 0 {
        out.push(i);
        i -= 1;
    }
    out
}

E0596 ("cannot borrow out as mutable") is about push, which needs to change the vector. E0384 is the reassignment of i. Rust wants every change declared up front, so a reader can see at the let which values will change.

Mini-project: your first Cargo project with Pixi

Mini-projecthello-rust: install Rust with Pixi and run the whole toolchain

Set up the local workflow you will use for every mini-project in the course: a Pixi workspace that owns the Rust toolchain, with a Cargo project inside it.

pixi init hello-rust && cd hello-rust
pixi add rust
pixi run cargo init --name hello
pixi run cargo run

What to do

  1. Run the commands above. cargo init creates Cargo.toml and src/main.rs; cargo run prints Hello, world!. Look at pixi.toml and find the rust dependency that pixi add wrote.
  2. Run pixi run rustc --version and pixi run cargo --version and note the versions.
  3. Edit src/main.rs so it prints a greeting that uses a variable inside the format string, and a second line built with a function that returns a String (reuse greeting from exercise 1).
  4. Break it on purpose: add a semicolon after the function's last expression, run pixi run cargo check, and read the error using the anatomy from this module. Then run pixi run rustc --explain E0308. Fix it.
  5. Run the linter: pixi run cargo clippy --all-targets -- -D warnings. The -D warnings part turns every warning into an error, which is how Pixi's own checks run. To see a warning, add let unused = 5; inside main and run it again.
  6. Mess up the indentation of main.rs, then run pixi run cargo fmt and look at the file again.
  • pixi.toml lists rust as a dependency, and pixi.lock pins its version
  • pixi run cargo run prints your two lines
  • You read an E0308 error and could point at its primary span and its help: line
  • pixi run cargo clippy --all-targets -- -D warnings finishes with no warnings
  • pixi run cargo fmt leaves the file formatted (running it a second time changes nothing)
  • No Rust tool was installed outside Pixi

Stretch goals: add Pixi tasks so that pixi run start runs cargo run and pixi run lint runs clippy and cargo fmt --check (look at how Pixi's own pixi.toml defines build-debug for the shape); run pixi run cargo build --release and compare the size and speed of target/release/hello with target/debug/hello; clone the Pixi snapshot and open crates/pixi/src/main.rs, the start of the whole pixi program.
