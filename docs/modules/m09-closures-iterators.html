Closures & Iterator Chains

Open almost any function in Pixi and you will find a closure passed to map, a chain of six iterator adapters ending in collect, or a helper that takes impl Fn. This module explains what a closure captures and why that decides which of the three closure traits it implements, how to write your own iterator, and how to read the long chains that fill the codebase without losing track of the types.

Closures: functions that remember

In Python you write small throwaway functions with lambda, and functions defined inside other functions can read the outer function's variables:

threshold = 10
big = [n for n in sizes if n > threshold]          # or:
big = list(filter(lambda n: n > threshold, sizes))

The lambda "remembers" threshold even though it is not a parameter. A function value plus the variables it remembers is called a closure, and Rust has the same idea with a shorter syntax: parameters go between vertical bars, and the body follows.

let threshold = 10;
let is_big = |n: u64| n > threshold;     // one expression: no braces needed
let describe = |name: &str, size: u64| {   // a block body for several statements
    let unit = if size > 1024 { "KiB" } else { "B" };
    format!("{name}: {size} {unit}")
};
let always = || 42;                          // no parameters: empty bars

Unlike a fn item, a closure's parameter and return types can usually be left out. The compiler infers them from how the closure is used, just as it infers the type of a let. That is why you can write .map(|p| p.name()) without naming the type of p.

Every closure has its own type

Inference happens once. The first time you call a closure without annotations, its parameter types are fixed. Calling it later with a different type is an error, not a second "overload":

The compiler reports E0308 (mismatched types): "expected String, found integer", with a note pointing at the first call, where the parameter type was decided. Python's lambda x: x accepts anything because Python checks types at run time; Rust decides every type at compile time, so a closure gets exactly one signature.

More surprising: the compiler creates a brand-new, anonymous struct type for every closure you write. The struct's fields are the captured variables, and calling the closure calls a method on that struct. Two closures with identical code still have two different types. You cannot write the name of a closure's type, which is why functions that take or return closures use generics, impl Fn, or dyn Fn, all covered below.

Anywhere a closure is expected, you can pass a named function or method instead: names.iter().map(String::len), lines.map(str::trim), results.into_iter().map(Some). Pixi does this constantly (.map(Into::into) appears all over the manifest crate). It reads well when the function already exists and you would only be forwarding the argument.

Remember: |args| body makes a closure. Its types are inferred once from its first use, and each closure is its own anonymous type that holds whatever it captured.

How closures capture

A Python closure keeps a reference to the outer variable, and nothing stops you from mutating that variable anywhere. Rust has to fit closures into the ownership rules from M03, so each captured variable is captured in one of three ways, and the compiler picks the weakest one that makes the body work:

The body...Capture modeLike holding
only reads the variableshared borrow&T
modifies the variablemutable borrow&mut T
moves the variable out (returns it, drops it, passes it by value)by valueT

Because a capture is a borrow, all the borrowing rules apply for as long as the closure is alive. A closure that mutably borrows a counter is a live &mut; you cannot read the counter until the closure's last use:

The first label points at the closure (the mutable borrow happens where the closure is created, not where it is called), the second at the println!, and the third at install(), the later use that keeps the borrow alive. Precise captures

Since edition 2021, a closure captures the exact place it uses, not the whole variable. If the body only touches manifest.name, only that field is borrowed, and you can still mutate manifest.version while the closure is alive. This removed a whole class of borrow errors that older Rust code worked around with temporary variables; you will still see those workarounds in older crates.

A closure reads config.channels and pushes onto log. Which capture mode does it use for each? Can you call config.channels.len() between creating and calling it? Can you call log.len()?

Remember: a capture is a borrow (or a move) that lasts as long as the closure is used. Mutating captures makes a live &mut and requires let mut on the closure.

Fn, FnMut, and FnOnce

Because every closure has its own type, a function that accepts "any closure" needs a trait to describe what it will do with it. Rust has three, nested like Russian dolls:

TraitCan be calledWhat the body may do with capturesCalled via
FnOnceat least onceanything, including moving them outself
FnMutmany times, not at the same timeread and modify&mut self
Fnmany times, even concurrentlyonly read&self

Every Fn closure is also FnMut, and every FnMut closure is also FnOnce. So the bound you choose as a caller of closures is a promise about how you will call them:

  • FnOnce is the most permissive bound: "I will call it once." Any closure qualifies. Use it for callbacks run exactly once, like Option::map, unwrap_or_else, or thread::spawn.
  • FnMut: "I may call it many times, one after another." Iterator adapters like map and filter take FnMut, so your closure can count or collect as it goes.
  • Fn is the most restrictive bound: "I may call it many times, possibly from several places at once." Use it when you store a callback and share it.

The trait a closure implements depends on what its body does with the captures, not on how it captures them. A closure that returns a captured String by value can be called only once, because after the first call the string is gone:

The error is E0382, "use of moved value: take_name", and the note explains why: "closure cannot be invoked more than once because it moves the variable name out of its environment". Calling an FnOnce closure consumes the closure itself, just as passing a String by value consumes the string.

The opposite mistake is passing a closure that mutates where the bound only allows reading:

E0594: "cannot assign to calls, as it is a captured variable in a Fn closure", with a label on the F: Fn() bound that forced it. The fix belongs to whoever owns the signature: if run_twice calls f sequentially, it should ask for FnMut and take mut f: F. Choosing the loosest bound that your code actually needs makes your function accept the most closures.

Pixi's spinner helper takes FnOnce because it runs the work exactly once (crates/pixi_progress/src/lib.rs):

pub fn wrap_in_progress<T, F: FnOnce() -> T>(msg: impl Into<Cow<'static, str>>, func: F) -> T {
    let pb = global_multi_progress().add(ProgressBar::new_spinner());
    // ...
    let result = func();
    pb.finish_and_clear();
    result
}

Because the bound is FnOnce, callers may pass a closure that moves a value into the work and consumes it, which Fn would forbid. The generic T lets the closure return anything, and the helper hands it straight back.

Remember: FnOnce ⊃ FnMut ⊃ Fn in what they accept. Ask for FnOnce if you call once, FnMut if you call repeatedly, Fn only if you must share or call through &.

move closures

Writing move before the bars forces every capture to be by value: the closure takes ownership of what it uses. This is about how it captures, which is a separate question from which Fn trait it implements. A move closure that only reads its owned data is still Fn.

You need move whenever the closure may outlive the scope that created it: a closure sent to another thread, returned from a function, or stored in a struct. A borrow of a local would dangle once the function returns, and the compiler refuses:

E0373: "closure may outlive the current function, but it borrows channel, which is owned by the current function". The help: line gives the fix verbatim: "to force the closure to take ownership of channel ..., use the move keyword". thread::spawn requires 'static (M07), because the new thread can run longer than main's stack frame.

A common pattern: clone first, then move the clone, so the original stays usable. This is exactly how Pixi hands an Arc to a spawned task (M08):

This is a classic source of "my counter never changes" bugs: if you want the caller to see the updates, drop the move so the closure borrows the variable instead.

Remember: move changes capture to by-value. Use it when the closure outlives the current scope (threads, returned closures, stored callbacks). Clone what you still need before the move.

Passing and returning closures

Since you cannot name a closure's type, there are four ways to accept one. They mirror the generics versus trait objects choice from M06:

// 1. Generic parameter with a bound: one compiled copy per closure type (static dispatch).
fn apply<F: Fn(u32) -> u32>(f: F, x: u32) -> u32 { f(x) }

// 2. impl Trait in argument position: the same thing, shorter to write.
fn apply2(f: impl Fn(u32) -> u32, x: u32) -> u32 { f(x) }

// 3. A trait object behind a reference: one compiled copy, a vtable call at run time.
fn apply3(f: &dyn Fn(u32) -> u32, x: u32) -> u32 { f(x) }

// 4. A where clause, for longer bounds.
fn apply4<F>(f: F, x: u32) -> u32
where
    F: Fn(u32) -> u32 + Send + 'static,
{ f(x) }

The Fn(u32) -> u32 syntax is special sugar for the closure traits: the arguments go in parentheses and the return type after the arrow. Options 1 and 2 are the default choice: the compiler generates specialized code for each closure, so a call costs nothing extra and can be inlined. Option 3 is useful when you want to avoid that code duplication or store many different closures together.

Returning closures

To return a single closure type, use impl Fn in return position. To return one of several closures, or to store closures of different types in a collection, box them as Box<dyn Fn>. The compiler shows you why with one of its best-known errors:

E0308 again, this time worded "if and else have incompatible types", with an unusually helpful note: "no two closures, even if identical, have the same type", and help: lines that rewrite the return type to Box<dyn Fn(&str) -> bool> and wrap each branch in Box::new. impl Fn means "one specific type that I am not naming", so both branches must produce that same type. Box<dyn Fn> erases the type: the closure moves to the heap, and the box holds a pointer plus a vtable.

One exception you may notice: a closure that captures nothing can be converted to a plain function pointer type, fn(&str) -> bool. If both branches above captured nothing, the compiler would quietly convert both to that one pointer type and the code would compile. As soon as a closure captures something (here max_len), it carries data, and that escape hatch closes.

Three things to notice. The type alias Rule keeps signatures readable. The second closure needs move because it outlives make_rules, which owns max_len. And bool::then takes a closure that runs only when the bool is true, which turns "if this, make an error message" into one expression.

A function like fn make(prefix: &str) -> impl Fn(&str) -> String is assumed, in edition 2024, to return something that may borrow from prefix, even if your closure owns a copy. Callers then get E0505 or E0597 when they drop the argument, plus a note that "Rust 2024 has adjusted the impl Trait lifetime capture rules". Write -> impl Fn(&str) -> String + use<> to promise that the result captures no lifetimes. You will do this in exercise 2.

Pixi uses impl Fn parameters to make code testable. The cache directory resolver does not read environment variables itself; it takes a lookup function (cache_dirs.rs), so production code passes the real environment and tests pass a closure over a map. You will read this function in full in Reading Pixi.

Remember: accept closures with impl Fn(..) or a generic bound by default. Return one with impl Fn. Use Box<dyn Fn> when the concrete closure varies at run time or you store several in one collection.

Writing your own iterator

In Python you make an object iterable by writing __iter__ and __next__, or more often a generator with yield. In Rust you implement one trait with one required method:

pub trait Iterator {
    type Item;                                  // the associated type from M06
    fn next(&mut self) -> Option<Self::Item>;  // Some(item), or None when finished
    // ...about 75 provided methods: map, filter, sum, collect, ...
}

Implement next and you get every adapter and consumer from M05 for free, because they are default methods built on top of next. The iterator keeps its progress in its own fields, which is why next takes &mut self. There are no generators in stable Rust (the gen keyword is reserved in edition 2024 for that future), so the state that a Python generator keeps in local variables lives in the struct instead.

def ancestors(parents, start):
    current = parents[start]
    while current is not None:
        yield current
        current = parents[current]
struct Ancestors<'a> {
    parents: &'a [Option<usize>],
    next: Option<usize>,
}

impl Iterator for Ancestors<'_> {
    type Item = usize;
    fn next(&mut self) -> Option<usize> {
        let current = self.next?;
        self.next = self.parents[current];
        Some(current)
    }
}

The ? on an Option (M04) does the work of the while condition: when self.next is None, next returns None and the iteration is over. Run it and see the free adapters at work:

Iterators without a struct

For one-off iterators, the standard library builds the struct for you from a closure:

  • std::iter::successors(first, |prev| next): each item is computed from the previous one; stops at the first None. The ancestor walk is successors(parents[3], |&i| parents[i]).
  • std::iter::from_fn(move || ...): any closure returning Option<T>; the closure is FnMut and keeps its state in its captures.
  • std::iter::once(x) and std::iter::repeat(x): one item, or the same item forever (pair it with take).

When your type is a collection, also implement IntoIterator for &YourType so that for x in &thing works, and give it an iter() method returning impl Iterator<Item = &T> + '_. Returning impl Iterator hides the concrete adapter type (which can be enormous) and lets you change the implementation later without breaking callers.

Remember: implement next(&mut self) -> Option<Item>, store the progress in fields, and every adapter comes free. Reach for successors or from_fn for quick one-off iterators.

Laziness: nothing happens until you consume

Python generators are lazy, and so are Rust iterators: calling map or filter builds a new iterator struct that wraps the old one, and does no work at all. Work happens only when a consumer (collect, sum, for, count, find, ...) starts calling next. Each item then travels through the whole chain before the next item starts. The output alternates map and filter for each item; there is no stage where all three items are mapped first. That is why chains are cheap: no intermediate Vec is built between adapters, and the compiler usually fuses the whole chain into one loop as fast as a hand-written one.

Laziness has two consequences you will meet in review:

  • A chain without a consumer does nothing. The compiler warns: "unused Map that must be used ... iterators are lazy and do nothing unless consumed". If you wanted side effects, use a for loop (or for_each), not map.
  • Short-circuiting consumers stop early. any, all, find, position, and collecting into Result or Option stop pulling items as soon as the answer is known. Expensive work later in the input never runs.

Do not put side effects you rely on (pushing to a list, logging that must happen, incrementing counters) inside map and then consume with a short-circuiting method. Some items may never reach your closure. Keep map closures pure and use a for loop when the side effect is the point.

Remember: adapters build a pipeline; consumers run it. Each item flows through every stage before the next item starts, and short-circuiting consumers stop early.

peekable for parsing

A Peekable wraps an iterator and buffers one item so you can look before you take. This is how you write small tokenizers, and Pixi uses it in exactly that way, for example in its shell-script parser (input.char_indices().peekable() in pixi_script_shell/src/parse.rs).

windows shows up in Pixi wherever bytes are scanned for a marker. To decide whether a script uses Windows line endings, Pixi looks for any two-byte window equal to \r\n (pixi_manifest/src/script/block.rs):

pub(crate) fn detect(contents: &[u8]) -> Self {
    if contents.windows(2).any(|window| window == b"\r\n") {
        Self::CrLf
    } else {
        Self::Lf
    }
}

b"\r\n" is a byte-string literal of type &[u8; 2], and any stops at the first match.

Remember: windows overlaps, chunks does not, chunk_by groups neighbours. peekable plus next_if is the standard way to tokenize.

itertools: Pixi's favourite extension

The itertools crate adds dozens of methods to every iterator. Pixi pins it once in the workspace (itertools = "0.15.0" in the root Cargo.toml) and imports it in a large share of its files. It works through the extension-trait pattern from M06: the crate defines a trait Itertools with default methods and implements it for every Iterator. The methods are only callable once the trait is in scope, which is why you see this line at the top of so many Pixi files:

use itertools::Itertools;

Reading long chains

A twelve-line chain looks intimidating until you read it the way the compiler does: one step at a time, tracking the item type. Write the type next to each line, on paper or in your head. Your editor's inlay hints (rust-analyzer) do exactly this, and turning them on is the single best aid for reading Pixi.

Here is a real one, from the conversion of Pixi's PyPI options into the lock-file type (pixi_manifest/src/pypi/pypi_options.rs). The fields are index_url: Option<Url>, extra_index_urls: Option<Vec<Url>>, and find_links: Option<Vec<FindLinksUrlOrPath>>:

#[cfg(feature = "rattler_lock")]
impl From<PypiOptions> for rattler_lock::PypiIndexes {
    fn from(value: PypiOptions) -> Self {
        let primary_index = value
            .index_url
            .unwrap_or(pixi_consts::consts::DEFAULT_PYPI_INDEX_URL.clone());
        Self {
            indexes: std::iter::once(primary_index)
                .chain(value.extra_index_urls.into_iter().flatten())
                .collect(),
            find_links: value
                .find_links
                .into_iter()
                .flatten()
                .map(Into::into)
                .collect(),
        }
    }
}

Annotated, the indexes chain reads:

std::iter::once(primary_index)        // Iterator<Item = Url>, exactly one item
    .chain(                           // then, after it:
        value.extra_index_urls        //   Option<Vec<Url>>
            .into_iter()              //   Iterator over 0 or 1 Vec<Url>
            .flatten())               //   Iterator<Item = Url>: the Vec's items, or nothing
    .collect()                        // into the field's type, Vec<Url>

Two idioms to recognize. option.into_iter().flatten() turns "maybe a list" into "the list's items, or none", without a match. And .collect() with no turbofish works because the target type is already known from the struct field. When you write chains, the same trick helps: annotate the let (let v: Vec<String> = ...) instead of guessing, and if a chain gets hard to read, split it into named let bindings. Laziness means splitting costs nothing.

A habit from Pixi review: when a chain ends in for_each with a big closure, or uses map only for side effects, reviewers ask for a for loop. Chains are for transforming data; loops are for doing things. Clippy enforces part of this (clippy::needless_collect, clippy::map_unwrap_or, clippy::unnecessary_fold).

Remember: read a chain top to bottom, writing down the item type after each step. once(x).chain(opt.into_iter().flatten()) and .map(Into::into) are everywhere in Pixi.

Reading Pixi

Excerpt 1: a hand-written iterator over operation parents

Pixi's compute engine tracks which operation started which, so progress reporting can show nested work. Each operation id records its parent, and walking up to the root is a custom iterator (crates/pixi_compute_reporters/src/operation_id.rs, lines 65-95). parents is a DashMap<OperationId, Option<OperationId>>, a concurrent hash map that can be read and written from many threads through &self.

    /// Direct parent of `id`, or `None` for a root operation or an
    /// unknown id.
    pub fn parent_of(&self, id: OperationId) -> Option<OperationId> {
        self.parents.get(&id).and_then(|v| *v)
    }

    /// Iterator over `id`'s ancestors, from immediate parent up to the
    /// root.
    pub fn ancestors(&self, id: OperationId) -> Ancestors<'_> {
        Ancestors {
            registry: self,
            next: self.parent_of(id),
        }
    }
}

/// Iterator returned by [`OperationRegistry::ancestors`].
pub struct Ancestors<'r> {
    registry: &'r OperationRegistry,
    next: Option<OperationId>,
}

impl Iterator for Ancestors<'_> {
    type Item = OperationId;

    fn next(&mut self) -> Option<Self::Item> {
        let cur = self.next?;
        self.next = self.registry.parent_of(cur);
        Some(cur)
    }
}
  • parent_of: get returns Option<Ref<..>> (a guard to the value, if the key exists). and_then(|v| *v) flattens "maybe a stored value, which is itself maybe a parent" into one Option. *v copies the inner Option<OperationId> out, which works because OperationId is Copy.
  • ancestors returns Ancestors<'_>: the iterator borrows the registry (M07), so it cannot outlive it. The first item is computed eagerly here, so next has the "what to yield now" value ready.
  • struct Ancestors<'r> holds exactly the state the walk needs: where to look, and what comes next. Its fields are private; callers only see that it is an Iterator.
  • next is the same three lines you wrote earlier: ? ends the iteration, the parent becomes the new state, and the current id is yielded. Callers get .collect(), .any(..), .count() and everything else for free.

Excerpt 2: a closure as a seam for testing

From crates/pixi_compute_cache_dirs/src/cache_dirs.rs, lines 99-124 (doc comments trimmed):

    pub fn resolve<L: CacheLocation>(
        &self,
        env_get: impl Fn(&str) -> Option<String>,
    ) -> AbsPresumedDirPathBuf {
        if let Some(p) = self.override_for::<L>() {
            return p.clone();
        }
        if let Some(name) = L::env_override()
            && let Some(raw) = env_get(name)
            && let Ok(p) = AbsPathBuf::new(raw)
        {
            return p.into_assume_dir();
        }
        self.anchor(L::base()).join(L::name()).into_assume_dir()
    }

    // ...
    pub fn resolve_with_env<L: CacheLocation>(
        &self,
        env: &HashMap<String, String>,
    ) -> AbsPresumedDirPathBuf {
        self.resolve::<L>(|n| env.get(n).cloned())
    }
  • env_get: impl Fn(&str) -> Option<String>: any closure or function that maps a variable name to a value. resolve does not know or care whether that is the process environment, a snapshot, or a test's fixed map.
  • The if let ... && let ... chain is an edition 2024 let chain: three fallible steps (the location has an env var name, the variable is set, its value is an absolute path) and the block runs only if all three succeed.
  • resolve_with_env adapts a HashMap to that interface with a one-line closure. |n| env.get(n).cloned() captures env by shared reference and only reads it, so it implements Fn, which is what the bound requires. .cloned() turns Option<&String> into Option<String>.
  • self.resolve::<L>(..) uses the turbofish because L appears only in the return path, not in any argument, so the compiler cannot infer it.
Question 1: why does parent_of use and_then and not map?

self.parents.get(&id) is an Option of a stored Option<OperationId>. map(|v| *v) would produce Option<Option<OperationId>>; and_then expects the closure to return an Option and flattens the two layers. "Unknown id" and "root operation" both become None, which is what the doc comment promises.

Question 2: could resolve take env_get: impl FnMut(&str) -> Option<String> instead? Would callers notice?

Yes. It calls env_get at most once, so even FnOnce would compile (it would then need no mut). A looser bound accepts strictly more closures, so no existing caller would break. Pixi's authors chose Fn, which documents that the lookup is a pure read; both choices are defensible, and this is the kind of question that comes up in review.

Question 3: write the ancestors walk with std::iter::successors. What would you lose?

std::iter::successors(self.parent_of(id), move |&cur| self.parent_of(cur)) returns impl Iterator<Item = OperationId> + '_ and behaves the same. You lose a nameable type: Ancestors can be stored in a struct field, mentioned in other signatures, and documented, while a successors closure type cannot be written down.

Practice

Each exercise is checked by cargo test. All of them use only the standard library.

Write apply_n(f, n, start) that applies f to start, then to the result, n times in total, and returns the final value. apply_n(|x| x * 2, 3, 1) is 8. With n == 0 it returns start. The third test mutates calls, so the closure is only FnMut. Change the bound to impl FnMut(i64) -> i64; to call an FnMut parameter you must declare it mut f. A for _ in 0..n loop is simplest.

fn apply_n(mut f: impl FnMut(i64) -> i64, n: usize, start: i64) -> i64 {
    let mut value = start;
    for _ in 0..n {
        value = f(value);
    }
    value
}

Write make_counter(start: u32, step: u32) that returns a closure. Each call returns the next value: first start, then start + step, and so on. Two counters must be independent. Also write make_labeler(prefix: &str) that returns a closure turning "numpy" into "<prefix>numpy"; the closure must not borrow the argument (tests drop the original string before calling it).

The starter's return type ends in + use<>. In edition 2024 an impl Trait return type is assumed to capture every lifetime in scope, including the one on prefix: &str, so the caller would have to keep the argument alive. use<> (precise capturing) says "this closure borrows nothing from the arguments", and the compiler will hold your body to that promise.

Hint

Both closures outlive the function, so both need move. For the counter, keep a let mut current = start; before the closure, return the current value and advance it. For the labeler, turn the &str into an owned String before the closure and move that in.

Show solution 
fn make_counter(start: u32, step: u32) -> impl FnMut() -> u32 {
    let mut current = start;
    move || {
        let value = current;
        current += step;
        value
    }
}

fn make_labeler(prefix: &str) -> impl Fn(&str) -> String + use<> {
    let prefix = prefix.to_string();
    move |name: &str| format!("{prefix}{name}")
}

Implement Iterator for MinorVersions, which yields (major, minor) pairs from start up to and including end, increasing the minor number. When the minor number reaches per_major, roll over to the next major at minor 0. For example, from (1, 8) to (2, 1) with per_major = 10 yields (1, 8), (1, 9), (2, 0), (2, 1). If start is after end, yield nothing. Then write count_between using your iterator.

Hint

In next: let current = self.next?;, return None if current > self.end (tuples compare element by element). Compute the following version, and set self.next to it, or to None once current == self.end. count_between is MinorVersions::new(start, end, 10).count().

Show solution 
struct MinorVersions {
    next: Option<(u32, u32)>,
    end: (u32, u32),
    per_major: u32,
}

impl MinorVersions {
    fn new(start: (u32, u32), end: (u32, u32), per_major: u32) -> Self {
        MinorVersions { next: Some(start), end, per_major }
    }
}

impl Iterator for MinorVersions {
    type Item = (u32, u32);

    fn next(&mut self) -> Option<(u32, u32)> {
        let current = self.next?;
        if current > self.end {
            self.next = None;
            return None;
        }
        let (major, minor) = current;
        let following = if minor + 1 >= self.per_major { (major + 1, 0) } else { (major, minor + 1) };
        self.next = if current == self.end { None } else { Some(following) };
        Some(current)
    }
}

fn count_between(start: (u32, u32), end: (u32, u32)) -> usize {
    MinorVersions::new(start, end, 10).count()
}

A Pipeline holds a list of string transformations and applies them in order. Implement new, then (which adds a step and returns the pipeline, so calls can be chained), and run. Each step is a Box<dyn Fn(String) -> String>, so different closures can live in the same Vec. Then write normalizer(prefix) that builds a pipeline which trims whitespace, lowercases, and replaces _ with -, and finally adds prefix in front.

Hint

then pushes Box::new(step); the 'static bound is what lets a generic closure become a Box<dyn Fn> (which is 'static by default). run can be a fold: self.steps.iter().fold(input.to_string(), |acc, step| step(acc)). In normalizer, own the prefix and use a move closure for the last step.

Show solution 
struct Pipeline {
    steps: Vec<Box<dyn Fn(String) -> String>>,
}

impl Pipeline {
    fn new() -> Self {
        Pipeline { steps: Vec::new() }
    }

    fn then(mut self, step: impl Fn(String) -> String + 'static) -> Self {
        self.steps.push(Box::new(step));
        self
    }

    fn run(&self, input: &str) -> String {
        self.steps.iter().fold(input.to_string(), |acc, step| step(acc))
    }
}

fn normalizer(prefix: &str) -> Pipeline {
    let prefix = prefix.to_string();
    Pipeline::new()
        .then(|s| s.trim().to_string())
        .then(|s| s.to_lowercase())
        .then(|s| s.replace('_', "-"))
        .then(move |s| format!("{prefix}{s}"))
}

Lock-file lines look like "conda-forge::numpy==1.26.4" (channel, ::, name, ==, version). Write report(lines) returning one line per channel, channels in alphabetical order, formatted "channel: name1, name2" with package names unique and sorted. Skip blank lines and lines starting with #; ignore lines that do not contain both separators. Return the lines joined with "\n" (no trailing newline). This is the kind of grouping Pixi does with itertools; here use a BTreeMap<&str, BTreeSet<&str>>.

Hint

Parse each line with filter_map: trim it, skip comments, then let (channel, rest) = line.split_once("::")?; and let (name, _version) = rest.split_once("==")?; inside a closure that returns Option<(&str, &str)>. Fold the pairs into the map with entry(channel).or_default().insert(name), then map each entry to a formatted line and join.

Show solution 
use std::collections::{BTreeMap, BTreeSet};

fn report(lines: &[&str]) -> String {
    let mut by_channel: BTreeMap<&str, BTreeSet<&str>> = BTreeMap::new();
    let records = lines.iter().filter_map(|line| {
        let line = line.trim();
        if line.is_empty() || line.starts_with('#') {
            return None;
        }
        let (channel, rest) = line.split_once("::")?;
        let (name, _version) = rest.split_once("==")?;
        Some((channel, name))
    });
    for (channel, name) in records {
        by_channel.entry(channel).or_default().insert(name);
    }
    by_channel
        .iter()
        .map(|(channel, names)| {
            let names: Vec<&str> = names.iter().copied().collect();
            format!("{channel}: {}", names.join(", "))
        })
        .collect::<Vec<_>>()
        .join("\n")
}

What to build

  • A Record { channel, name, version } struct and a parse_line(&str) -> Option<Record> for lines like conda-forge::numpy==2.3.1.
  • A custom iterator Records that wraps std::str::Lines and yields only the lines that parse, skipping comments and blanks. Implement Iterator yourself rather than using filter_map, for practice.

  • Every filter is a move closure in a Box<dyn Fn>; no filter borrows from main's locals
  • With no flags, every record is reported
  • The output order is identical across runs (no HashMap iteration in the output)
  • At least three #[test] functions cover parsing and one filter each
  • pixi run cargo clippy --all-targets -- -D warnings passes

Stretch goals: rewrite the grouping with itertools (sorted_by_key, chunk_by, format_with) and compare readability; add --exclude that wraps another filter in a negating closure (move |r| !inner(r)); make Records generic over any Iterator<Item = S> where S: AsRef<str>.

Quiz

Recap

  • A closure is |args| body. Its types are inferred once, and each closure has its own anonymous type holding its captures.
  • Captures use the weakest mode that works: &T to read, &mut T to modify, by value to move out. The borrow lasts as long as the closure is used.
  • Fn (read, call many times), FnMut (modify, call sequentially), FnOnce (may consume, call once). Ask for the loosest bound your code needs.
  • move makes every capture by value; needed when a closure outlives its scope. Clone what you still need first.
  • Take closures with impl Fn(..) or generics; return with impl Fn; use Box<dyn Fn> when closures vary at run time.
  • Implement Iterator::next and every adapter is free. Iterators are lazy; consumers drive them one item at a time.
  • Pixi leans on itertools (sorted, unique, join, format_with) for deterministic, readable output. Read chains by tracking the item type.
