Testing Like Pixi Does

At the snapshot, Pixi's crates contain about 2,300 #[test] functions, about 660 #[tokio::test] functions, and around 390 snapshot files. No pull request lands without tests, and most reviews start by reading them. This module teaches Rust's built-in test tools from the pytest you already know, then the three things Pixi adds on top: snapshot testing with insta, shared fixtures, and cargo nextest.

#[test] and the assert macros

With pytest, a test is a function whose name starts with test_, and a failing assert fails it. Rust's built-in harness works the same way with one difference: a test is any function marked with the #[test] attribute (its name does not matter), and a test fails when it panics.

# test_spec.py
from spec import split_spec

def test_splits_name_and_constraint():
    assert split_spec("numpy >=1.26") == ("numpy", ">=1.26")

def test_no_constraint():
    name, constraint = split_spec("python")
    assert constraint == "*", "a bare name means any version"
// src/spec.rs
pub fn split_spec(spec: &str) -> (&str, &str) {
    spec.split_once(' ').unwrap_or((spec, "*"))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn splits_name_and_constraint() {
        assert_eq!(split_spec("numpy >=1.26"), ("numpy", ">=1.26"));
    }

    #[test]
    fn no_constraint() {
        let (_, constraint) = split_spec("python");
        assert_eq!(constraint, "*", "a bare name means any version");
    }
}

Three macros cover most assertions:

  • assert!(cond) panics if cond is false.
  • assert_eq!(left, right) panics if they differ, and prints both values with Debug. So both types must implement PartialEq with each other and Debug.
  • assert_ne!(left, right) is the opposite.

Every one of them accepts an optional message after the values, written like format!: assert!(name.starts_with(".pixi"), "expected prefix `.pixi`, got `{name}`"). Unlike pytest, Rust does not rewrite your expression to show intermediate values, so a good message is the difference between a failure you understand from the CI log and one you have to reproduce locally. The panic message on stderr shows assertion `left == right` failed: normalizing "Scikit_Learn", then left: "scikit_learn" and right: "scikit-learn". By convention put the actual value on the left and the expected value on the right, so "left" always means "what the code did".

Notice that normalize returns a String and it is compared with a &str literal. That works because String: PartialEq<&str>. What does not work is comparing a type that has no Debug:

E0277: "Spec doesn't implement Debug", pointing into the macro, with a help: to add #[derive(Debug)]. This is one reason nearly every type in Pixi derives Debug: tests need to print it.

pixi run cargo test builds a test binary per crate target and runs every #[test] in parallel threads. Useful variations: cargo test spec (only tests whose path contains "spec"), cargo test -- --nocapture (show println! output from passing tests, which is captured by default), cargo test --lib (unit tests only), cargo test -- --test-threads=1 (run serially, for tests that share global state such as environment variables).

Remember: #[test] marks a test; a panic fails it. assert_eq!(actual, expected, "message {context}"), and derive Debug on what you compare.

Testing failures: should_panic, Result, and ignore

pytest has with pytest.raises(ValueError, match="..."):. Rust has two tools, depending on whether the failure is a panic or an Err.

Panics: #[should_panic]

#[test]
#[should_panic(expected = "at most 100")]
fn rejects_large_percentages() {
    Percentage::new(150);
}

The test passes only if the body panics and the panic message contains the expected text. Always give expected: without it, any panic passes the test, including an unrelated unwrap on None three lines earlier.

Errors: assert on the Result, or return one

Most failures in Pixi are Results, not panics, so most failure tests look like this:

#[test]
fn rejects_empty_name() {
    let err = PackageName::new("").unwrap_err();     // panics (fails the test) if it was Ok
    assert_eq!(err.to_string(), "package name is empty");
    assert!(matches!(err, NameError::Empty), "unexpected error: {err:?}");
}

A test may also return a Result. Then ? works inside it, and an Err fails the test with the error's Debug output. This keeps the happy path free of unwraps:

#[test]
fn parses_full_spec() -> Result<(), String> {
    let spec = Spec::parse("numpy >=1.26")?;
    assert_eq!(spec.name, "numpy");
    Ok(())
}

Pixi's tests mostly use .unwrap() instead, which is fine in tests: a test is exactly the place where "panic if this is not what I expect" is the desired behavior. Pick one style per file.

Skipping: #[ignore]

#[ignore] skips a test unless you run cargo test -- --ignored (only ignored ones) or -- --include-ignored. Pixi combines it with cfg_attr from M10 so slow tests are skipped by default and enabled by a Cargo feature (crates/pixi/tests/integration_rust/install_tests.rs):

#[cfg_attr(not(feature = "slow_integration_tests"), ignore)]

/// Makes sure the lock file isn't touched and the environment is still
/// installed.

The same pattern with online_tests marks tests that need the internet. Without the feature they show as "ignored", so a contributor on a plane can still run the whole suite.

Remember: #[should_panic(expected = "..")] for panics, unwrap_err() plus asserts (or matches!) for Errs, -> Result to use ?, and #[cfg_attr(not(feature = ".."), ignore)] for opt-in tests.

Unit tests, integration tests, and what they can see

Rust has two places for tests, and the difference is about visibility (M10).

Unit testsIntegration tests
Whereinside the source file, in #[cfg(test)] mod tests { use super::*; .. }files in the crate's tests/ directory
Compiled aspart of the crate, only under cfg(test)a separate crate per file, depending on yours
Can useeverything in the module, including private itemsonly the pub API, like any other user
Good forthe details of one modulewhole features through the public API

use super::*; works for private items because tests is a child module, and private means "this module and its descendants". Pytest has no equivalent: Python tests can poke at anything. #[cfg(test)] means the module and its test-only dependencies ([dev-dependencies] such as insta and tempfile) are compiled only for cargo test.

crates/pixi_glob/
  Cargo.toml          # [dev-dependencies] insta, rstest, ...
  src/
    lib.rs
    glob_hash.rs      # ends with #[cfg(test)] mod test { ... }
    snapshots/        # insta snapshot files for the unit tests
crates/pixi/
  tests/
    integration_rust/
      main.rs         # one integration-test binary...
      add_tests.rs    # ...whose modules are the test files
      install_tests.rs
      common/         # shared helpers (PixiControl, builders)

Pixi's main integration suite is one test crate, crates/pixi/tests/integration_rust/main.rs, which declares mod add_tests; mod install_tests; ... (main.rs). Each top-level file directly in tests/ would be a separate binary, and each binary links against all of Pixi; with twenty files that is twenty multi-second link steps. One binary with modules links once. It also lets helpers live in mod common without being compiled twenty times. The same file sets up tracing once for the whole run with a std::sync::Once (M08).

Pixi names its unit-test module test in some files and tests in others. The name is only a convention; the #[cfg(test)] attribute is what matters. Follow whatever the file you are editing already does.

Remember: unit tests sit next to the code and see private items; integration tests in tests/ see only pub. Prefer one integration binary with modules for large crates.

Doc tests

M10 showed # Examples sections in doc comments. Code blocks there are doc tests: cargo test extracts each one, wraps it in a fn main, compiles it as an external user of your crate, and runs it. An example that no longer compiles or whose assert fails is a failing test, so documentation cannot silently rot. Python's doctest module is the same idea, but checks printed output instead of running asserts.

Test helpers and fixtures

Pytest fixtures are functions that build what a test needs, injected by name. Rust has no injection in the standard harness. You call helper functions directly, and Rust's ownership rules give you clean-up for free: a value's Drop runs when the test ends, whether it passed or panicked.

Helpers and builders

The simplest fixture is a function in mod tests that returns test data. When tests need many small variations, a builder (a struct with chained setter methods and a final build) keeps each test to the lines that matter. Pixi's integration tests use builders for pixi add and pixi install invocations, and a PixiControl type that owns a temporary workspace:

Temporary directories

The tempfile crate (a dependency of about half of Pixi's crates, used in a few hundred places) creates a fresh directory and deletes it when the guard is dropped:

#[test]
fn test_temp_file_created_in_same_dir_when_writable() {
    let dir = tempfile::tempdir().unwrap();
    let target = dir.path().join("pixi.toml");

    let temp = temp_file_for(&target, None).unwrap();

    assert_eq!(temp.path().parent().unwrap(), dir.path());
}   // `dir` is dropped here: the directory and everything in it is removed

(pixi_utils/src/atomic_write.rs, lines 114-122.) A common bug: let path = tempfile::tempdir().unwrap().path().to_path_buf(); drops the guard at the end of the statement, so the directory is already gone on the next line. Keep the guard in a variable for as long as you use the path.

Pytest's @pytest.mark.parametrize and fixtures have a Rust counterpart in the rstest crate, which Pixi uses in a dozen crates. Each #[case] becomes a separately named test, and a #[fixture] function is injected by parameter name, much like pytest (pixi_glob/src/glob_hash.rs):

Snapshot testing with insta

Some outputs are too big to write as an assert_eq! by hand: a rendered error message with source spans, a parsed manifest's full Debug tree, a lock file. Snapshot testing records the output once, stores it next to the test, and fails if a later run produces something different. You review the recorded output like any other code. Python has syrupy and pytest-snapshot; in Rust the standard is insta, and about half of Pixi's crates use it (around 630 snapshot assertions at the snapshot).

The macros

  • insta::assert_snapshot!(value): value is anything that implements Display (usually a String you built).
  • insta::assert_debug_snapshot!(value): records the pretty-printed Debug output, {:#?}.
  • assert_yaml_snapshot!, assert_json_snapshot!: serialize with serde (Level 2).

A snapshot is stored in one of two places:

  • Inline: assert_snapshot!(value, @"expected text"). The expected text lives in the test itself, usually as a raw string @r###"..."###. Good for short output.
  • In a file: assert_snapshot!(value) with no @. The file goes in a snapshots/ directory next to the source file, named <crate>__<module path>__<test name>.snap (with any test_ prefix dropped), for example crates/pixi_manifest/src/snapshots/pixi_manifest__discovery__test__workspace_discoverer.snap.

Here is a real inline snapshot test, from Pixi's channel parser (pixi_manifest/src/toml/channel.rs, lines 208-223). It snapshots the user-facing error for a channel table without a name:

The review workflow

When output changes (or a new snapshot has no stored value yet), the test fails and insta writes the new value next to the old one: a .snap.new file, or a .pending-snap file for inline snapshots. Then you review:

pixi run cargo test -p pixi_manifest        # fails, writes pending snapshots
pixi run cargo insta review                 # interactive diff: a(ccept), r(eject), s(kip)
pixi run cargo insta test --review          # run the tests and review in one step
pixi run cargo insta accept                 # accept everything pending (only after reading it!)
# in Pixi's checkout, the rust-test environment wraps these:
pixi run insta-review

Accepting rewrites the .snap file or the inline literal in your source, and the change shows up in your diff. Reviewers read snapshot diffs as carefully as code: a snapshot diff is a precise description of how your change alters behavior. cargo insta is a separate tool (the cargo-insta package; Pixi's rust-test environment installs it from conda-forge). In CI, insta never writes files; a mismatch is simply a failure.

Deterministic snapshots

A snapshot test is only useful if the same code always produces the same text, on every machine. The usual enemies, and the fixes:

  • Absolute paths (/home/alice/pixi/... vs C:\Users\bob\...): replace the machine-specific prefix with a placeholder, and backslashes with slashes.
  • Versions that change every release: replace with a placeholder.
  • HashMap order: sort first, or use BTreeMap/IndexMap.
  • Colors and terminal width: render with a fixed, colorless theme.
  • Timestamps, hashes of temp paths: insta's redactions and filters features replace them by pattern.

Pixi's format_diagnostic does the first four in one place (crates/pixi_test_utils/src/lib.rs); you will implement its normalization in exercise 3:

pub fn format_diagnostic(error: &dyn Diagnostic) -> String {
    // Disable colors in tests
    let mut s = String::new();
    let report_handler = GraphicalReportHandler::new()
        .with_cause_chain()
        .with_break_words(false)
        .with_theme(GraphicalTheme::unicode_nocolor());
    report_handler.render_report(&mut s, error).unwrap();
    // ... strip ANSI escape codes ...

    // Strip machine specific paths
    // (cargo_root: the repository root, computed from CARGO_MANIFEST_DIR)
    s = s.replace(&cargo_root, "<CARGO_ROOT>");

    // Replace pixi version with a placeholder so snapshots don't need updating on releases
    s = s.replace(PIXI_VERSION, "<PIXI_VERSION>");

    // Replace backslashes with forward slashes
    s = s.replace("\\", "/");

    // Remove trailing whitespace in the error message.
    s.lines()
        .map(|line| line.trim_end())
        .format("\n")
        .to_string()
}

Never accept a snapshot you have not read. "Update the snapshots" is the most common way a regression sneaks into a pull request, because the diff looks like routine churn. If a snapshot changes and your change was not supposed to affect that output, that is a bug report, not a chore.

Remember: assert_snapshot! (Display) and assert_debug_snapshot! ({:#?}), inline with @r"..." or in snapshots/*.snap. Review with cargo insta review. Normalize paths, versions, order, and colors first.

#[tokio::test]: a preview

About a fifth of Pixi's tests are async fns, because the code under test downloads, solves, and installs asynchronously. A plain #[test] cannot be async: something has to drive the future to completion. #[tokio::test] wraps the body in a Tokio runtime, the way pytest-asyncio's @pytest.mark.asyncio runs a coroutine in an event loop:

#[tokio::test]
async fn resolves_channel() {
    let client = test_client();
    let repodata = client.fetch("conda-forge", "noarch").await.unwrap();
    assert!(!repodata.is_empty(), "noarch repodata should list packages");
}

// Some Pixi tests need a multi-threaded runtime, for code that spawns blocking work:
#[tokio::test(flavor = "multi_thread", worker_threads = 1)]
async fn test_old_lock_install() { /* ... */ }

Everything else in this module applies unchanged: asserts, should_panic, Result returns, cfg_attr ignores, and snapshots. Async Rust is Level 2; for now, read #[tokio::test] async fn as "a test whose body may use .await".

Remember: #[tokio::test] = #[test] plus a runtime for .await. The flavor argument picks a multi-threaded runtime when the code needs one.

cargo nextest and Pixi's test tasks

cargo test runs all tests of a binary as threads in one process. cargo nextest is a drop-in replacement runner that runs each test in its own process, in parallel across all test binaries. For a big workspace that buys:

  • Isolation. A test that changes an environment variable, the current directory, or a global cannot affect another test, because they no longer share a process.
  • Speed. Scheduling is across the whole workspace, so one slow binary does not leave the other cores idle.
  • Readable output. One line per test with its time, failures printed together at the end, slow tests flagged, and retries for flaky tests.

The cost: nextest does not run doc tests (use cargo test --doc), and process-per-test startup is slower for suites of many tiny tests in one binary.

Pixi's tasks for the Rust suite live in its rust-test environment (pixi.toml, lines 589-596):

test-fast = {
  cmd = """RUST_LOG="debug,resolvo=info" cargo nextest run --workspace --all-targets""",
  description = "Run fast Rust tests",
}
test-slow = {
  cmd = """RUST_LOG="debug,resolvo=info" cargo nextest run --workspace --all-targets --features slow_integration_tests,online_tests --status-level skip --failure-output immediate-final --no-fail-fast --final-status-level slow""",
  description = "Run slow Rust tests with integration and online features",
}
  • --workspace --all-targets: every crate, and every target (lib, bins, tests/, examples, benches).
  • test-slow adds the two features from M10, which flip the cfg_attr(.., ignore) tests back on. --no-fail-fast keeps going after a failure so one run reports everything.
  • RUST_LOG configures the tracing output shown for failing tests: debug for Pixi, quieter for the resolvo solver.
pixi add cargo-nextest                      # conda-forge has it
pixi run cargo nextest run                  # all tests
pixi run cargo nextest run spec             # filter by name
pixi run cargo nextest run --no-capture     # show output, like -- --nocapture
pixi run cargo test --doc                   # doc tests, which nextest skips

To run part of Pixi's suite while working on one crate, run nextest through Pixi's own environment with a package filter: pixi run -e rust-test cargo nextest run -p pixi_manifest. Running the whole workspace takes a while; the narrow loop is what you use while developing, and test-fast is what you run before pushing. Building and running Pixi's suite is Level 3; for now, know what the tasks mean.

Remember: nextest = one process per test, parallel across the workspace, no doc tests. Pixi's test-fast is cargo nextest run --workspace --all-targets; test-slow adds slow_integration_tests,online_tests.

The definition of done: clippy and rustfmt

Passing tests is necessary, not sufficient. In Pixi a change is ready when it is formatted, lint-free, and tested. Two tools ship with the rust package from conda-forge:

  • rustfmt (cargo fmt) formats code to the one community style. Like ruff format, it ends style debates; reviewers do not comment on formatting.
  • clippy (cargo clippy) is a linter with hundreds of lints: correctness bugs, needless clones and collects, non-idiomatic patterns. -- -D warnings turns every warning into an error, so nothing slips through in CI.

Pixi's tasks (pixi.toml, lines 257-268):

cargo-clippy = {
  cmd = "cargo clippy --all-targets --workspace -- -D warnings",
  description = "Run clippy on all targets",
}
# ...
cargo-fmt = {
  cmd = "cargo fmt --all",
  description = "Format Rust code",
}

pixi run lint in Pixi's checkout runs these through lefthook, a git-hook runner: formatting, typos (a spell checker for code), and cargo-shear (unused dependencies) on the fast pre-commit stage, and clippy and cargo-deny (license checks) on the slower pre-push stage. Note --all-targets on clippy: tests are linted too.

pixi run cargo fmt --check                          # formatted? (fmt without --check fixes it)
pixi run cargo clippy --all-targets -- -D warnings  # lint-free, tests included
pixi run cargo test                                 # or: cargo nextest run, plus cargo test --doc

Habits Pixi reviewers look for in tests: one behavior per test, named for the behavior (rejects_empty_name, not test1); assert messages that say what was expected; a regression test for every bug fix, failing before the fix; snapshot tests for anything user-facing (error messages, CLI output); and no sleeps or network in fast tests.

Remember: fmt, clippy with -D warnings on all targets, then tests. In Pixi: pixi run lint and pixi run test-fast.

  • The imports show the dev-dependencies at work: insta for snapshots and pixi_test_utils for the shared error formatter.
  • TopLevel is a test-only fixture type: the channel value cannot be parsed on its own, so the test wraps it in a one-field table. #[allow(dead_code)] silences the warning that the field is never read (only Debug uses it, and dead-code analysis ignores derived impls).
  • The toml_span::Deserialize impl is how Pixi parses TOML with spans for error messages (Level 2). th.required("channel")? errors if the key is missing; that is the error the test_without_name snapshot captured earlier.
  • assert_debug_snapshot!(channel, @r###"..."###): the whole parsed tree, inline. Reading it tells you that a table-form channel becomes Map(PrioritizedChannel { .. }) with priority: None, without opening the parser.

Question 1: in excerpt 2, the snapshot includes a SHA-256 hash of files on disk. Is that deterministic across machines?

It is, provided the hashed files have identical bytes everywhere. The globbed files are committed test data, and a sibling test, test_normalize_line_endings, shows that Pixi normalizes \r\n to \n before hashing, so a Windows checkout with converted line endings still produces the same hash. Without that, this snapshot would fail on Windows.

Question 2: you change the error wording for a missing channel name. What fails, and what do you do?

test_without_name fails with a diff between the inline literal and the new output, and insta writes a pending snapshot. Run cargo insta review (Pixi: pixi run insta-review), read the diff, accept if it is exactly the change you intended, and commit the updated test file together with the code change. Grep for other snapshots containing the old wording too; any of them may change.

Question 3: why might TopLevel live in the test module instead of the parser module?

It exists only to make the channel value parseable in isolation. Under #[cfg(test)] it is not compiled into Pixi at all, cannot be used by production code by accident, and does not need to be documented or kept stable.

Implement the normalization step of Pixi's format_diagnostic: normalize_for_snapshot(output, cargo_root, version) must, in this order, replace every occurrence of cargo_root with <CARGO_ROOT>, replace every occurrence of version with <PIXI_VERSION>, replace backslashes with forward slashes, and trim trailing whitespace from every line, joining lines with "\n". fn normalize_for_snapshot(output: &str, cargo_root: &str, version: &str) -> String {
    let s = output
        .replace(cargo_root, "<CARGO_ROOT>")
        .replace(version, "<PIXI_VERSION>")
        .replace('\\', "/");
    s.lines().map(str::trim_end).collect::<Vec<_>>().join("\n")
}

Write a ManifestBuilder fixture: new(name), chained channel, platform, and dependency(name, spec) methods that take and return self, and build() that renders the TOML exactly as the test's inline "snapshot" shows. Channels and platforms keep insertion order; dependencies are sorted by name (use a BTreeMap) so output never depends on call order. Hint

Write a small helper that renders a list: items.iter().map(|s| format!("\"{s}\"")).collect::<Vec<_>>().join(", "), wrapped in brackets. In build, choose the defaults with if self.channels.is_empty(), then push lines onto a String with push_str or writeln! (that needs use std::fmt::Write;).

Show solution 
use std::collections::BTreeMap;

struct ManifestBuilder {
    name: String,
    channels: Vec<String>,
    platforms: Vec<String>,
    dependencies: BTreeMap<String, String>,
}

fn toml_list(items: &[String], default: &str) -> String {
    let rendered: Vec<String> = if items.is_empty() {
        vec![format!("\"{default}\"")]
    } else {
        items.iter().map(|s| format!("\"{s}\"")).collect()
    };
    format!("[{}]", rendered.join(", "))
}

impl ManifestBuilder {
    fn new(name: &str) -> Self {
        ManifestBuilder {
            name: name.to_string(),
            channels: Vec::new(),
            platforms: Vec::new(),
            dependencies: BTreeMap::new(),
        }
    }

    fn channel(mut self, channel: &str) -> Self {
        self.channels.push(channel.to_string());
        self
    }

    fn platform(mut self, platform: &str) -> Self {
        self.platforms.push(platform.to_string());
        self
    }

    fn dependency(mut self, name: &str, spec: &str) -> Self {
        self.dependencies.insert(name.to_string(), spec.to_string());
        self
    }

    fn build(&self) -> String {
        let mut out = String::from("[workspace]\n");
        out.push_str(&format!("name = \"{}\"\n", self.name));
        out.push_str(&format!("channels = {}\n", toml_list(&self.channels, "conda-forge")));
        out.push_str(&format!("platforms = {}\n", toml_list(&self.platforms, "linux-64")));
        if !self.dependencies.is_empty() {
            out.push_str("\n[dependencies]\n");
            for (name, spec) in &self.dependencies {
                out.push_str(&format!("{name} = \"{spec}\"\n"));
            }
        }
        out
    }
}

Pixi hashes files selected by glob patterns (excerpt 2). Implement a small matcher, glob_match(pattern, path), where ? matches one character other than /, * matches any run of characters (possibly empty) not containing /, ** matches any run of characters including /, and every other character matches itself. The whole path must match. The tests are a table of cases in the std-only style from this module; each failure names its case.

Hint

Work on Vec<char> (or byte slices) with a recursive helper fn m(p: &[char], s: &[char]) -> bool. If p starts with **, try matching the rest of the pattern at every position of s ((0..=s.len()).any(|i| m(&p[2..], &s[i..]))). For a single *, do the same but stop before the first /. Careful with **/: "**/*.toml" must not match "pixi.toml" in this simplified version, only paths with a /, which falls out naturally if you treat the / after ** as a literal.

Show solution 
fn glob_match(pattern: &str, path: &str) -> bool {
    fn m(p: &[char], s: &[char]) -> bool {
        match p {
            [] => s.is_empty(),
            ['*', '*', rest @ ..] => (0..=s.len()).any(|i| m(rest, &s[i..])),
            ['*', rest @ ..] => {
                let limit = s.iter().position(|&c| c == '/').unwrap_or(s.len());
                (0..=limit).any(|i| m(rest, &s[i..]))
            }
            ['?', rest @ ..] => matches!(s, [c, ..] if *c != '/') && m(rest, &s[1..]),
            [c, rest @ ..] => s.first() == Some(c) && m(rest, &s[1..]),
        }
    }
    let p: Vec<char> = pattern.chars().collect();
    let s: Vec<char> = path.chars().collect();
    m(&p, &s)
}

Quiz

Recap

  • #[test] marks a test; a panic fails it. assert!, assert_eq!, assert_ne! take a format!-style message; compared types need PartialEq and Debug.
  • #[should_panic(expected = "..")] for panics; unwrap_err() and matches! for Errs; tests may return Result and use ?. #[cfg_attr(not(feature = ".."), ignore)] makes tests opt-in.
  • Unit tests live in #[cfg(test)] mod tests and see private items; integration tests in tests/ see only pub. Doc tests run your examples as an external user.
  • Fixtures are functions and builders; Drop cleans up (tempfile::tempdir()). Paths come from CARGO_MANIFEST_DIR; shared helpers live in pixi_test_utils; rstest gives cases and fixtures.
  • insta: assert_snapshot!/assert_debug_snapshot!, inline @r"..." or snapshots/*.snap, reviewed with cargo insta review. Normalize first.
  • cargo nextest runs each test in its own process, in parallel, but skips doc tests. Pixi: test-fast, test-slow, then lint (fmt, clippy -D warnings).
