Types, Structs & Enums

Python lets a value be anything until it is used. Rust makes you say what each value is, and then uses that knowledge to rule out mistakes before the program runs. This module covers the building blocks: numbers and their exact sizes, tuples and arrays, a first look at the two string types, and the two ways you define your own types, structs and enums. Almost every line of Pixi uses them; by the end you will read Pixi's Task and SpecType definitions without effort.

Bindings: immutable by default, mut, and shadowing

In Python, x = 1 creates a name, and you can point it at something else at any time: x = x + 1, x = "now a string". In Rust, let x = 1; creates a binding, and by default a binding can never be changed. You saw E0384 in M00 when you tried. If a value must change, you declare that with let mut.

Why make immutability the default? Because most values never change after they are computed, and when you read code, knowing that is valuable: if you see let spec = ...; at the top of a 60-line function, you know spec still has that value at the bottom. Only the mut bindings need watching. The compiler also uses this to check that no one changes data while someone else is reading it (M03).

There is a second way to "change" a name: shadowing. A new let with the same name creates a new binding that hides the old one. The new binding can even have a different type. Predict the output:

The first spec is a string with spaces, the second is the trimmed string ("numpy>=1.26", 11 characters), and the third is a number. Each let made a new binding; none was mutated. Shadowing is idiomatic for a value that goes through a series of transformations where you never need the old version again, as in let line = line.trim();. Use mut when a value really does change over time, such as a counter or a vector you push to.

For values known at compile time, use a constant: const MAX_RETRIES: u32 = 3;. Constants are written in SCREAMING_SNAKE_CASE, must have their type written out, and can be declared at module level, like module-level constants in Python (except these really cannot change).

Remember: let is immutable; let mut can change; a second let with the same name shadows the first and may change its type. const is for compile-time constants.

Scalar types: integers, floats, booleans, characters

Python has one int that grows as large as needed and one float. Rust has a family of fixed-size numbers, because a fixed size is what lets the compiler lay data out in memory with no overhead:

TypeWhat it isRange or notes
i8, i16, i32, i64, i128Signed integers of 8 to 128 bitsi32: about ±2.1 billion. The default for integer literals.
u8, u16, u32, u64, u128Unsigned (never negative)u8: 0 to 255, used for bytes
usize, isizePointer-sized integers (64 bits on 64-bit machines)usize is the type of lengths and indexes: v.len() returns usize
f64, f32Floating-point numbersf64 is the default, same as Python's float

Some differences from Python stand out. Underscores in literals are only for readability, as in Python. 7 / 2 is 3: dividing two integers gives an integer, truncated toward zero, like Python's int(7 / 2), not 3.5. -7 % 3 is -1 (Python gives 2), because Rust's % is a remainder that keeps the sign of the left side. And each type knows its limits: u8::MAX, i64::MIN.

Type inference and annotations

You rarely need to write the types of local variables. The compiler infers them from how they are used, and falls back to i32 and f64 for bare literals. Function signatures are the exception: parameters and return types must always be written. That is a deliberate rule. A signature is a contract other code relies on, so it should not change because someone edited the function body.

Overflow

A Python int never overflows. A u8 holds at most 255, so what is 250 + 10? In a debug build, Rust checks and panics (stops the program with an error message) when arithmetic overflows. In a release build it does not check, and the value wraps around (260 becomes 4). Run this:

The first call prints 250; the second panics with "attempt to add with overflow". When you need specific behavior, ask for it with a method: checked_add returns "no value" on overflow (an Option, M04), saturating_add stops at the maximum, and wrapping_add wraps on purpose.

Pick integer types for the values they must hold, not to save memory. For counts and indexes, use usize (it is what len() returns, so you avoid casts). For sizes in bytes, use u64. Small types such as u8 are for bytes and for data formats that define them.

Remember: integers have fixed sizes; i32 and f64 are the defaults; usize is for lengths and indexes. Integer division truncates. Overflow panics in debug and wraps in release unless you choose a checked_, saturating_, or wrapping_ method.

Converting numbers with as

Python mixes int and float freely: 7.5 / 3 just works. Rust never converts between number types implicitly, not even from a smaller integer to a larger one. Compile this:

The error is E0277: cannot divide `f64` by `usize`, with the label "no implementation for f64 / usize". (The many note: lines after it list the combinations that are implemented; you can skip them.) Arithmetic in Rust is defined between two values of the same type. Why so strict? Because silent conversions are a classic source of bugs: a negative number becoming a huge unsigned one, or a 64-bit size quietly cut down to 32 bits.

The as keyword converts between number types explicitly: total_mb / files as f64. It always succeeds, so you must know what it does when the value does not fit:

  • Integer to a smaller integer truncates: 300 does not fit in a u8, and keeps only its low 8 bits, giving 44.
  • Signed to unsigned reinterprets the bits: -1i32 as u32 is 4294967295.
  • Float to integer rounds toward zero and saturates: 3.99 becomes 3, and a negative float becomes 0 for an unsigned type.
  • u8 as char turns a byte into the character with that code (65 is 'A').
  • {:.2} prints a float with two decimals, like Python's f"{x:.2f}".

as is fine for widening (u32 to u64), for integers to floats, and when you have already checked the range. When a value might not fit, use the checked conversions u8::try_from(x) and u64::from(x) from M06, which report failure instead of truncating. Clippy has lints for lossy casts that many projects turn on.

Remember: no implicit numeric conversions. as converts explicitly and never fails: it truncates integers, saturates floats, and reinterprets signs.

Tuples and arrays

A tuple groups a fixed number of values of possibly different types, like a Python tuple. Its type lists each element's type: (&str, u32, bool). You read elements with .0, .1, and so on, or unpack them all at once with a pattern, as in Python.

An array is a fixed number of values of the same type. Its type includes the length: [&str; 3] is "three string slices". The length is part of the type, so it can never change. For a list that grows, use Vec<T> (M05); arrays are for things like "the three supported platforms" or a fixed-size buffer.

_ in a pattern means "ignore this one". [0u8; 4] means "four copies of 0u8". {zeros:?} prints with the Debug format (more on that at the end of the module), which for arrays looks like a Python list.

Indexing is checked. Reading past the end does not return garbage and is not an exception you can catch; it panics:

The message is "index out of bounds: the len is 3 but the index is 3". This check is one of the reasons Rust is memory-safe: in C the same code would read whatever memory happens to follow the array.

One special tuple has no elements: (), called unit. It is the type of "no meaningful value", what a function returns when it has no return type, like Python's None as a return value. You met it in M00's semicolon error.

Remember: tuples are fixed-size and mixed-type, accessed with .0 or a pattern. Arrays are fixed-size and single-type, [T; N]. Out-of-bounds indexing panics. () is unit, the empty tuple.

String and &str: a first look

Python has one string type. Rust has two that you use constantly, and the difference is about ownership, the subject of the next module:

  • String is an owned, growable string stored on the heap. The variable that holds it is responsible for it and frees it when done. You create one with String::from("..."), "...".to_string(), or format!(...), and you can change it if it is mut (push, push_str).
  • &str (say "string slice" or "str ref") is a borrowed view into string data owned by someone else. It cannot grow, and it does not free anything. String literals such as "pixi" have type &'static str: a view of text built into the program, valid for the program's whole life ('static).

Think of String as the file and &str as a read-only window onto (part of) it. Both hold UTF-8 text. Because of that, s.len() counts bytes, not characters, and you cannot write s[0] to get a character (M05 shows chars()).

shout takes &str, so it accepts a literal directly and a String when you put & in front (&owned borrows it, and Rust converts &String to &str automatically). It returns a String because it builds new text that the caller will own. That is the rule of thumb for now:

  • Parameters: take &str when you only need to read the text.
  • Return values and struct fields: use String when the value must own its text.

Going the other way does not happen automatically. A function that wants a String will not accept a literal:

E0308: mismatched types, "expected String, found &str". The help: suggests "pixi".to_string(), which compiles, but the better fix is usually to change the parameter to &str, since shout only reads its input. M03 explains why, with the ownership visualizer.

Remember: String owns its text; &str borrows a view of text someone else owns. Read with &str, own with String. len() is in bytes.

Structs: your own record types

In Python you might hold a workspace's settings in a dict ({"name": ..., "channels": [...]}) or a dataclass. A dict accepts any key and any value, so a typo such as ws["chanels"] is found only when that line runs. A Rust struct is closer to a frozen dataclass with type hints that are enforced: a named type with a fixed set of named, typed fields.

from dataclasses import dataclass

@dataclass
class Workspace:
    name: str
    version: str
    channels: list[str]
    requires_pixi: bool
struct Workspace {
    name: String,
    version: String,
    channels: Vec<String>,
    requires_pixi: bool,
}
  • To create a value you must give every field. There are no default values unless you write a constructor (next section) or derive Default (M06).
  • name, on its own is field init shorthand for name: name,.
  • ..ws is struct update syntax: "take the remaining fields from ws", like dataclasses.replace(ws, name="hello-2"). It moves those fields out of ws, so afterwards ws can no longer be used as a whole (M03 explains moves).
  • Fields are read with a dot. To change a field, the whole binding must be mut; Rust has no per-field mutability.

Tuple structs and newtypes

A tuple struct has fields without names, accessed as .0, .1. The most useful form has exactly one field and is called a newtype: a new, distinct type that wraps an existing one. Pixi's TaskName is struct TaskName(String);. Why wrap a String? Because then a function that takes a TaskName cannot be given an environment name or a file path by mistake, even though all three are strings inside.

E0308: "expected Bytes, found Count". Both wrap a u64, but they are different types. A newtype costs nothing at run time; it exists only for the type checker. Python's typing.NewType has the same idea, but only a type checker such as mypy enforces it, and only if you run it.

Finally, a unit struct has no fields at all (struct Marker;). It is used as a type that carries no data, for example to implement a trait (M06).

Remember: structs have fixed, typed fields; all are given at creation. Shorthand name, and update syntax ..other save typing. A one-field tuple struct (newtype) makes a distinct type at no run-time cost.

impl blocks: methods and associated functions

A Python class keeps its data and its methods together in one class body. Rust separates them: the struct declares the data, and an impl block ("implementation") holds the functions for that type. There can be several impl blocks for one type, even in different files of the same crate.

Read the first parameter of each function. It decides what kind of function it is:

First parameterKindCalled asMeaning
noneAssociated functionVersion::new(0, 81, 0)Belongs to the type, not to a value. Like a Python @staticmethod or @classmethod.
&selfMethod, borrowsv.render()Reads the value. The most common kind.
&mut selfMethod, borrows mutablyv.bump_patch()Changes the value in place. Needs a mut binding.
selfMethod, takes ownershipv.into_tuple()Consumes the value; v is gone afterwards. Common for conversions (into_...) and builders.

Self (capital S) inside an impl is another name for the type being implemented, here Version. self (lowercase) is the value, like Python's self, except that you access fields with self.major and must always write self..

new is not a keyword. It is just the conventional name for the main constructor, and a type can have several (Version::parse, Version::zero). Rust has no __init__; struct literals like Version { major, minor, patch } are the only way to build a value, and new is a function that wraps one.

Calling a &mut self method on an immutable binding is an error, and a common one:

E0596: cannot borrow `v` as mutable, as it is not declared as mutable, with help: consider changing this to be mutable and the let mut v diff. The signature &mut self tells every caller "this changes the value", and the compiler holds callers to it.

Choose the receiver by what the method needs: &self unless it must change the value (&mut self) or consume it (self). Pixi's getters are almost all &self methods returning a reference, such as TaskName::as_str(&self) -> &str in the Reading Pixi section.

Remember: data in struct, behavior in impl. No self parameter: associated function, called with Type::name(). &self reads, &mut self changes, self consumes. new is a convention.

Enums: one of several kinds, each with its own data

Python's enum.Enum gives you a fixed set of named constants. Rust's enum starts there and goes much further: each variant can carry its own data, of its own shape. The simplest form matches Python's. Pixi's SpecType names the four kinds of dependency table:

A value of type SpecType is always exactly one of the four variants, written SpecType::Host and so on. Now the more powerful form. A Pixi task can be a plain command string, a command with options such as depends-on, or an alias that only runs other tasks. In Python you might model that with a class hierarchy, or a dict with a "kind" key and different other keys per kind. In Rust it is one enum:

Variants come in the same three shapes as structs: no data (Host), tuple-like (Plain(String)), and struct-like with named fields (Execute { cmd, depends_on }). The key property is that the data belongs to the variant. An Alias has no cmd at all, so there is no way to read the command of an alias by mistake. In the Python dict version, task["cmd"] on an alias is a KeyError at run time; in Rust, the code that would do it does not compile.

Enums like this are called sum types or tagged unions. They are one of the most important tools in Rust. The two most-used types in the standard library are enums: Option<T> (Some(value) or None) and Result<T, E> (Ok(value) or Err(error)). M04 is about them.

Pixi's pixi.toml lets a dependency be a version string (numpy = ">=1.26"), a table with a version and a channel, a git source, or a local path. How would you model "one dependency spec" as an enum? Which variants would carry which fields? (Level 3 shows how pixi_spec does it.)

Remember: an enum value is exactly one variant. Variants can be bare, tuple-like, or struct-like, and each carries only its own data. "One of several kinds" in Rust is an enum, not a string tag or a class hierarchy.

match: exhaustive by design

match compares a value against a list of patterns and runs the arm for the first one that fits. Python 3.10's match statement looks similar, but there is one crucial difference: Rust's match must be exhaustive. Every possible value must be handled by some arm, or the code does not compile. Remove the last arm and see:

error[E0004]: non-exhaustive patterns: `SpecType::RunConstraints` not covered. The primary span is the value being matched, a note: points at the variant you forgot, and the help: shows the arm to add. This is why Rust developers like enums so much. When someone adds a variant to SpecType later, every match that does not handle it becomes a compile error, pointing at exactly the places that need updating. In Python, a new enum member slips through every if/elif chain silently.

Patterns you will use

  • Literals such as 0 match that value.
  • | means "or": 1 | 2.
  • A plain name such as n matches anything and binds it, so the arm can use it.
  • if n < 10 after a pattern is a guard, an extra condition.
  • _ is the wildcard: anything not matched above. A u32 has four billion values, so without _ this match would not be exhaustive.
  • Patterns destructure data: Task::Execute { cmd, depends_on } binds both fields; Task::Execute { cmd, .. } binds one and ignores the rest; Task::Plain(_) ignores the payload.

match is an expression: it produces a value, so you can return it or assign it (let name = match spec { ... };). Every arm must then produce the same type.

if let for one pattern

When you care about only one variant, a full match with a _ => {} arm is noisy. if let runs a block only if the value matches one pattern:

if let Task::Alias(names) = &task {
    println!("alias for {} tasks", names.len());
}

Be careful with _ on your own enums. A wildcard arm makes the match exhaustive forever, so when a new variant is added it silently falls into _ instead of producing an error. Listing the variants explicitly, as Pixi's Task::is_executable does below, keeps the compiler on your side.

Remember: match must cover every value (E0004). Patterns can be literals, | alternatives, bindings, guards, _, and destructuring. match is an expression. if let handles one pattern.

#[derive(Debug, Clone, PartialEq)]: a first look

A Python dataclass gives you __repr__ and __eq__ for free. A new Rust struct or enum gets nothing: it cannot be printed for debugging, copied, or compared with == until you say so. The quickest way to say so is the derive attribute, which asks the compiler to generate the code:

  • Debug enables {:?} (one line) and {:#?} (pretty, multi-line), like repr(). It is for developers; user-facing output uses Display and {} (M06).
  • Clone adds .clone(), an explicit deep copy.
  • PartialEq enables == and !=, comparing field by field.
  • Copy, on the enum, makes copying implicit, like a number. Only types with no heap data may be Copy. M03 explains the difference from Clone.

Here is what happens without the derives. The compiler tells you exactly what to add.

The first gives E0277: `Channel` doesn't implement `Debug` with "consider annotating Channel with #[derive(Debug)]". The second gives E0369: binary operation `==` cannot be applied to type `Channel` with a suggestion to derive PartialEq. These are the two you will hit most in tests, because assert_eq!(a, b) needs both: PartialEq to compare, and Debug to print the two values when they differ.

What are Debug, Clone and PartialEq, exactly? They are traits, Rust's interfaces, and derive writes their implementations for you. M06 covers traits fully, including writing implementations by hand.

Almost every Pixi type starts with a derive line. SpecType has #[derive(Deserialize, Serialize, Debug, Copy, Clone, Hash, PartialEq, Eq)]. Serialize and Deserialize come from the serde crate (Level 2) and generate code that reads and writes the type as TOML or JSON. Derive macros from crates work exactly like the built-in ones.

Remember: new types have no printing, copying, or comparison until you derive or implement them. Debug for {:?}, Clone for .clone(), PartialEq for ==. assert_eq! needs Debug and PartialEq.

Reading Pixi: SpecType, TaskName, and Task

1. A simple enum with methods

From crates/pixi_manifest/src/spec_type.rs, lines 3-39:

#[derive(Deserialize, Serialize, Debug, Copy, Clone, Hash, PartialEq, Eq)]
/// What kind of dependency spec do we have
pub enum SpecType {
    /// Host dependencies are used that are needed by the host environment when
    /// running the project
    Host,
    /// Build dependencies are used when we need to build the project, may not
    /// be required at runtime
    Build,
    /// Regular dependencies that are used when we need to run the project
    Run,
    /// Runtime constraints on packages we might have
    RunConstraints,
}

impl SpecType {
    /// Convert to a name used in the manifest
    pub fn name(&self) -> &'static str {
        match self {
            SpecType::Host => "host-dependencies",
            SpecType::Build => "build-dependencies",
            SpecType::Run => "dependencies",
            SpecType::RunConstraints => "run-constraints",
        }
    }

    /// Returns all the variants of the enum
    pub fn all() -> impl Iterator<Item = SpecType> {
        [
            SpecType::Run,
            SpecType::Host,
            SpecType::Build,
            SpecType::RunConstraints,
        ]
        .into_iter()
    }
}
  • Line 3 derives eight traits. Copy is allowed because the enum carries no data; it makes SpecType as cheap to pass around as an integer. Hash and Eq let it be a key in a HashMap (M05).
  • /// lines are doc comments; they become the crate's documentation (M10).
  • name(&self) is a method. match self lists all four variants with no _, so adding a fifth variant would fail to compile right here until someone writes its table name. The return type &'static str says "a string literal": the names are built into the program.
  • all() has no self, so it is an associated function: SpecType::all(). It builds an array of the four variants and turns it into an iterator. impl Iterator<Item = SpecType> means "some iterator of SpecType" (M06 and M09); read it as "returns the variants one by one".

2. A newtype

From crates/pixi_manifest/src/task.rs, lines 22-30:

/// Represents a task name

TaskName wraps a String so that a task name cannot be confused with any other string. The field has no pub, so code outside the module cannot reach .0; it must go through as_str(), which lends out a &str view of the owned String. That is the String/&str rule from this module: the struct owns, the getter lends. 3. An enum with data

From task.rs, lines 157-190, trimmed:

/// Represents different types of scripts
#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum Task {
    Plain(TemplateString),
    Execute(Box<Execute>),
    Alias(Alias),
    Custom(Custom),
}

impl Task {
    /// Returns the names of the task that this task depends on
    pub fn depends_on(&self) -> &[Dependency] {
        match self {
            Task::Plain(_) | Task::Custom(_) => &[],
            Task::Execute(cmd) => &cmd.depends_on,
            Task::Alias(cmd) => &cmd.depends_on,
        }
    }

    // ...

    /// Returns true if this task is directly executable
    pub fn is_executable(&self) -> bool {
        match self {
            Task::Plain(_) | Task::Custom(_) | Task::Execute(_) => true,
            Task::Alias(_) => false,
        }
    }
  • Each variant wraps one value. TemplateString is a command string that may contain template variables. Execute, Alias, and Custom are structs defined further down the file: for example Alias has depends_on, description, and args fields (lines 816-825). Wrapping a struct in a tuple variant is a common Pixi style: the struct can have its own methods.
  • Box<Execute> puts the large Execute struct on the heap so that every Task value stays small (M08). Code can still read cmd.depends_on through the box.
  • depends_on returns &[Dependency], a borrowed slice (a view of a list; M03). Plain and custom tasks have no dependencies, so they return &[], an empty slice. The others lend out their own field.
  • Task::Plain(_) | Task::Custom(_) uses | to share an arm and _ to ignore the payload. Both matches list every variant explicitly instead of using a wildcard.
Question: Pixi adds a fifth Task variant. What happens when it compiles?

Both depends_on and is_executable fail with E0004 (non-exhaustive patterns), naming the new variant. The person adding it is forced to decide, at each place, whether the new kind of task has dependencies and whether it can be executed. That is exactly why these matches avoid _.

Question: why can SpecType derive Copy, but Task cannot?

SpecType's variants carry no data, so a value is just a small tag and copying it is trivial. Task's variants own heap data (strings, vectors, a Box), and Copy is only allowed for types that can be duplicated by copying bytes. Task derives Clone instead, which makes copying explicit with .clone().

Question: outside pixi_manifest, can you write name.0 for a TaskName?

No. The struct is pub but its field is not (pub struct TaskName(String);), so .0 is private to the module. You must use name.as_str(). Keeping fields private lets the type guarantee things about its contents, for example that a name was validated when it was created.

Practice

Write two small functions:

  • percent(done: u32, total: u32) -> f64: the percentage of total that is done, as a float. percent(1, 4) is 25.0. When total is 0, return 0.0 instead of dividing by zero.
  • mib(bytes: u64) -> u64: whole mebibytes (1 MiB = 1024 × 1024 bytes), rounded down. mib(3_145_728) is 3 and mib(1_048_575) is 0.
Hint

Convert before dividing: done as f64 / total as f64 * 100.0. Integer division on u64 already rounds down, so mib is one division. Use an if expression for the zero case.

Show solution 
fn percent(done: u32, total: u32) -> f64 {
    if total == 0 {
        0.0
    } else {
        done as f64 / total as f64 * 100.0
    }
}

fn mib(bytes: u64) -> u64 {
    bytes / (1024 * 1024)
}

as binds tighter than /, so done as f64 / total as f64 converts both sides first. Converting u32 to f64 is always exact. Writing (done / total) as f64 would divide integers first and give 0 for 1/3.

Complete the impl block for Version:

  • Version::new(major, minor, patch) builds a version.
  • render(&self) returns "major.minor.patch", such as "0.81.0".
  • bump_minor(&mut self) adds 1 to minor and resets patch to 0.
  • is_compatible_with(&self, other: &Version) applies Cargo's caret rule from M01: if major is greater than 0, versions are compatible when their majors are equal; if major is 0, both major and minor must be equal.
Hint

new can use field init shorthand: Self { major, minor, patch }. For the caret rule, an if self.major == 0 { ... } else { ... } expression whose branches are boolean comparisons joined with &&.

Show solution 
#[derive(Debug, Clone, PartialEq)]
struct Version {
    major: u32,
    minor: u32,
    patch: u32,
}

impl Version {
    fn new(major: u32, minor: u32, patch: u32) -> Self {
        Self { major, minor, patch }
    }

    fn render(&self) -> String {
        format!("{}.{}.{}", self.major, self.minor, self.patch)
    }

    fn bump_minor(&mut self) {
        self.minor += 1;
        self.patch = 0;
    }

    fn is_compatible_with(&self, other: &Version) -> bool {
        if self.major == 0 {
            other.major == 0 && self.minor == other.minor
        } else {
            self.major == other.major
        }
    }
}

            SpecType::Host | SpecType::Build => true,
            SpecType::Run | SpecType::RunConstraints => false,
        }
    }
}

The standard library also has a matches! macro for this: matches!(self, SpecType::Host | SpecType::Build). It is shorter, but like _ it would not flag a new variant.

Here is a simplified version of Pixi's Task. Implement three methods with match:

  • depends_on(&self) -> &[String]: the task's dependencies. Plain has none (return &[]); Execute and Alias lend out their depends_on field.
  • is_executable(&self) -> bool: false only for Alias.
  • summary(&self) -> String: for Plain and Execute, the command; for Alias, "alias: " followed by its dependencies joined with ", ", such as "alias: lint, test".
Hint

Destructure in the patterns: Task::Execute { depends_on, .. } => depends_on gives you a reference to the vector (because self is a reference), which Rust turns into a slice for the return type. Two variants with a field of the same name and type can share an arm: Task::Execute { depends_on, .. } | Task::Alias { depends_on } => depends_on.

For summary, cmd.clone() or cmd.to_string() turns the borrowed command into an owned String, and format!("alias: {}", depends_on.join(", ")) builds the alias text.

Show solution 
enum Task {
    Plain(String),
    Execute { cmd: String, depends_on: Vec<String> },
    Alias { depends_on: Vec<String> },
}

impl Task {
    fn depends_on(&self) -> &[String] {
        match self {
            Task::Plain(_) => &[],
            Task::Execute { depends_on, .. } | Task::Alias { depends_on } => depends_on,
        }
    }

    fn is_executable(&self) -> bool {
        match self {
            Task::Plain(_) | Task::Execute { .. } => true,
            Task::Alias { .. } => false,
        }
    }

    fn summary(&self) -> String {
        match self {
            Task::Plain(cmd) | Task::Execute { cmd, .. } => cmd.clone(),
            Task::Alias { depends_on } => format!("alias: {}", depends_on.join(", ")),
        }
    }
}

Compare with Pixi's Task::depends_on in the Reading Pixi section: same shape, same empty slice for tasks with no dependencies, and no wildcard arms.

A Pixi environment is a list of features, and it includes the default feature unless no-default-feature = true. Implement:

  • Environment::new(name): no extra features, no_default_feature false.
  • with_feature(self, feature) and without_default(self): builder methods. Each takes self by value, changes it, and returns it, so calls can be chained: Environment::new("test").with_feature("py312").with_feature("test").
  • all_features(&self) -> Vec<String>: "default" first (unless no_default_feature), then the added features in the order they were added.
Hint

A method that takes self owns the value, so it may change it if the parameter is declared mutable: write fn with_feature(mut self, feature: &str) -> Self, then self.features.push(feature.to_string()); and end with self. Adding mut there does not change the method's signature for callers.

For all_features: start with let mut all = Vec::new();, push "default".to_string() if needed, then loop over &self.features pushing f.clone().

Show solution 
#[derive(Debug, Clone, PartialEq)]
struct Environment {
    name: String,
    features: Vec<String>,
    no_default_feature: bool,
}

impl Environment {
    fn new(name: &str) -> Self {
        Self { name: name.to_string(), features: Vec::new(), no_default_feature: false }
    }

    fn with_feature(mut self, feature: &str) -> Self {
        self.features.push(feature.to_string());
        self
    }

    fn without_default(mut self) -> Self {
        self.no_default_feature = true;
        self
    }

    fn all_features(&self) -> Vec<String> {
        let mut all = Vec::new();
        if !self.no_default_feature {
            all.push("default".to_string());
        }
        for f in &self.features {
            all.push(f.clone());
        }
        all
    }
}

The builder pattern is common in Rust because there are no keyword arguments or default parameter values. You will see it in Pixi for things like HTTP clients and solver settings. Taking self by value means a builder chain needs no mut binding at all.

Quiz

Recap

  • Bindings are immutable unless let mut. Shadowing with a new let creates a new binding, possibly of a new type.
  • Integers have fixed sizes (i32 default, usize for lengths). Integer division truncates. Overflow panics in debug, wraps in release.
  • No implicit numeric conversions. as converts explicitly: it truncates integers, saturates floats, and reinterprets signs.
  • Tuples group mixed types (.0, patterns). Arrays are [T; N] with a fixed length. Out-of-bounds indexing panics.
  • String owns text; &str borrows it. Take &str to read; return or store String.
  • Structs have named, typed fields; newtypes make distinct types for free. impl blocks hold associated functions (new) and methods taking &self, &mut self, or self.
  • Enum variants carry their own data. match must be exhaustive (E0004); avoid _ on your own enums so new variants are caught.
  • #[derive(Debug, Clone, PartialEq)] adds printing, cloning, and comparison; assert_eq! needs Debug and PartialEq.
