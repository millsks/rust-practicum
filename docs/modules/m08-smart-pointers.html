Smart Pointers & Shared State

Ownership says every value has exactly one owner, and borrowing says references must not outlive it. Real programs need more: a tree whose nodes contain nodes, one HTTP client used by twenty download tasks, a cache that many threads update. Rust's standard library meets those needs with a small set of smart pointers, types that own a value and add a rule about how it is shared or changed. This module teaches each one by the problem it solves, and ends with why nearly every long-lived object in Pixi sits behind an Arc.

Box<T>: one owner, on the heap

In Python, every object lives on the heap and every variable is a pointer to one, so you never think about where a value lives. In Rust, a value lives wherever its owner is: a local i32 or a struct sits directly in the function's stack frame, and its size must be known at compile time. A String or a Vec is a small fixed-size handle on the stack that owns a heap buffer (M03).

Box<T> is the simplest smart pointer: it puts one T on the heap and owns it. A box is one pointer wide, has exactly one owner, moves like any other value, and frees its T when it is dropped. Box::new(value) creates one, and *b or auto-deref (calling methods directly on b) reaches the value. You need it in three situations.

1. Recursive types

A type that contains itself directly would be infinitely large. An expression tree is the classic case:

(A second error, E0391 "cycle detected", is a follow-on from the same problem; fix the first error and it disappears.) A box has a fixed size (one pointer), so the recursion moves to the heap:

Notice eval(a) where a: &Box<Expr>: deref coercion turns &Box<Expr> into &Expr automatically. A Vec<Expr> field would also break the cycle, because a Vec already keeps its elements on the heap; that is how tree-like types such as a dependency tree usually hold their children.

2. Trait objects

M06 introduced Box<dyn Trait>: a value of some type that implements the trait, chosen at run time. Different types have different sizes, so they cannot sit side by side in a Vec; boxing each gives every element the same size (a pointer plus a vtable pointer).

Remember: Box<T> is single ownership on the heap. Reach for it for recursive types, dyn Trait values, and large, rare enum variants. It adds no sharing and no mutability rules.

Rc<T>: many owners, one thread

Sometimes a value genuinely has several owners, and none of them is clearly the last to use it. In Python that is every object: CPython counts references and frees the object when the count reaches zero. Rc<T> ("reference counted") gives you exactly that model, opt-in, for one value.

Rc::new(value) moves the value to the heap next to a counter set to 1. Rc::clone(&rc) does not copy the value: it increments the counter and returns another pointer to the same allocation. Dropping an Rc decrements the counter, and the value is dropped when it reaches zero. Predict the counts:

The convention is to write Rc::clone(&x) rather than x.clone(). Both do the same thing, but the explicit form tells a reader "this is a cheap pointer copy, not a deep clone of the vector".

There is a catch: Rc<T> only gives out shared references. If several owners could each get &mut T, the "one writer or many readers" rule from M03 would be broken. So this fails:

"cannot borrow data in an Rc as mutable" is the rule doing its job. Shared ownership plus mutation needs one more piece, coming next.

Reference counting has one leak: a cycle. If a holds an Rc to b and b holds one to a, neither count reaches zero. Python has a cycle collector for this; Rust does not. Break cycles with std::rc::Weak, a non-owning pointer that you upgrade() to an Option<Rc<T>> when you need it (parent pointers in trees are the usual case).

Remember: Rc::clone copies a pointer and bumps a count. The value is dropped when the last Rc goes. Rc is read-only and single-thread only.

RefCell<T> and interior mutability

The borrow rules are checked at compile time. Occasionally you know a mutation is safe but the compiler cannot see it, usually because the only thing you have is a &self or a shared Rc. Interior mutability is the name for types that allow mutation through a shared reference, by checking the rules some other way.

RefCell<T> checks the borrowing rules at run time. It keeps a small counter of active borrows:

  • cell.borrow() returns a Ref<T>, which acts like &T. Many can exist at once.
  • cell.borrow_mut() returns a RefMut<T>, which acts like &mut T. Only one can exist, and only when there are no Refs.
  • Breaking the rule does not fail to compile; it panics. try_borrow_mut() returns a Result instead.

The guards release their borrow when dropped, just like a reference's last use ends a borrow. A common pattern is a type whose methods take &self but record something on the side:

Combine it with Rc and you get shared, mutable, single-threaded state: Rc<RefCell<T>>. Every owner can call borrow_mut(). This is the closest thing Rust has to an ordinary Python object shared between two parts of a program.

std::cell::Cell<T> is interior mutability without borrows: you get() a copy or set() a new value, so it can never panic. It suits small Copy values such as counters and flags: calls: Cell<u32> and self.calls.set(self.calls.get() + 1).

Pixi's Python build backend collects warnings while it reads pyproject.toml metadata, from methods that only take &self (crates/pixi_build_python/src/metadata.rs):

pub struct PyprojectMetadataProvider {
    manifest_root: PathBuf,
    pyproject_manifest: OnceCell<PyProjectToml>,
    mode: PyprojectManifestMode,
    warnings: RefCell<Vec<String>>,
}
// ...
    pub fn warnings(&self) -> Vec<String> {
        self.warnings.borrow().clone()
    }

    /// Adds a warning message to the warning collection.
    fn add_warning(&self, warning: impl Into<String>) {
        self.warnings.borrow_mut().push(warning.into());
    }

Both guards live for one expression, so a double borrow cannot happen. The OnceCell field is another interior-mutability type, covered below.

Remember: RefCell moves the borrow check to run time: borrow() for many readers, borrow_mut() for one writer, a panic if you break it. Rc<RefCell<T>> is shared mutable state on one thread.

Threads, Send and Sync

Rc's counter is a plain integer. If two threads cloned the same Rc at the same moment, both could read 1 and both write 2, and the value would later be freed while one thread still uses it. Python avoids this with the global interpreter lock; Rust avoids it with two marker traits that the compiler checks.

  • Send: a value of this type can be moved to another thread.
  • Sync: a &T can be shared between threads (precisely, T is Sync if &T is Send).

You almost never implement these. The compiler derives them automatically: a struct is Send if all its fields are. String, Vec<T> of Send things, and integers are both. Rc<T> is neither, and RefCell<T> is Send but not Sync. std::thread::spawn requires its closure to be Send, so:

Arc, Mutex and RwLock

Arc<T> ("atomically reference counted") is Rc<T> with a counter updated by atomic CPU instructions, which are safe to run from several threads at once. Same API, slightly slower clones, and Send + Sync when T is. Swap Rc for Arc in the failing program above and it compiles.

Like Rc, Arc gives shared access only. To mutate shared data from several threads you need the thread-safe version of RefCell: a lock.

  • Mutex<T> ("mutual exclusion"): m.lock() waits until no other thread holds the lock, then returns a MutexGuard<T> that derefs to &mut T. Dropping the guard unlocks.
  • RwLock<T> (reader-writer lock): read() gives shared access to many threads at once, write() gives exclusive access to one. Better when reads vastly outnumber writes.

Unlike Python's threading.Lock, which guards whatever code you remember to put inside with lock:, a Rust Mutex contains the data. There is no way to reach the data without taking the lock, so "forgot to lock" is a compile error, not a bug report.

The shape is worth memorizing, because you will see it everywhere: create the Arc, then for each thread clone it into a new variable with the same name and move that clone into the closure. After every thread is joined and its clone dropped, the count is back to 1.

Why .lock().unwrap()?

If a thread panics while holding a std Mutex, the data might be half-updated, so the lock becomes poisoned and later lock() calls return Err. Most code treats that as a bug and propagates the panic with unwrap(). That is one of the accepted uses of unwrap from M04.

Keep the guard short

A guard holds the lock until it is dropped. Holding it while doing slow work (a download, a solve) makes every other thread wait. Take the lock, copy out or update what you need, and let the guard go, as the example does by locking inside a single statement. Taking two locks in different orders in two threads can deadlock; the simplest defence is to never hold two at once.

Most of Pixi uses the parking_lot crate's Mutex and RwLock instead of std's. They are smaller and do not poison, so lock(), read() and write() return the guard directly, with no unwrap():

use parking_lot::Mutex;              // e.g. crates/pixi_progress/src/lib.rs
let guard = state.lock();            // MutexGuard, no Result
use std::sync::Mutex;
let guard = state.lock().unwrap();   // LockResult<MutexGuard>

So when you read self.inner.write() with no unwrap in Pixi, look at the imports: it is a parking_lot::RwLock. The std version still appears where a dependency is not worth it, such as the once-per-run warning set in pixi_config (crates/pixi_config/src/lib.rs#L140-L141 and #L652-L653):

static NETFS_REDIRECT_WARNED: LazyLock<Mutex<HashSet<CacheKind>>> =
    LazyLock::new(|| Mutex::new(HashSet::new()));
// ...
    let mut warned = NETFS_REDIRECT_WARNED.lock().unwrap();
    if warned.insert(kind) {

HashSet::insert returns true only the first time, so each cache kind warns once per process, even when several threads resolve cache directories at the same time.

Async code (Level 2) has its own rule: never hold a std or parking_lot guard across an .await. The task may move to another thread while it waits. Pixi uses tokio::sync locks and semaphores where a lock must be held across an await.

Remember: Arc shares, the lock mutates. Arc<Mutex<T>> for shared mutable state across threads, Arc<RwLock<T>> when reads dominate. Clone the Arc before move; keep guards short.

Scoped threads: borrowing without Arc

M07 showed that thread::spawn needs 'static closures, because a spawned thread might outlive the function that started it. That is the reason Arc appears in the previous example: each thread had to own its pointer. But if you only need parallelism for the duration of one function call, there is a simpler tool.

std::thread::scope(|s| { ... }) creates a scope in which s.spawn(...) starts threads that are guaranteed to finish before scope returns. Because of that guarantee, those threads may borrow local variables, with ordinary borrowing rules, and no Arc or 'static bound:

Each thread gets a shared borrow of one platform name and a mutable borrow of a distinct slot in sizes. The borrow checker accepts this because iter_mut hands out non-overlapping &mut references. Here, move moves the references into each closure, not the vectors, so platforms is still usable afterwards.

Pixi's CMake backend runs three ninja queries in parallel so that no process blocks on a full output pipe. The threads borrow self, which a plain thread::spawn could not do (crates/pixi_build_cmake/src/inputs.rs):

    fn run_concurrently(
        &self,
        queries: [(&'static str, &[&str]); 3],
    ) -> io::Result<[(&'static str, Output); 3]> {
        std::thread::scope(|s| {
            let handles = queries.map(|(label, args)| {
                let h = s.spawn(move || {
                    Command::new(&self.binary)
                        .arg("-C")
                        .arg(&self.build_dir)
                        .args(args)
                        .output()
                });
                (label, h)
            });
            // ... join each handle, collect the outputs
        })
    }

&self.binary inside a thread closure is the giveaway: that borrow is only legal in a scoped thread.

Remember: if the threads end before the function does, use thread::scope and borrow. Use Arc when the work outlives the caller, as spawned threads and async tasks do.

Cow<'_, str>: borrow when you can, own when you must

M07 ended with a dilemma: a function that sometimes returns its input unchanged and sometimes builds a new string. Returning String always allocates, even in the common unchanged case. Returning &str cannot express the changed case.

std::borrow::Cow ("clone on write") is an enum with both options:

enum Cow<'a, B: ?Sized + ToOwned> {
    Borrowed(&'a B),          // for str: &'a str
    Owned(<B as ToOwned>::Owned), // for str: String
}

A Cow<'_, str> derefs to &str, so callers use it like any string. It allocates only in the Owned case. .into_owned() turns it into a String (copying only if it was borrowed), and .to_mut() gives a &mut String, cloning first if needed. That last method is where the name comes from.

A second use: Cow<'static, str> as a field that holds either a string literal (free) or a formatted String. Combined with impl Into<Cow<'static, str>> parameters, a function accepts both "literal" and format!(...) without forcing callers to allocate.

Pixi's task runner quotes arguments for its shell with a function of exactly this shape (crates/pixi_manifest/src/task.rs):

pub fn quote(in_str: &str) -> Cow<'_, str> {
    if in_str.is_empty() {
        "\"\"".into()
    } else if in_str.contains(['\t', '\r', '\n', ' ', '[', ']']) {
        let mut out: String = String::with_capacity(in_str.len() + 2);
        // ... push '"', each char (escaping '"' and '\\'), then '"'
        out.into()
    } else {
        in_str.into()
    }
}

.into() converts through From (M06): &str becomes Cow::Borrowed, String becomes Cow::Owned. The empty case returns the literal "\"\"", a &'static str, which also fits Cow<'_, str>. Pixi's manifest errors use the second pattern: GenericError::new(message: impl Into<Cow<'static, str>>) (crates/pixi_manifest/src/error.rs).

Remember: return Cow<'_, str> when the usual result is the input unchanged and the rare one is new text. It reads as &str and allocates only when needed.

OnceLock, LazyLock, and once_cell

Python modules often hold globals computed at import time: DEFAULT_CHANNELS = load() or a compiled regex. Rust static items must be built by constant expressions, so a Regex or a value read from the environment cannot be a plain static. And some struct fields are expensive to create but not always needed, such as an HTTP client. Both cases want "compute on first use, then share".

  • std::sync::OnceLock<T>: a cell that starts empty and can be set exactly once. get_or_init(|| ...) runs the closure the first time and returns &T on every call. It is thread-safe: if two threads race, one runs the closure and the other waits.
  • std::sync::LazyLock<T>: a OnceLock with its initializer built in. Declare it with a closure; the first dereference runs it. Ideal for static items.

A static lives for the whole program, so a reference into it is &'static, which is why cache_dir can return &'static str. The AtomicUsize counter is itself a small piece of thread-safe interior mutability: a static that can be changed without a lock.

Pixi reads proxy settings once per process with LazyLock statics (crates/pixi_config/src/lib.rs):

// detect proxy env vars like curl: https://curl.se/docs/manpage.html
static ENV_HTTP_PROXY: LazyLock<Option<String>> = LazyLock::new(|| {
    ["http_proxy", "all_proxy", "ALL_PROXY"]
        .iter()
        .find_map(|&k| std::env::var(k).ok().filter(|v| !v.is_empty()))
});
// ...
static USE_PROXY_FROM_ENV: LazyLock<bool> =
    LazyLock::new(|| (*ENV_HTTPS_PROXY).is_some() || (*ENV_HTTP_PROXY).is_some());

(*ENV_HTTPS_PROXY) dereferences the lazy static, forcing its initializer if no one has yet. One lazy value can depend on another.

Why Pixi still uses once_cell

Before Rust 1.70 (OnceLock) and 1.80 (LazyLock), the once_cell crate provided these types, and the standard library versions were modelled on it. New code should use std. Pixi has moved most statics to std, but some fields still use once_cell::sync::OnceCell, and a comment says why (crates/pixi_core/src/workspace/mod.rs):

Remember: LazyLock for statics computed on first use, OnceLock for "set once" fields and function-local statics. once_cell::sync::{OnceCell, Lazy} are the same ideas from before std had them.

Why Pixi passes Arc everywhere

Open almost any Pixi crate and you will find Arc<Gateway>, Arc<Semaphore>, Arc<CacheDirs>, Arc<EnvironmentSpec>. The reasons follow from everything above:

  1. Long-lived services are shared. One repodata gateway, one HTTP client, one download budget serve every solve and install in a run. Nobody is the single natural owner.
  2. Async tasks need 'static + Send. Pixi downloads and solves concurrently on tokio. A spawned task cannot borrow from the function that spawned it (M07), so it must own what it uses. Cloning an Arc gives each task an owning handle for the price of an atomic increment.
  3. Clones must be cheap. Cloning a Gateway or a large spec by value would copy caches and maps. Cloning an Arc copies a pointer.
  4. Immutability makes sharing safe. Most shared data is never changed after creation, so it needs no lock at all: Arc<T> alone is enough. Where something does change, a lock goes inside: Arc<RwLock<T>>.

A common Pixi idiom builds a cheaply clonable handle: a struct whose only real field is an Arc to the shared data, with #[derive(Clone)]. The command dispatcher that runs every solve and build is one (crates/pixi_command_dispatcher/src/command_dispatcher/mod.rs):

#[derive(Clone)]
pub struct CommandDispatcher {
    /// Holds the shared data required by the command dispatcher.
    pub(crate) data: Arc<CommandDispatcherData>,
    // ...
    /// Held so that when the last [`CommandDispatcher`] clone drops,
    /// the compute dep-graph snapshot is written if the
    /// `PIXI_COMPUTE_DEP_GRAPH` env var is set.
    _dump_guard: Arc<DepGraphDumpGuard>,
}

The _dump_guard field uses the reference count as a signal: its Drop impl writes a debug file, and because it sits in an Arc, that happens exactly once, when the last clone of the dispatcher goes away. Here is the same idea in miniature. Predict the output, including when "dropped" appears:

Choosing a pointer

Do not wrap things in Arc<Mutex<...>> by reflex. Start with plain ownership and borrowing; add Arc when a value must be shared by things that outlive each other; add a lock only when shared data must change. Reviewers ask "who mutates this?" when they see a lock, and expect an answer.

Remember: Pixi uses Arc because its services are shared by many concurrent tasks that must own their handles. An Arc clone is a pointer copy, and most shared data is immutable, so no lock is needed.

Reading Pixi

Two excerpts from the snapshot combine several of this module's pointers in one place.

1. A thread-safe registry of environment specs

The command dispatcher hands out small ids for workspace environments and keeps their full specs in a registry that many concurrent computations read (crates/pixi_command_dispatcher/src/environment/registry.rs#L25-L101):

pub struct WorkspaceEnvRegistry {
    inner: RwLock<WorkspaceEnvRegistryInner>,
}

#[derive(Default)]
struct WorkspaceEnvRegistryInner {
    entries: Vec<Arc<EnvironmentSpec>>,
    refs_by_key: HashMap<WorkspaceEnvRegistryKey, WorkspaceEnvRef>,
}

impl WorkspaceEnvRegistry {
    pub fn allocate(&self, name: String, platform: String, spec: EnvironmentSpec) -> WorkspaceEnvRef {
        let mut inner = self.inner.write();
        // ... build `key` from name, platform and spec
        if let Some(existing) = inner.refs_by_key.get(&key) {
            return existing.clone();
        }
        // ... compute a new `id` from inner.entries.len()
        inner.entries.push(Arc::new(key.spec.clone()));
        // ... build `env_ref`
        inner.refs_by_key.insert(key, env_ref.clone());
        env_ref
    }

    pub fn get(&self, id: WorkspaceEnvId) -> Arc<EnvironmentSpec> {
        self.inner
            .read()
            .entries
            .get(id.as_index())
            .expect("allocated WorkspaceEnvId must have a registry entry")
            .clone()
    }
}
  • RwLock here is parking_lot::RwLock (line 3 imports it), which is why write() and read() have no unwrap().
  • Both methods take &self, yet allocate mutates. That is interior mutability: the lock turns a shared reference into exclusive access for the duration of the guard.
  • let mut inner = self.inner.write(); holds one write guard for the whole method. The doc comment on allocate explains why: lookup and insert must happen under the same lock, or two threads allocating the same key could both miss the lookup and mint two ids.
  • Vec<Arc<EnvironmentSpec>>: each spec is immutable once stored, so readers get their own Arc from get and can use it after the read guard is gone, with no lock held while they work.
  • In get, the read guard is a temporary in a method chain; it is dropped at the end of the statement, right after .clone() bumped the count. The lock is held for a few instructions.
  • Elsewhere in the file (lines 109-119), the registry itself is stored as Arc<WorkspaceEnvRegistry>, so the shape is Arc<RwLock<Vec<Arc<T>>>> with the lock inside the struct.
Question: why does get return Arc<EnvironmentSpec> instead of &EnvironmentSpec?

A reference into entries would have to borrow from the read guard, so the caller would keep the read lock held as long as it used the spec, blocking every allocate. (The signature could not even express it without returning the guard.) Returning a cloned Arc lets the guard drop immediately; the spec stays alive through the caller's own count.

Question: what would go wrong if allocate took a read lock for the lookup, released it, and then took a write lock to insert?

Between the two locks, another thread could allocate the same key. Both would see "not found" and insert, creating two ids for one environment, which breaks the "equal requests reuse the id" promise. Holding the write lock across both steps makes check-then-insert atomic.

2. A lazily created, shared download budget

The Workspace limits how many downloads run at once with a semaphore (a counter of permits that async tasks wait on). It is created on first use and shared by every download (crates/pixi_core/src/workspace/mod.rs#L192-L193 and #L1149-L1156):

    /// The concurrent request semaphore
    concurrent_downloads_semaphore: OnceCell<Arc<Semaphore>>,
// ...
    pub fn concurrent_downloads_semaphore(&self) -> Arc<Semaphore> {
        self.concurrent_downloads_semaphore
            .get_or_init(|| {
                let max_concurrent_downloads = self.config().max_concurrent_downloads();
                Arc::new(Semaphore::new(max_concurrent_downloads))
            })
            .clone()
    }
  • OnceCell is once_cell::sync::OnceCell (imported at line 38), the crate version of OnceLock. The field starts empty when the workspace is loaded.
  • get_or_init takes &self: it is interior mutability that can only ever go from empty to full once. The closure reads the user's config only on the first call.
  • The cell holds an Arc<Semaphore>, and the method returns .clone() of it. Each caller receives its own owning handle to the same semaphore, so permits are shared across every download task, and the handle can move into a 'static task.
  • The semaphore is tokio::sync::Semaphore; it was the io_semaphore: Option<Arc<Semaphore>> parameter you met in M07's spawn_blocking_with_io_permit.
Question: why not store a plain Semaphore in the cell and return &Semaphore?

The borrow would be tied to &self, the workspace. Download tasks are spawned onto tokio and must be 'static, so they cannot hold a borrow of the workspace. An Arc they own can go anywhere and keeps the semaphore alive as long as any task needs it.

Question: this field could use std::sync::OnceLock today. Why might it still be once_cell?

Its initializer cannot fail, so std's OnceLock::get_or_init would work. The neighbouring client and repodata_gateway fields need a fallible initializer, so the file already depends on once_cell, and keeping one type for all the lazy fields is consistent. A small cleanup PR could switch this field; that is the kind of change Level 3 prepares you to make.

The enum below describes a version-constraint expression tree. Implement matches(c: &Constraint, v: u32) -> bool (AtLeast(n) means v >= n, Below(n) means v < n, And/Or/Not as usual) and depth(c: &Constraint) -> usize (a leaf has depth 1; each And, Or or Not adds 1 to its deepest child). Then write a helper between(lo: u32, hi: u32) -> Constraint that builds And(AtLeast(lo), Below(hi)).

Hint

match c { Constraint::And(a, b) => matches(a, v) && matches(b, v), ... }: a is a &Box<Constraint>, which deref-coerces to &Constraint. For depth, 1 + depth(a).max(depth(b)).

Show solution 
enum Constraint {
    AtLeast(u32),
    Below(u32),
    And(Box<Constraint>, Box<Constraint>),
    Or(Box<Constraint>, Box<Constraint>),
    Not(Box<Constraint>),
}

fn matches(c: &Constraint, v: u32) -> bool {
    match c {
        Constraint::AtLeast(n) => v >= *n,
        Constraint::Below(n) => v < *n,
        Constraint::And(a, b) => matches(a, v) && matches(b, v),
        Constraint::Or(a, b) => matches(a, v) || matches(b, v),
        Constraint::Not(a) => !matches(a, v),
    }
}

fn depth(c: &Constraint) -> usize {
    match c {
        Constraint::AtLeast(_) | Constraint::Below(_) => 1,
        Constraint::And(a, b) | Constraint::Or(a, b) => 1 + depth(a).max(depth(b)),
        Constraint::Not(a) => 1 + depth(a),
    }
}

fn between(lo: u32, hi: u32) -> Constraint {
    Constraint::And(Box::new(Constraint::AtLeast(lo)), Box::new(Constraint::Below(hi)))
}

Like Pixi's PyprojectMetadataProvider, this checker's methods take &self but must record warnings. Complete Checker using the RefCell field and a Cell<u32> counter: new(), check(&self, name: &str) -> bool (increments checked; records "empty name" for an empty name and returns false; records "'{name}' has uppercase letters" for a name with any uppercase character but still returns true; otherwise returns true), warnings(&self) -> Vec<String> (a copy, in order), and checked(&self) -> u32.

Hint

self.checked.set(self.checked.get() + 1); self.warnings.borrow_mut().push(...) in one statement so the guard drops at once; self.warnings.borrow().clone() to return a copy.

Show solution 
use std::cell::{Cell, RefCell};

struct Checker {
    warnings: RefCell<Vec<String>>,
    checked: Cell<u32>,
}

impl Checker {
    fn new() -> Self {
        Checker { warnings: RefCell::new(Vec::new()), checked: Cell::new(0) }
    }

    fn check(&self, name: &str) -> bool {
        self.checked.set(self.checked.get() + 1);
        if name.is_empty() {
            self.warnings.borrow_mut().push("empty name".to_string());
            return false;
        }
        if name.chars().any(char::is_uppercase) {
            self.warnings.borrow_mut().push(format!("'{name}' has uppercase letters"));
        }
        true
    }

    fn warnings(&self) -> Vec<String> {
        self.warnings.borrow().clone()
    }

    fn checked(&self) -> u32 {
        self.checked.get()
    }
}

Write install_all(log: &Arc<Mutex<Vec<String>>>, packages: Vec<String>) that spawns one std::thread::spawn thread per package. Each thread pushes "installed {name}" onto the shared log. The function must join every thread before returning, so that when it returns, all entries are present and every clone of the Arc has been dropped. Then write sorted_log(log: &Arc<Mutex<Vec<String>>>) -> Vec<String> that returns a sorted copy (threads finish in any order).

Hint

Collect the JoinHandles in a Vec. In the loop: let log = Arc::clone(log); then thread::spawn(move || log.lock().unwrap().push(format!(...))). Afterwards for h in handles { h.join().unwrap(); }. For the sorted copy: let mut v = log.lock().unwrap().clone(); v.sort(); v.

Show solution 
use std::sync::{Arc, Mutex};
use std::thread;

fn install_all(log: &Arc<Mutex<Vec<String>>>, packages: Vec<String>) {
    let handles: Vec<_> = packages
        .into_iter()
        .map(|name| {
            let log = Arc::clone(log);
            thread::spawn(move || {
                log.lock().unwrap().push(format!("installed {name}"));
            })
        })
        .collect();
    for h in handles {
        h.join().unwrap();
    }
}

fn sorted_log(log: &Arc<Mutex<Vec<String>>>) -> Vec<String> {
    let mut v = log.lock().unwrap().clone();
    v.sort();
    v
}

Write normalize(name: &str) -> Cow<'_, str> that lowercases a package name and replaces _ and . with -. If the name is already normalized (no uppercase, no _, no .), return it borrowed, with no allocation. Then write count_allocations(names: &[&str]) -> usize returning how many names needed an owned result.

Hint

Test first: if name.chars().any(|c| c.is_uppercase() || c == '_' || c == '.'). Owned case: Cow::Owned(name.to_lowercase().replace(['_', '.'], "-")). For counting, .filter(|n| matches!(normalize(n), Cow::Owned(_))).count().

Show solution 
use std::borrow::Cow;

fn normalize(name: &str) -> Cow<'_, str> {
    if name.chars().any(|c| c.is_uppercase() || c == '_' || c == '.') {
        Cow::Owned(name.to_lowercase().replace(['_', '.'], "-"))
    } else {
        Cow::Borrowed(name)
    }
}

fn count_allocations(names: &[&str]) -> usize {
    names.iter().filter(|n| matches!(normalize(n), Cow::Owned(_))).count()
}

Model Pixi's concurrent_downloads_semaphore with std types. Workspace has a max_downloads setting, an empty OnceLock<Arc<Budget>>, and a Cell<u32> that counts how many times a budget was created. Write Workspace::new(max_downloads: usize) and budget(&self) -> Arc<Budget>: the first call creates Budget { permits: max_downloads } (incrementing created), and every call returns a clone of the same Arc.

Hint

OnceLock::new() and Cell::new(0) in new. In budget: self.budget.get_or_init(|| { self.created.set(...); Arc::new(Budget { permits: self.max_downloads }) }).clone(). The .clone() at the end is the Arc clone.

Show solution 
use std::cell::Cell;
use std::sync::{Arc, OnceLock};

struct Budget {
    permits: usize,
}

struct Workspace {
    max_downloads: usize,
    budget: OnceLock<Arc<Budget>>,
    created: Cell<u32>,
}

impl Workspace {
    fn new(max_downloads: usize) -> Self {
        Workspace { max_downloads, budget: OnceLock::new(), created: Cell::new(0) }
    }

    fn budget(&self) -> Arc<Budget> {
        self.budget
            .get_or_init(|| {
                self.created.set(self.created.get() + 1);
                Arc::new(Budget { permits: self.max_downloads })
            })
            .clone()
    }
}

Quiz

Recap

  • Box<T>: one owner, value on the heap. For recursive types, dyn Trait, and large rare enum variants.
  • Rc<T>: shared ownership on one thread. Clone bumps a count; the value drops with the last owner; read-only; cycles leak unless broken with Weak.
  • Cell/RefCell: mutation through &self. RefCell checks borrows at run time and panics on a violation.
  • Send/Sync: may move to / be shared between threads. The compiler derives them and reports violations as E0277.
  • Arc<T> is the thread-safe Rc; Mutex/RwLock are the thread-safe RefCell. parking_lot's locks do not poison, so no unwrap().
  • thread::scope lets threads borrow locals, because they are joined before it returns.
  • Cow<'_, str>: borrowed in the common case, owned when changed.
  • LazyLock and OnceLock compute once on first use; once_cell is the older crate Pixi still uses where it needs a fallible initializer.
  • Pixi shares long-lived services as Arc<T> because concurrent tasks must own cheap handles, and adds a lock inside only where data changes.
