Option, Result & ?

Rust has no None that can sneak into any variable, and no exceptions that can fly out of any call. Absence is a value of type Option<T> and failure is a value of type Result<T, E>, and the type checker makes you deal with both. This module teaches you to handle them fluently, to propagate errors with ?, and to design the error types you will see on every function in Pixi.

None and exceptions, as values

In Python, two things can happen to any call that the signature does not tell you about. It can return None, and it can raise.

config = {"channels": ["conda-forge"]}
platform = config.get("platform")      # None: the key is missing
print(platform.upper())                # AttributeError: 'NoneType' object has no attribute 'upper'

port = int("80a")                      # ValueError: invalid literal for int() with base 10: '80a'

A type hint like Optional[str] documents the first case, but nothing forces the caller to check, and a type checker is optional. The second case is not in the signature at all: you learn which exceptions int() raises by reading the docs or by watching it fail in production.

Rust uses two ordinary enums from the standard library instead. You already know enums with data from M02; these are the same thing.

enum Option<T> {
    None,      // there is no value
    Some(T),   // there is a value, of type T
}

enum Result<T, E> {
    Ok(T),     // it worked, and here is the value
    Err(E),    // it failed, and here is why
}

The <T> makes them generic: Option<u16> is "maybe a u16", Result<u16, ParseIntError> is "a u16, or a parse error" (M06 covers generics properly). They are so common that Some, None, Ok, and Err are in scope everywhere without a use.

The difference from Python is that the possibility of absence or failure is part of the type. A function that returns Option<&String> cannot be used as if it returned a &String. Try it.

This is E0308, "mismatched types": "expected &String, found Option<&String>". first() returns None for an empty vector, so its result is an Option. The compiler will not let you forget that, which is exactly the Python AttributeError above, caught at compile time. The help: line suggests one fix, .expect(...); this module teaches you all of them and when each is right.

Run this to see what these values look like when printed with {:?}.

Note the last line: the error is a value, ParseIntError { kind: InvalidDigit }, that you can store, return, inspect, and print. Nothing was raised; nothing unwound the stack.

Why not just have null? Its inventor, Tony Hoare, called it his "billion-dollar mistake": when every reference might be null, every use is a possible crash. In Rust, a &String is always a valid string. Only an Option<&String> might be absent, and you can see which is which. (It costs nothing at run time: Option<&T> is the same size as &T, with None stored as the null pointer.)

Remember: Option<T> is Some(T) or None; Result<T, E> is Ok(T) or Err(E). They are plain enums, and the type system makes you handle both variants before you get at the T.

Getting the value out: match, if let, let-else, while let

Because Option and Result are enums, the basic tool is match, and it must be exhaustive (M02): you cannot forget the None or Err arm.

Patterns can match a literal inside Some (Some("linux-64")) as well as bind whatever is there (Some(other)). Arms are tried top to bottom.

if let: when only one case matters

When you only care about one variant, a full match is noise. if let runs a block only when the pattern matches, with an optional else.

if let Some(platform) = config.platform {
    println!("solving for {platform}");
} else {
    println!("solving for the current platform");
}

Edition 2024 adds let chains: you can combine if let with other conditions using &&. You will see this more and more in Pixi.

if let Some(version) = python_version && version.starts_with("3.") {
    println!("Python 3: {version}");
}

let-else: bind or bail out

The most common shape in real code is "get the value, or return early". let-else writes that directly: the pattern either matches and binds a variable for the rest of the function, or the else block runs, and that block must leave the function (with return, break, continue, or a panic).

def channel_name(spec: str) -> str:
    if "::" not in spec:
        return "default"
    channel, _ = spec.split("::", 1)
    return channel
fn channel_name(spec: &str) -> &str {
    let Some((channel, _)) = spec.split_once("::") else {
        return "default";
    };
    channel
}

The happy path stays at the left margin, with no nesting. Pixi uses this everywhere; you will see two examples in the Reading Pixi section. If the else block does not diverge, the compiler stops you.

E0308 again, with the note "else clause of let...else does not diverge" and help: try adding a diverging expression, such as return or panic!(..). If the pattern did not match, there is no major to use on the next line, so the else block must not continue into it. Adding return 0; after the println! fixes it.

while let: loop while something is there

while let repeats as long as the pattern matches. The classic use is draining a stack, where pop() returns Option<T>.

Remember: match when several cases matter; if let for one case; let-else to bind or return early (its else must diverge); while let to loop until None.

Result instead of exceptions

Here is the same parse in both languages. Read them side by side.

def parse_port(text: str) -> int:
    try:
        port = int(text)
    except ValueError as e:
        raise ValueError(f"bad port {text!r}: {e}")
    if not 0 < port < 65536:
        raise ValueError(f"port {port} out of range")
    return port
fn parse_port(text: &str) -> Result<u16, String> {
    let port: u16 = match text.parse() {
        Ok(p) => p,
        Err(e) => return Err(format!("bad port {text:?}: {e}")),
    };
    if port == 0 {
        return Err(String::from("port 0 is reserved"));
    }
    Ok(port)
}

The Rust signature, -> Result<u16, String>, tells every caller "this can fail, and the failure is described by a String". Parsing into u16 rejects anything above 65535 for free, because the type itself has that range. And the error is returned: there is no hidden second exit from the function.

What does that buy you? In Python, any line might raise, so reasoning about what state an object is in after a failure is hard. In Rust, a function can only fail at the places that return an Err, and you can see them. When you read Pixi, every fallible step is marked, usually with the ? you will learn shortly.

A Result is not the number inside it. You must decide what to do with the error before you can do arithmetic.

E0369, "cannot add {integer} to Result<u16, ParseIntError>". The left side's type names the problem: port is a Result. Handle it first (with match, ?, or a combinator) to get the u16 out.

Ignoring a Result entirely is allowed, but the compiler warns, because Result is marked #[must_use]. Run this and look at the compiler output.

The warning is "unused Result that must be used" with "this Result may be an Err variant, which should be handled". Pixi builds with -D warnings in CI, so in Pixi this would be an error. If you really mean to ignore a failure, say so with let _ = save("");, and leave a comment explaining why.

Ok(()) is how a function that returns nothing useful says "it worked". () is the unit type, Rust's equivalent of a function returning None in Python.

Remember: a fallible function returns Result<T, E>, and the error is an ordinary return value. You cannot use the T until you have handled the E, and you cannot silently ignore the whole thing.

unwrap, expect, and the defaults

unwrap() gives you the value inside Some or Ok, and panics on None or Err. A panic stops the current thread with an error message and a non-zero exit. It is closer to Python's assert than to an exception: it means "this is a bug", not "this can happen". expect("message") is the same with a message you choose.

The first port prints. The second panics, and the message on stderr reads a line that starts thread 'main' and names the location, src/main.rs:4:38, then ports in this list are hard-coded and valid: ParseIntError { kind: InvalidDigit }. You get the file and line, your message, and the error's debug form. That is why expect beats unwrap: the message records why you believed this could not fail, which is what the person reading the crash report needs.

When unwrap and expect are acceptable

  • In tests. A panic fails the test with a clear message, which is what you want.
  • When an invariant guarantees success and you can say why in the expect message. Pixi does this: adding one day to a valid date cannot overflow, so (crates/pixi_spec/src/exclude_newer.rs):
let next_midnight = date
    .checked_add_days(Days::new(1))
    .expect("valid exclude-newer date should have a following day")
    .and_time(NaiveTime::MIN)
    .and_utc();
  • In examples and throwaway prototypes, where error handling would hide the point.

Not acceptable: anything that depends on user input, files, the network, environment variables, or the contents of a pixi.toml. Those fail for reasons outside your program, and a panic gives the user a crash instead of an error message. In Pixi review, an unwrap() on user data is a change request.

Defaults instead of panics

Often the right answer to "what if it is missing?" is a default value. These methods never panic:

MethodGives youUse when
unwrap_or(v)the value, or vthe default is a cheap constant
unwrap_or_else(|| f())the value, or the result of calling fthe default is expensive (allocates, does I/O); f runs only when needed
unwrap_or_default()the value, or the type's Default (0, "", empty Vec)"empty" is the natural default

The |e| { ... } is a closure, an inline anonymous function, like Python's lambda but allowed to contain statements. For Result::unwrap_or_else, the closure receives the error. Closures get a full module in M09; for now, read |x| expr as lambda x: expr.

unwrap_or(expensive()) calls expensive() every time, even when the value is present, because arguments are evaluated before the call. Clippy's or_fun_call lint catches this; switch to unwrap_or_else(|| expensive()).

Remember: unwrap/expect mean "a failure here is a bug". Use them in tests and for real invariants, with an expect message that says why it cannot fail. For defaults, use unwrap_or, unwrap_or_else, or unwrap_or_default.

Combinators: transform without unpacking

A lot of code has the shape "if there is a value, do something to it; otherwise pass the absence along". Writing a match for each step gets long. Combinators are methods on Option and Result that do one such step each, so you can chain them.

MethodOnDoes
map(f)bothtransform the inside value: Some(x) → Some(f(x)), Ok(x) → Ok(f(x)); absence or error passes through
and_then(f)bothlike map, but f itself returns an Option/Result, so the step can fail too
filter(p)Optionkeep Some(x) only if p(&x) is true
ok_or(e) / ok_or_else(f)Optionturn Option into Result: None becomes Err(e)
ok()Resultturn Result into Option, discarding the error
map_err(f)Resulttransform the error, leave Ok alone
is_some(), is_none(), is_ok(), is_err()bothtest which variant, as a bool
as_deref()Option&Option<String> → Option<&str>, for borrowing what is inside

The difference between map and and_then is the one people trip on. If the step cannot fail, use map. If it can (it returns Option or Result), use and_then, otherwise you end up with Some(Some(x)).

Read major_of top to bottom as a pipeline: split at == (maybe), keep the version part, take the text before the first dot (maybe), parse it (maybe). Any None short-circuits the rest. Note .parse().ok(): parse returns a Result, and .ok() turns it into an Option so it fits the chain.

Pixi strips the internal direct+ prefix from a URL with exactly this style (crates/pixi_install_pypi/src/utils.rs):

/// Strip of the `direct` scheme from the url if it is there
pub fn strip_direct_scheme(url: &Url) -> Cow<'_, Url> {
    url.as_ref()
        .strip_prefix("direct+")
        .and_then(|str| Url::from_str(str).ok())
        .map(Cow::Owned)
        .unwrap_or(Cow::Borrowed(url))
}

strip_prefix returns Option<&str> (None if there is no prefix). and_then parses what remains, and .ok() turns a parse failure into None. map(Cow::Owned) wraps a newly parsed URL; unwrap_or falls back to borrowing the original. Cow ("clone on write") is either borrowed or owned data; it is covered in M08. Passing a variant name like Cow::Owned as the function is a common shorthand for |u| Cow::Owned(u).

Combinator chains are idiomatic, but not mandatory. If a chain needs a comment to be understood, a match or a let-else is often clearer. Pixi mixes both. Clippy will suggest the combinator form for simple cases (manual_map, option_map_unit_fn), so you will see those transformations in review.

Remember: map for steps that cannot fail, and_then for steps that can, ok_or to turn absence into an error, ok() to turn an error into absence, map_err to change the error.

The ? operator

Most of the time, a function that hits an error cannot fix it and should hand it to its caller. Writing that with match is repetitive:

let text = match std::fs::read_to_string(path) {
    Ok(t) => t,
    Err(e) => return Err(e.into()),
};

The ? operator is that whole match in one character:

let text = std::fs::read_to_string(path)?;

Precisely, expr? on a Result means: if expr is Ok(v), the expression's value is v; if it is Err(e), return Err(From::from(e)) from the current function right now. That From::from step converts the error into the function's own error type, if a conversion exists; you will use it in the next section.

def read_threads(text: str) -> int:
    # int() may raise; the exception just
    # propagates, invisibly, to our caller.
    n = int(text.strip())
    return n * 2
use std::num::ParseIntError;

fn read_threads(text: &str) -> Result<u32, ParseIntError> {
    // `?` propagates, visibly, to our caller.
    let n: u32 = text.trim().parse()?;
    Ok(n * 2)
}

This is the closest Rust gets to Python's exception propagation, with one big difference: the ? marks every place where the function can return early. When you read Pixi, scan for ? to see every failure point.

? on Option

? also works on an Option inside a function that returns Option: None returns None early. This often reads better than a long and_then chain.

Where ? is not allowed

? needs somewhere to return the error to, so the enclosing function must return a compatible type. Using it in a main that returns () is the classic mistake.

E0277: "the ? operator can only be used in a function that returns Result or Option (or another type that implements FromResidual)". The label sits on the ?, and a second span marks the function: "this function should return Result or Option to accept ?". The fix is to change the return type; for main, see Box<dyn Error> below. Mixing the two also fails: ? on an Option inside a function returning Result is E0277 too. Convert first with .ok_or(...)?.

Remember: x? = "unwrap Ok/Some, or return the Err (converted with From) or None from this function now". The function's return type must be a Result or Option to match.

Custom error types

Result<T, String> is fine for a quick script, but a String error has a problem: callers cannot react differently to different failures without parsing text. In Python you would define exception classes. In Rust you define an error enum, one variant per kind of failure, each carrying the data needed to explain it.

A proper error type does three things:

  1. Implements Display, so {} prints a message for humans.
  2. Implements std::error::Error, the standard trait every error type shares. Its source() method can return the lower-level error that caused this one, giving a chain like Python's raise ... from e.
  3. Implements From<LowerLevelError> for each error it wraps, so ? converts automatically.
class PinError(Exception):
    pass

class EmptySpec(PinError):
    pass

class BadVersion(PinError):
    def __init__(self, text, cause):
        super().__init__(f"bad version {text!r}")
        self.__cause__ = cause
#[derive(Debug)]
enum PinError {
    EmptySpec,
    MissingVersion(String),
    BadVersion(ParseIntError),
}
// plus: impl Display, impl Error, impl From

Here is a complete one. Read it in order, then run it.

The pieces, one at a time:

  • #[derive(Debug)] is required: the Error trait needs both Debug and Display.
  • impl fmt::Display writes one message per variant. Messages are lowercase with no trailing period, by Rust convention, because they are often embedded in longer messages.
  • impl Error needs no methods at all; source has a default that returns None. Override it when a variant wraps a cause, as BadVersion does.
  • impl From<ParseIntError> is what makes version.parse()? compile in a function returning Result<_, PinError>: the ? calls PinError::from(e).
  • ok_or_else(|| ...)? converts the Option from split_once into a Result with a specific error, then propagates it.

Delete the From impl and see what ? says without it.

E0277: "? couldn't convert the error to PinError", with "the trait From<ParseIntError> is not implemented for PinError". The note explains the rule: "the question mark operation (?) implicitly performs a conversion on the error value using the From trait". Two fixes: add the From impl, or convert explicitly at that call with .map_err(PinError::BadVersion)?. The explicit form is useful when the same lower-level error should become different variants in different places. (The cell names the target type with parse::<u32>() on purpose. With let major: u32 = version.parse()?; the compiler tries to make parse produce a PinError directly and reports the less helpful E0271, "type mismatch resolving". When an error around ? is confusing, pinning down the types with ::<T> (the "turbofish") or a type annotation often makes it clearer.)

Remember: a library-quality error is an enum with Debug, Display, Error (with source for wrapped causes), and a From impl per wrapped error so that ? converts automatically.

Box<dyn Error> and errors in main

Sometimes you do not want a precise error type. In main, in a small tool, or in a test helper, you just want "any error, with a message". Rust's answer is Box<dyn Error>: a heap-allocated value of some type that implements Error. dyn Error is a trait object, a value known only by the trait it implements (M06 explains it; Box is M08). For now, the useful fact is that ? converts any error type into Box<dyn Error>, and so do String and &str via .into().

main itself may return Result<(), E> for any E that implements Debug. If it returns Err, Rust prints Error: followed by the error's Debug form, and the process exits with code 1.

The first call prints 8. The second returns an error, ? in main passes it up, and the runtime prints Error: "jobs must be at least 1" (the quotes are because it uses Debug) and exits with status 1. Two different error types, ParseIntError and a string message, flowed through one Box<dyn Error> return type with no conversion code.

Which one should I use?

SituationError typeWhy
A library function others will callA custom enumCallers can match on the variant and react
main, a CLI command, a script, a test helperBox<dyn Error> (or miette::Result in Pixi)You only report the error; precise types add nothing
A quick private helperStringAcceptable while prototyping; upgrade when callers need to branch

Remember: Box<dyn Error> is "any error". ? converts every error into it, and "text".into() makes one from a message. Use it at the top of a program; use custom enums in library code.

What Pixi uses: thiserror and miette

Writing Display, Error, and From by hand for every error enum is mechanical. Pixi, like most of the Rust ecosystem, uses two crates to do it. You will learn them properly in Level 2; here you only need to read them.

  • thiserror is a derive macro: you annotate an enum and it writes the Display, Error, and From impls for you. The generated code is the same code you wrote in the previous section.
  • miette adds a Diagnostic trait for rich, user-facing error reports (help text, error codes, source snippets with underlined spans, like the Rust compiler's own messages). Pixi's CLI commands return miette::Result<T>, the application-level "any error" type, playing the role Box<dyn Error> played above.

Here is part of a real Pixi error enum (crates/pypi_modifiers/src/pypi_tags.rs, trimmed):

#[derive(Debug, thiserror::Error, Diagnostic)]
#[error("failed to determine pypi tags")]
pub enum PyPITagError {
    #[error("failed to determine the python wheel tags for the target platform")]
    FailedToDetermineWheelTags(#[from] uv_platform_tags::TagsError),

    #[error("failed to determine pypi tag for platform: {0}")]
    FailedToDeterminePlatformTags(Platform),
    // ...
    #[error("failed to get major and minor version from '{0}' version: '{1}'")]
    FailedToGetMajorMinorVersion(String, String),
    // ...
    #[error(transparent)]
    ParseMatchSpecError(#[from] rattler_conda_types::ParseMatchSpecError),
}

Read each attribute as the hand-written code it replaces:

AttributeGenerates
#[derive(thiserror::Error)]impl std::error::Error for PyPITagError
#[error("...: {0}")] on a variantthat variant's arm in impl Display; {0}, {1} are the tuple fields
#[from] on a fieldimpl From<TagsError> for PyPITagError, and source() returning that field
#[error(transparent)]Display and source forwarded straight to the wrapped error
Diagnostic (from miette)the hooks miette uses for codes, help text, and labels (all defaults here)

So the FailedToGetMajorMinorVersion arm is equivalent to this, which you could now write yourself:

PyPITagError::FailedToGetMajorMinorVersion(a, b) => {
    write!(f, "failed to get major and minor version from '{a}' version: '{b}'")
}

The Playground has thiserror, so you can try the derive. This cell is the error enum from the previous section, written with the derive instead of by hand.

In Pixi's CLI code you will see .into_diagnostic()? on calls to other crates, for example compiling a user-supplied regex in pixi exec (crates/pixi_cli/src/exec.rs):

if let Some(ref regex) = regex {
    let regex = regex::Regex::new(regex).into_diagnostic()?;
    packages_to_output.retain(|package| regex.is_match(package.name.as_normalized()));
}

into_diagnostic() is a miette helper that wraps any std::error::Error as a miette report, so ? can return it from a function whose type is miette::Result. It plays the same role as the automatic conversion into Box<dyn Error>.

Remember: thiserror writes the Display, Error, and From impls from attributes; #[from] is what makes ? convert. miette is Pixi's user-facing report type, and into_diagnostic()? is how foreign errors enter it.

Reading Pixi

A pipeline of fallible steps

Pixi computes the Python wheel tags for a platform (the cp313-manylinux_2_28_x86_64-style strings that decide which PyPI wheels are installable) in crates/pypi_modifiers/src/pypi_tags.rs:

/// Get the python version and implementation name for the specified platform.
pub fn get_pypi_tags(
    platform: &PixiPlatform,
    python_record: &PackageRecord,
) -> Result<uv_platform_tags::Tags, PyPITagError> {
    let platform = get_platform_tags(platform)?;
    let python_version = get_python_version(python_record)?;
    let implementation_name = get_implementation_name(python_record)?;
    let gil_disabled = gil_disabled(python_record)?;
    create_tags(platform, python_version, implementation_name, gil_disabled)
}

And one of the steps it calls (same file):

fn get_python_version(python_record: &PackageRecord) -> Result<(u8, u8), PyPITagError> {
    let Some(python_version) = python_record.version.as_major_minor() else {
        return Err(PyPITagError::FailedToGetMajorMinorVersion(
            python_record.name.as_normalized().to_string(),
            python_record.version.to_string(),
        ));
    };
    Ok((python_version.0 as u8, python_version.1 as u8))
}
  • Both functions borrow their inputs (&PixiPlatform, &PackageRecord, from M03) and return Result<_, PyPITagError>: one error enum for the whole module.
  • In get_pypi_tags, four lines end in ?. Each is a step that can fail; the first failure returns from the function. Because every step already returns PyPITagError, the From conversion is the identity.
  • The last line has no ? and no Ok(...): create_tags already returns a Result<Tags, PyPITagError>, so its result is returned as is.
  • Shadowing: let platform = get_platform_tags(platform)?; replaces the &PixiPlatform parameter with the computed tag platform under the same name (shadowing, M02).
  • In get_python_version, as_major_minor() returns an Option. The let-else turns None into a specific, descriptive error carrying the package name and version as owned Strings, built with to_string() because the error must outlive the borrowed record.
  • python_version.0 as u8: tuple field access and a numeric cast (M02). The result is wrapped in Ok.

Option and Result together, with early returns

From crates/pixi_manifest/src/platform/host.rs, which applies a user's CONDA_OVERRIDE_ARCHSPEC environment variable to the detected virtual packages:

fn apply_archspec_override(packages: &mut Vec<GenericVirtualPackage>) {
    if std::env::var_os(Archspec::DEFAULT_ENV_NAME).is_none() {
        return;
    }
    let overridden = match Archspec::detect_with_fallback(&Override::DefaultEnvVar, || Ok(None)) {
        Ok(overridden) => overridden,
        Err(error) => {
            tracing::warn!("Ignoring {}: {error}", Archspec::DEFAULT_ENV_NAME);
            return;
        }
    };

    // Set empty: no `__archspec` at all.
    let Some(overridden) = overridden else {
        packages.retain(|p| p.name.as_normalized() != "__archspec");
        return;
    };
    // ...
    let overridden = GenericVirtualPackage::from(overridden);
    match packages
        .iter_mut()
        .find(|p| p.name.as_normalized() == "__archspec")
    {
        Some(existing) => *existing = overridden,
        None => packages.push(overridden),
    }
}
  • var_os(...) returns Option<OsString>; .is_none() asks "is the variable unset?" and returns early if so.
  • detect_with_fallback returns Result<Option<Archspec>, _>: it can fail, and if it succeeds the value may still be absent (the variable was set to an empty string). The match takes the Ok value or logs a warning and returns. This function returns (), so it cannot use ?; a bad override is reported and ignored rather than fatal.
  • The let-else handles the None inside: remove any __archspec entry and return. After it, overridden is the plain value.
  • The final match on find's Option<&mut GenericVirtualPackage> either overwrites the existing entry through the mutable reference (*existing = overridden, M03) or pushes a new one.
Why does get_python_version call .to_string() twice instead of storing &str in the error?

The error is returned to callers who no longer have the record borrowed, so it must own its data. PyPITagError's variants hold String, so the error is self-contained and can be passed anywhere (it has no lifetime parameter). Owned data in error types is the normal choice.

Could apply_archspec_override use ? on the detect_with_fallback result?

Not as written: it returns (), so ? would be E0277. And it should not: the design choice is that a malformed override is a warning, not a failure. To use ?, the function would need to return a Result, and every caller would then have to decide what to do with that error.

What does get_pypi_tags return if both get_platform_tags and get_python_version would fail?

Only the first error. ? returns at the first failure, so get_python_version is never called. If you wanted to report every problem, you would collect the errors instead of using ?.

Write parse_port(text: &str) -> Option<u16>. Trim surrounding whitespace, parse the rest as a u16, and return None if it is not a number, is out of range, or is 0.

Hint

Show solution 
fn parse_port(text: &str) -> Option<u16> {

fn parse_major_minor(text: &str) -> Result<(u32, u32), String> {
    let bad = || format!("expected MAJOR.MINOR, got `{text}`");
    let (major, minor) = text.split_once('.').ok_or_else(bad)?;
    let major = major.parse::<u32>().map_err(|_| bad())?;
    let minor = minor.parse::<u32>().map_err(|_| bad())?;
    Ok((major, minor))
}

use std::num::ParseIntError;

#[derive(Debug, PartialEq)]
enum PinError {
    MissingVersion(String),
    BadVersion(ParseIntError),
}

impl From<ParseIntError> for PinError {
    fn from(e: ParseIntError) -> Self {
        PinError::BadVersion(e)
    }
}

fn parse_pin(spec: &str) -> Result<(&str, u32), PinError> {
    let (name, version) = spec
        .split_once("==")
        .ok_or_else(|| PinError::MissingVersion(spec.to_string()))?;
    Ok((name, version.parse()?))
}

fn highest_major(specs: &[&str]) -> Result<Option<u32>, PinError> {
    let mut best: Option<u32> = None;
    for spec in specs {
        let (_, major) = parse_pin(spec)?;
        best = match best {
            Some(b) if b >= major => Some(b),
            _ => Some(major),
        };
    }
    Ok(best)
}

Quiz

Recap

  • Option<T> (Some/None) and Result<T, E> (Ok/Err) are ordinary enums that put absence and failure into the type.
  • Unpack with match, if let (one case), let-else (bind or return early; the else must diverge), and while let.
  • unwrap/expect panic; use them in tests and for real invariants, with an expect message saying why. Prefer unwrap_or, unwrap_or_else, unwrap_or_default for defaults.
  • Combinators: map (cannot fail), and_then (can fail), ok_or, ok(), map_err, filter.
  • ? unwraps or returns early, converting the error with From. It works on Option in functions returning Option.
  • Library errors are enums with Debug, Display, Error, and From. Application code can use Box<dyn Error>; Pixi uses miette::Result.
  • thiserror generates the error impls from #[error(...)] and #[from]; into_diagnostic()? brings foreign errors into miette.
