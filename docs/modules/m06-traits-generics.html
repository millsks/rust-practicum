Traits & Generics

Traits are how Rust says "any type that can do this." They play the part of Python's protocols, abstract base classes, and dunder methods all at once, and the compiler checks every one of them before your program runs. Pixi is built on them: its platform and environment names parse and print through FromStr and Display, its dependency specs convert with From, and its environments, solve groups, and feature collections share dozens of methods through one trait. By the end of this module you can read all of that.

Defining and implementing a trait

In Python you describe "things that can do X" in one of three ways: duck typing (just call the method and hope), an abstract base class (abc.ABC with @abstractmethod), or a typing.Protocol that a type checker verifies. Rust has one mechanism, the trait: a named set of method signatures that a type can promise to provide.

from typing import Protocol

class Describe(Protocol):
    def describe(self) -> str: ...

class Package:
    def __init__(self, name: str, version: str):
        self.name, self.version = name, version
    def describe(self) -> str:
        return f"{self.name} {self.version}"
trait Describe {
    fn describe(&self) -> String;
}

struct Package {
    name: String,
    version: String,
}

impl Describe for Package {
    fn describe(&self) -> String {
        format!("{} {}", self.name, self.version)
    }
}

The trait block declares what an implementer must provide: here one method that borrows self and returns a String. The impl Describe for Package block is the promise, and it is checked: leave out a method, or get its signature wrong, and the program does not compile. Compare that with a Python protocol, where nothing stops a class from forgetting a method until a type checker or a test notices.

Two differences from Python classes matter immediately:

  • Implementations are separate from the type. A struct's fields live in the struct; its inherent methods live in impl Package { ... } (M02); each trait it implements gets its own impl Trait for Package { ... } block, which can even live in a different file. There is no inheritance between structs. Traits are how Rust shares behavior.
  • You can implement your trait for types you did not write. impl Describe for i32 or impl Describe for Vec<String> are both fine. The orphan rule at the end of this module says exactly when that is allowed.

A trait must be in scope to call its methods

Here is a rule with no Python equivalent, and one you will meet on your first day in Pixi. A trait's methods can only be called where the trait itself is in scope, either because it was defined in the same module or because you imported it with use. The type implementing it is not enough:

E0599: no method named `describe` found for struct `Package` in the current scope. The help: lines explain it ("items from traits can only be used if the trait is in scope") and offer the fix, use crate::model::Describe;. The rule exists so that adding a trait somewhere in a large program cannot silently change which method a call in your file resolves to: only the traits you import can contribute methods.

When a Pixi call such as environment.channels() fails with E0599, the method almost always comes from a trait you have not imported. The CLI's tree command starts with use pixi_manifest::{FeaturesExt, HasWorkspaceManifest as _, PixiPlatform, PixiPlatformName}; (crates/pixi_cli/src/tree.rs#L20). as _ imports a trait only for its methods, without binding its name, which avoids name clashes.

Remember: a trait is a checked list of methods. impl Trait for Type provides them. Calling a trait method requires the trait in scope, so E0599 on a method you know exists means "add a use."

Default methods

A trait can provide a body for some of its methods. Implementers get those default methods for free and may override them. Defaults can call the trait's required methods, which is how a trait with one or two required methods can offer dozens of useful ones. Python's closest equivalent is a mixin class or a non-abstract method on an ABC.

Task implements only name and inherits both defaults. Package overrides kind, and the default describe calls the overridden version, just as a method on a Python base class calls an overridden method on self.

You have already used the most famous example. The Iterator trait has exactly one required method, next, and over seventy default methods: map, filter, collect, sum, and every other adapter and consumer from M05. Implement next for your own type and all of them work on it; you will do that later in this module.

Remember: required methods have only a signature; default methods have a body that may call the required ones. Implementers can override defaults.

Generic functions and structs

In Python you write one largest(items) and it works on any list whose items support >; if they do not, you find out with a TypeError at run time. Type hints can say so with a TypeVar bound to a protocol, but nothing enforces it when the program runs. Rust's generics are the enforced version: a type parameter in angle brackets, such as <T>, stands for "some type, chosen by the caller."

The catch is that inside the function you can only do with a T what you have said every T can do. Say nothing, and you can do almost nothing:

E0369: binary operation `>` cannot be applied to type `&T`. The compiler checks the generic function once, for every possible T, and some types cannot be compared. The help: line says what to promise: "consider restricting type parameter T with trait PartialOrd." PartialOrd is the trait behind < and >. Adding it, written <T: PartialOrd>, is called a trait bound, the subject of the next section.

One function works for integers, floats, and strings, and returns None for an empty slice instead of panicking (first()? is M04's ? on an Option). The last call uses the turbofish to name T, because an empty slice gives the compiler nothing to infer it from.

How generics are compiled: monomorphization

Generic code has no run-time cost. For each concrete type a generic function is used with, the compiler generates a separate copy specialized for that type: largest::<i32>, largest::<f64>, largest::<&str>. This is called monomorphization. Each copy is as fast as one written by hand for that type. The price is compile time and binary size, one reason a large Rust project like Pixi takes minutes to build.

Generic structs and impl blocks

Structs and enums take type parameters too. You have used two already: Option<T> and Vec<T>. Methods are written in impl<T> Name<T> { ... }: the first <T> declares the parameter, the second uses it. An impl block can also be written for one specific type, which adds methods only to that version.

Remember: <T> declares a type parameter; inside, you can only use what the bounds promise. Generics are monomorphized: one fast copy per concrete type. impl<T> S<T> adds methods for every T; impl S<u32> for one.

Trait bounds and where clauses

A trait bound is a requirement on a type parameter: T: PartialOrd means "only types that implement PartialOrd." Bounds work in both directions. Inside the function they are what let you call > or .to_string(); at the call site the compiler checks that the caller's type meets them, and rejects the call otherwise.

Combine bounds with +. When the list gets long, move it into a where clause after the signature. The two forms mean the same thing; where is easier to read and is what Pixi and rustfmt favor for anything non-trivial.

use std::fmt::{Debug, Display};
use std::hash::Hash;

// Inline bounds
fn report<T: Display + Clone>(item: &T) -> String { format!("{item}") }

// The same with a where clause, plus a second parameter
fn index_by<K, V>(items: &[V], key: impl Fn(&V) -> K) -> std::collections::HashMap<K, Vec<V>>
where
    K: Hash + Eq,
    V: Clone + Debug,
{
    // ...
    todo!()
}

Bounds can also sit on an impl block, which adds methods only when the type parameter qualifies. That is how a generic wrapper can be printable only when its contents are. The standard library uses the same idea on single methods: sort on a slice carries the bound where T: Ord, so Vec<String> has it and Vec<f64> does not (M05's E0277).

Notice that count_distinct collects references (&T) into the set. That needs &T: Ord, and the standard library provides it: whenever T: Ord, so is &T, by comparing what the references point at.

A Python habit to drop: adding bounds "just in case." Each bound is a requirement every caller must meet. Ask for exactly what the body uses, and nothing more; the compiler tells you when something is missing, with E0369, E0599, or E0277 and a help: line naming the trait.

Remember: T: A + B requires both traits. where clauses say the same thing more readably. Bounds on an impl block make its methods conditional.

impl Trait in argument and return position

Writing out a type parameter and its bound is verbose when the parameter is used once. Rust offers a shorthand, impl Trait, which means "some type that implements this trait." Its meaning depends on where you put it.

In argument position: shorthand for a generic

fn new(name: impl Into<String>) means exactly fn new<S: Into<String>>(name: S). The caller picks the type. You lose only the ability to name it, for example in a turbofish.

Pixi uses this for friendly constructors. NewEnvironment::new takes name: impl Into<String> and calls name.into(), so callers can pass a &str or a String without converting first (crates/pixi_manifest/src/environment.rs#L168-L175). Into is covered in the conversions section below.

In return position: "I return one type, and I am not telling you which"

Returning impl Trait is different: the function picks the type, and callers only know the trait. It is essential for iterators. The real type of v.iter().filter(...).map(...) is something like Map<Filter<Iter<'_, String>, {closure}>, {closure}>, and closure types cannot even be written down. So you return impl Iterator<Item = ...>:

The returned iterator is still lazy and still has every adapter. (The &'static str is a lifetime annotation, which M07 explains; read it as "string literals.")

The rule to remember: return-position impl Trait stands for one concrete type. A function cannot return one iterator type in one branch and another in a different branch:

E0308: `if` and `else` have incompatible types: one branch is a Chain<...>, the other an array::IntoIter<...>. Both implement Iterator, but impl Iterator must be a single type. The compiler suggests one fix, returning Box<dyn Iterator<Item = &'static str>> (next section). Another is a two-variant enum that is an iterator whenever both variants are, which is what the itertools crate's Either type is, and exactly what Pixi does in Reading Pixi.

In edition 2024, a return-position impl Trait automatically captures every lifetime in scope, so fn f(v: &[T]) -> impl Iterator<Item = &T> borrows from v without extra annotations. M07 covers what "captures" means.

Remember: impl Trait as an argument is a generic the caller chooses. As a return type it is one hidden concrete type the function chooses; different types in different branches need Box<dyn Trait> or an enum such as Either.

Trait objects: dyn Trait

Generics decide types at compile time. Sometimes you need the decision at run time: a list holding a mix of types, chosen while the program runs, such as a list of checks loaded from configuration. In Python every list is like this. In Rust you ask for it explicitly with a trait object, written dyn Trait: "some value whose type implements Trait, I do not know which."

Because different types have different sizes, a dyn Trait value cannot sit in a variable or a Vec slot directly. It always lives behind a pointer: &dyn Trait (borrowed) or Box<dyn Trait> (owned, on the heap; M08 covers Box). The pointer is "fat": it holds the address of the value and the address of a vtable, a table of that type's method implementations. Each method call looks up the function in the table, which is called dynamic dispatch. Python does that on every method call.

check.as_ref() turns a &Box<dyn Check> into a &dyn Check. In many places Rust does that conversion for you, but spelling it out once shows what is going on. &NonEmpty converts to &dyn Check automatically.

Not every trait can be a trait object

A vtable has one entry per method, so every method must be callable without knowing the concrete type. A generic method has no single entry (each T would need its own copy), and a method returning Self has no size the caller can know. Traits that avoid those are dyn compatible (older material says "object safe").

E0038: the trait `Render` is not dyn compatible, "because method render has generic type parameters." The usual fixes are to take a trait object in the method too (out: &mut dyn Write), or to add where Self: Sized to the generic method, which excludes it from the vtable.

Generics or dyn?

Generics / impl Traitdyn Trait

Default to generics. Reach for dyn when you need a heterogeneous collection, when the set of types is open-ended (plugins, user configuration), when a function must return different types from different branches, or when compile time and binary size matter more than a few nanoseconds per call.

You will see both in Pixi. Most code is generic, but errors use trait objects: Box<dyn std::error::Error + Send + Sync> (M04's Box<dyn Error> plus the thread markers from M08) and miette diagnostics as Box<dyn Diagnostic + Send + Sync + 'static>, because any of many error types can end up in the same place. Level 2 covers miette.

Remember: dyn Trait lives behind & or Box and dispatches through a vtable. Use it for mixed collections and run-time choice; use generics otherwise. Generic methods make a trait not dyn compatible (E0038).

Derive and the common std traits

Python gives every class a default __repr__, __eq__ by identity, and __hash__ by identity, and you override dunder methods to change them. A Rust type starts with none of this: it cannot be printed, compared, copied, or used as a map key until it implements the corresponding trait. For most of them you do not write the code; you ask the compiler to generate it with #[derive(...)], as in M02. A derive generates the obvious implementation: field by field, in declaration order.

1.10.0 > 1.9.7 is true because derived Ord compares major, then minor as numbers, then patch: exactly semantic-version order, and unlike comparing the strings "1.10.0" and "1.9.7". The field order in the struct is the sort order, so choose it deliberately.

Display is never derived

Debug is for developers, so a mechanical format is fine. Display, used by {} and .to_string(), is what users see, and only you know what that should look like. So it cannot be derived, and forgetting it is a common first error:

E0277: `Version` doesn't implement `std::fmt::Display`, and the note suggests {:?} instead. To implement it, write one method that writes into a Formatter:

write! is format! that writes into f and returns a fmt::Result. Implementing Display also gives you to_string() for free, through a blanket implementation in the standard library (the last section explains those). The padded output shows a subtlety: write! ignores width options like {:>8}, which is why Pixi's PixiPlatformName forwards to the inner string's fmt instead (Reading Pixi).

Remember: derive Debug, Clone, PartialEq and friends; derived comparisons go field by field in declaration order. Write Display by hand; it gives you to_string().

Conversion traits: From, Into, TryFrom, FromStr, AsRef

Python converts with constructors and class methods: str(x), int("3"), Path(s), Version.parse(s). Rust standardizes conversions as traits, so every type converts the same way and generic code can ask for "anything that converts into X."

From and Into

You implement From, never Into: the standard library has a blanket implementation that gives you Into automatically for every From. Use U::from(t) when you want the target type visible, and t.into() when the target is already known from context, such as a function argument or a typed let. M04 showed the other big use: ? calls From::from on the error, so a From impl between error types makes ? convert them.

This cell is a near copy of Pixi's real TaskName, a newtype (a one-field tuple struct wrapping another type to give it its own identity) with From<&str> and From<String> implementations (crates/pixi_manifest/src/task.rs#L22-L47). The dependency-spec crate goes further: PixiSpec, the enum for everything you can write on the right of numpy = ..., has a From impl for each kind of spec, so code can write detailed_spec.into() or git_spec.into() (crates/pixi_spec/src/lib.rs#L747-L791).

TryFrom and FromStr: conversions that validate

When a conversion can fail, implement TryFrom, or FromStr for parsing text. Each has an associated type for the error, type Error and type Err (the names differ for historical reasons), which the next section explains. FromStr is what str::parse calls, so implementing it lets your type be parsed exactly like u32.

This is the "parse, don't validate" pattern Pixi uses for every kind of name. Once you hold an EnvName, you know it is valid, because the only way to build one from text is through from_str. Functions that take an EnvName never re-check it. Python can approximate this with a class whose constructor validates; Rust makes it airtight by keeping the field private to its module (M10).

Pixi's EnvironmentName implements FromStr with a regex (^[a-z0-9-]+$) and maps the literal "default" to its Default variant (crates/pixi_manifest/src/environment.rs#L123-L141). That is why pixi run -e Test fails with "please use only lowercase letters, numbers and dashes."

AsRef: accept anything that can lend a view

AsRef<T> means "I can cheaply give you a &T." Its main use is flexible parameters: fn open(path: impl AsRef<Path>) accepts a &str, a String, a PathBuf, or a &Path, because all of them implement AsRef<Path>. Inside, path.as_ref() gives a &Path. Pixi's script manifest loaders take path: impl AsRef<Path> for exactly this reason. The difference from Into: AsRef borrows and never allocates; Into may build a new owned value.

Remember: implement From and get Into free. Fallible conversions are TryFrom (any input) and FromStr (text, via .parse()). impl Into<String> and impl AsRef<Path> make friendly parameters.

Associated types: Iterator::Item and friends

Look at how Iterator is defined in the standard library (simplified):

pub trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
    // ...seventy-odd default methods: map, filter, collect, sum...
}

type Item; is an associated type: a type that each implementation chooses, named Self::Item inside the trait. A Vec<String>'s iter() sets Item = &String; a chars() iterator sets Item = char. When you write impl Iterator<Item = String>, you are constraining that associated type. FromStr::Err and TryFrom::Error are associated types too.

Why not a generic parameter, Iterator<T>? Because a generic trait can be implemented many times for one type (From<&str> and From<String> for TaskName), while an associated type allows exactly one choice per type. An iterator yields one kind of item, so Item is associated; a type can be built from many sources, so From<T> is generic. The one-choice rule also means the compiler never needs you to say which Item you meant.

Implement Iterator, get everything

Implement next and choose Item, and your type has every adapter and consumer from M05. This is default methods paying off at scale:

A retry schedule with exponential backoff (100, 200, 400, 800 ms) in a dozen lines, and it already supports sum, filter, take, and collect. M09 goes further with custom iterators.

Remember: an associated type (type Item;) is chosen once per implementation and named Self::Item. Use a generic trait parameter when a type should implement the trait several ways; use an associated type when there is one natural answer.

The orphan rule, newtypes, and blanket impls

Python lets any code monkey-patch any class. Rust has a rule that prevents two crates from both implementing the same trait for the same type, which would leave the compiler unable to choose. The orphan rule: you may write impl Trait for Type only if the trait or the type is defined in your crate. Your trait for Vec: fine. Display for your struct: fine. Display (from std) for Vec (from std): not yours to decide.

E0117: only traits defined in the current crate can be implemented for types defined outside of the crate. The last note gives the standard way out: "define and implement a trait or new type instead." The newtype pattern wraps the foreign type in a local one-field struct, which you are free to give any trait:

The wrapper costs nothing at run time; it has the same layout as the Vec it holds. That is why Pixi is full of newtypes such as TaskName(String) and PixiPlatformName(String): each one gets its own Display, its own validation, and its own identity, so a task name cannot be passed where a platform name is expected.

Blanket implementations

A blanket implementation implements a trait for every type that meets some bound: impl<T: Display> ToString for T is the one in std that gave your Version a to_string() as soon as it implemented Display. The From-gives-Into rule is another. You can write your own, and Pixi does, as you will see next.

Remember: implement a trait only if the trait or the type is yours (E0117 otherwise). Wrap a foreign type in a newtype to give it foreign traits. A blanket impl (impl<T: Bound> Trait for T) gives a trait to every qualifying type at once.

Reading Pixi

A validated newtype: PixiPlatformName

Platform names in a Pixi manifest (linux-64, or a custom name like linux-64-cuda) are represented by a newtype that can only be built through validation. First the type and its Display (crates/pixi_manifest/src/platform.rs#L59-L76):

// `Deserialize` is implemented by hand (below) to route through `TryFrom` so
// the name validation can't be bypassed; the derive would accept any string.
#[derive(Clone, Debug, Eq, PartialEq, Ord, PartialOrd, Hash, serde::Serialize)]
#[serde(transparent)]
pub struct PixiPlatformName(String);

// ... a hand-written serde::Deserialize impl that calls try_from ...

impl Display for PixiPlatformName {
    fn fmt(&self, f: &mut Formatter<'_>) -> fmt::Result {
        self.0.fmt(f)
    }
}

Then the conversions (crates/pixi_manifest/src/platform.rs#L117-L143):

impl TryFrom<&str> for PixiPlatformName {
    type Error = PixiPlatformNameError;

    fn try_from(input: &str) -> Result<Self, Self::Error> {
        let validated = Self::valid_pixi_platform_name(input)?;
        // Family selectors (`linux`/`unix`/`win`/`osx`/`macos`) double as
        // `target.<family>.*` keys; a platform named after one would shadow them.
        if crate::target::family_name_to_selector(&validated).is_some() {
            return Err(PixiPlatformNameError::ReservedName(validated));
        }
        Ok(PixiPlatformName(validated))
    }
}

impl From<Platform> for PixiPlatformName {
    fn from(subdir: Platform) -> Self {
        PixiPlatformName(subdir.to_string())
    }
}

impl std::str::FromStr for PixiPlatformName {
    type Err = PixiPlatformNameError;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        PixiPlatformName::try_from(s)
    }
}
  • The derive line gives the name everything a map key and a sorted list need: Eq and Hash for HashSet<PixiPlatformName> (M05's FeaturesExt::platforms returns one), Ord for BTreeMap and sorting. Default is deliberately absent: an empty platform name is invalid. Serialize comes from serde, a Level 2 topic.
  • The comment explains a design decision you now understand: deriving Deserialize would build the struct directly from any string, bypassing validation, so the impl is hand-written and routes through try_from.
  • Display forwards to the String's own fmt, which respects width and alignment flags, unlike write!(f, "{}", self.0).
  • TryFrom<&str> chooses its error with the associated type type Error, validates the characters with a helper (? propagates its error), then rejects reserved names like linux, and only then wraps the string.
  • From<Platform> is infallible: a rattler Platform (a conda subdir such as osx-arm64) is always a valid name, so this conversion needs no Result.
  • FromStr delegates to try_from, so "linux-64".parse(), PixiPlatformName::try_from("linux-64"), and deserializing from TOML all run the same checks.

One trait, many collections: HasFeaturesIter and FeaturesExt

An environment, a grouped environment, and a solve group are different types, but each is "a collection of features," and each needs the same questions answered: which channels, which platforms, which dependencies. Pixi writes those answers once. The required part is a tiny trait (crates/pixi_manifest/src/has_features_iter.rs#L9-L12):

pub trait HasFeaturesIter<'source> {
    /// Returns an iterator to all Features in this collection
    fn features(&self) -> impl DoubleEndedIterator<Item = &'source Feature> + 'source;
}

The shared methods live in FeaturesExt, whose supertraits require both HasWorkspaceManifest and HasFeaturesIter, and a blanket impl gives it to every type that has both (line 41, lines 393-396):

pub trait FeaturesExt<'source>: HasWorkspaceManifest<'source> + HasFeaturesIter<'source> {
    // ... about twenty default methods: channels(), platforms(), dependencies(), ...
}

impl<'source, FeatureCollection> FeaturesExt<'source> for FeatureCollection where
    FeatureCollection: HasWorkspaceManifest<'source> + HasFeaturesIter<'source>
{
}

And here is Environment providing the one required method (crates/pixi_core/src/workspace/environment.rs#L510-L526):

impl<'p> HasFeaturesIter<'p> for Environment<'p> {
    /// Returns references to the features that make up this environment.
    fn features(&self) -> impl DoubleEndedIterator<Item = &'p Feature> + 'p {
        let manifest = self.workspace_manifest();
        let environment_features = self.environment.features.iter().map(|feature_name| {
            manifest
                .feature(feature_name)
                .expect("feature usage should have been validated upfront")
        });

        if self.environment.no_default_feature {
            Either::Right(environment_features)
        } else {
            Either::Left(environment_features.chain([self.workspace_manifest().default_feature()]))
        }
    }
}
  • 'source and 'p are lifetime parameters, the subject of M07. Read them as "the features are borrowed from the workspace."
  • Return-position impl Trait in a trait. features returns "some double-ended iterator of feature references"; each implementer picks its own concrete iterator type. DoubleEndedIterator is Iterator plus the ability to iterate from the back (.rev()).
  • Supertraits. FeaturesExt: HasWorkspaceManifest + HasFeaturesIter means "anything implementing FeaturesExt must also implement both," so its default methods may call self.features() and self.workspace_manifest(). That is how channels() and platforms() from M05's reading can be written once.
  • The blanket impl has an empty body: every method is a default. Implementing the two small traits is enough to receive all of FeaturesExt, automatically.
  • Either solves the E0308 problem from the impl Trait section. One branch returns the mapped iterator, the other the same iterator chained with the default feature. Those are different types, so each is wrapped in a variant of itertools::Either, which implements Iterator (and DoubleEndedIterator) when both sides do. The function now returns one type, with no heap allocation.
Why does PixiPlatformName implement both TryFrom<&str> and FromStr when they do the same thing?

They serve different callers. FromStr is what str::parse and many libraries (clap for command-line arguments, for example) look for; TryFrom is the general conversion trait that generic code and the hand-written Deserialize use. Delegating one to the other keeps a single validation path.

Why not return Box<dyn DoubleEndedIterator<...>> instead of using Either?

It would work, but it costs a heap allocation per call and a vtable call for every next. features() is called all over Pixi (every FeaturesExt method starts with it), so the zero-cost Either is worth the extra import. That is the generics-versus-dyn trade-off in a real codebase.

A new type Preset implements HasWorkspaceManifest and HasFeaturesIter. What else must it do to get preset.channels()?

Nothing in its own code: the blanket impl gives it FeaturesExt. The caller must have FeaturesExt in scope (use pixi_manifest::FeaturesExt;) to call channels(), or the call fails with E0599.

Practice

Five exercises, ending with a small type that sorts, prints, and parses like a real Pixi type.

The Describe trait has one required method and two defaults. Implement it for both structs:

  • Package: name() is the name and version separated by a space ("numpy 2.1"); override kind() to return "package".
  • Task: name() is the task name; keep the default kind().

use std::collections::BTreeSet;
use std::fmt::Display;

fn largest<T: PartialOrd>(items: &[T]) -> Option<&T> {
    let mut best = items.first()?;
    for item in items {
        if item > best {
            best = item;
        }
    }
    Some(best)
}

fn count_distinct<T: Ord>(items: &[T]) -> usize {
    items.iter().collect::<BTreeSet<_>>().len()
}

    items.iter().map(|i| i.to_string()).collect::<Vec<_>>().join(sep)
}

Build a small PlatformName in the style of Pixi's PixiPlatformName. Implement TryFrom<&str>, FromStr (delegating to try_from), and Display (the bare name). The rules, checked character by character with the position counted in characters from 0:

  • The empty string is PlatformNameError::Empty.
  • The first character must be an ASCII lowercase letter.
  • Every other character must be an ASCII lowercase letter, an ASCII digit, or -.
  • The first character that breaks a rule is reported as PlatformNameError::InvalidCharacter { character, position }.
Hint

Check for empty first. Then for (position, character) in input.chars().enumerate(), with let ok = if position == 0 { character.is_ascii_lowercase() } else { ... };. from_str is one line: PlatformName::try_from(s). For Display, use self.0.fmt(f) so the padding test passes.

Show solution
use std::fmt;
use std::str::FromStr;

#[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord, Hash)]
struct PlatformName(String);

#[derive(Debug, PartialEq)]
enum PlatformNameError {
    Empty,
    InvalidCharacter { character: char, position: usize },
}

impl TryFrom<&str> for PlatformName {
    type Error = PlatformNameError;

    fn try_from(input: &str) -> Result<Self, Self::Error> {
        if input.is_empty() {
            return Err(PlatformNameError::Empty);
        }
        for (position, character) in input.chars().enumerate() {
            let ok = if position == 0 {
                character.is_ascii_lowercase()
            } else {
                character.is_ascii_lowercase() || character.is_ascii_digit() || character == '-'
            };
            if !ok {
                return Err(PlatformNameError::InvalidCharacter { character, position });
            }
        }
        Ok(PlatformName(input.to_string()))
    }
}

impl FromStr for PlatformName {
    type Err = PlatformNameError;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        PlatformName::try_from(s)
    }
}

impl fmt::Display for PlatformName {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        self.0.fmt(f)
    }
}

Implement the Check trait for three validators, then two functions:

trait Check {
    fn name(&self) -> String;
    fn passes(&self, value: &str) -> bool;
}

struct NonEmpty;
struct MaxLen(usize);
struct Lowercase;

impl Check for NonEmpty {
    fn name(&self) -> String { "non-empty".to_string() }
    fn passes(&self, value: &str) -> bool { !value.is_empty() }
}

impl Check for MaxLen {
    fn name(&self) -> String { format!("max-len {}", self.0) }
    fn passes(&self, value: &str) -> bool { value.len() <= self.0 }
}

impl Check for Lowercase {
    fn name(&self) -> String { "lowercase".to_string() }
    fn passes(&self, value: &str) -> bool { value == value.to_lowercase() }
}

fn default_checks() -> Vec<Box<dyn Check>> {
    vec![Box::new(NonEmpty), Box::new(MaxLen(20)), Box::new(Lowercase)]
}

fn failing(checks: &[Box<dyn Check>], value: &str) -> Vec<String> {
    checks.iter().filter(|c| !c.passes(value)).map(|c| c.name()).collect()
}

This exercise starts with a compile error: the tests compare, sort, and print Version values with assert_eq!, and the struct derives nothing. Read the errors (E0369, E0277) and add the derives they ask for. Then implement:

  • Display: MAJOR.MINOR.PATCH, for example 1.10.0.
  • FromStr with type Err = String: exactly three dot-separated parts, each a u32. A wrong number of parts or a part that does not parse is an Err (any message).
  • latest(inputs): parse every string, skip the ones that fail, and return the highest version, or None if nothing parsed.

Versions must compare numerically, so 1.10.0 > 1.9.9.

Hint

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)] on the struct; the field order already gives semantic-version ordering. In from_str, collect s.split('.').map(|p| p.parse::<u32>().map_err(|e| e.to_string())).collect::<Result<Vec<_>, _>>()?, then check there are exactly three. latest is inputs.iter().filter_map(|s| s.parse().ok()).max().

Show solution
use std::fmt;
use std::str::FromStr;

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
struct Version {
    major: u32,
    minor: u32,
    patch: u32,
}

impl fmt::Display for Version {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}.{}.{}", self.major, self.minor, self.patch)
    }
}

impl FromStr for Version {
    type Err = String;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        let parts = s
            .split('.')
            .map(|p| p.parse::<u32>().map_err(|e| format!("invalid part '{p}': {e}")))
            .collect::<Result<Vec<_>, _>>()?;
        match parts.as_slice() {
            [major, minor, patch] => Ok(Version { major: *major, minor: *minor, patch: *patch }),
            _ => Err(format!("expected MAJOR.MINOR.PATCH, got '{s}'")),
        }
    }
}

fn latest(inputs: &[&str]) -> Option<Version> {
    inputs.iter().filter_map(|s| s.parse().ok()).max()
}

Quiz

Recap

  • A trait is a checked set of methods; impl Trait for Type provides them. Required methods have no body, default methods do and can call the required ones.
  • Trait methods are callable only with the trait in scope: E0599 on a method you know exists means a missing use.
  • Generics (<T>) are monomorphized: one specialized copy per type, no run-time cost. Inside, you can use only what the bounds (T: A + B, where) promise.
  • impl Trait as an argument is an anonymous generic; as a return type it is one hidden concrete type, which is why branches returning different iterators need Box<dyn ...> or Either.
  • dyn Trait lives behind & or Box and dispatches through a vtable: use it for mixed collections and run-time choice. Generic methods make a trait not dyn compatible (E0038).
  • Derive Debug, Clone, Copy, PartialEq/Eq, Hash, PartialOrd/Ord, Default; derived comparisons follow field order. Write Display by hand.
  • Implement From to get Into; TryFrom and FromStr validate; AsRef borrows a view. Pixi's names are validated newtypes built this way.
  • Associated types (Iterator::Item, FromStr::Err) are one choice per implementation.
  • The orphan rule: the trait or the type must be yours (E0117). Newtypes get around it; blanket impls give a trait to every qualifying type.
