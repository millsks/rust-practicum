Lifetimes in Practice

In M03 the borrow checker followed references inside one function. This module is about references that cross a function boundary or sit inside a struct, where the compiler needs you to say how they relate. A lifetime annotation is that statement: "the reference I return points into this argument, not that one." Once you read 'a as a relationship rather than a length of time, most lifetime errors become one-line fixes, and you will know when the right fix is to stop borrowing and own the data.

⏱ ~2 hoursPrerequisites: M03 Ownership & Borrowing, M06 Traits & Generics
  • Explain what a lifetime annotation means: a constraint linking references, not a duration you choose
  • Apply the three elision rules to predict when a signature needs explicit lifetimes
  • Write functions that return references tied to the correct input, and only that input
  • Define structs that hold references, and write impl blocks and trait impls for them
  • Tell &'static str apart from the bound T: 'static, and explain why threads and tasks need the bound
  • Read and fix E0106, E0597, E0515, E0716, and E0373
  • Decide when to stop fighting the borrow checker and return or store owned data instead

The problem lifetimes solve

In Python, a reference keeps its object alive. If you write r = config["channels"] and then del config, the list is still there: the interpreter counts references, and the list is freed only when the last one goes away. You can never hold a reference to freed memory, because holding the reference is what prevents the free.

Rust does not count references. A &T is a plain pointer with no say over when its target is freed. The owner decides that: the value is dropped when its owner goes out of scope (M03). So Rust needs a different guarantee, and it gets one at compile time. The borrow checker proves, for every reference, that the value it points to is still alive at every place the reference is used. A reference that outlives its target is a dangling reference, and Rust refuses to compile one.

The lifetime of a reference is the region of code over which that reference must stay valid: from where it is created to its last use. The compiler computes these regions itself. Step through the program below and watch the borrow arrow outlive its target.

Remember: a reference never keeps its target alive. The borrow checker proves the target outlives every use of the reference, and rejects the program when it cannot.

What 'a means: a relationship, not a duration

Inside one function the compiler can see every borrow and every drop, so it never asks you for help. A function signature is different. When main calls a function, the compiler checks the call using only the function's signature, not its body. That is what keeps compile times and error messages local: change a body, and callers do not need rechecking. So if a function returns a reference, the signature must say which argument that reference borrows from.

Try a function that returns the longer of two names:

E0106 says the return type "contains a borrowed value, but the signature does not say whether it is borrowed from a or b". The compiler is not confused about the body. It is telling you the signature is incomplete: a caller would not know how long it may keep the result.

You answer with a lifetime parameter. It is declared in angle brackets like a generic type parameter, written with a leading apostrophe, and conventionally named 'a, 'b, and so on:

Read the signature out loud as a contract: "for some region 'a, if both a and b are valid for all of 'a, then the result is valid for 'a too." At each call, the compiler picks 'a as the region where both arguments are alive (their overlap), and then checks that the result is not used outside it. You never pick the length of 'a. You only state which references are linked.

That is why "lifetime annotations describe, they do not prescribe" is the most useful sentence in this module. An annotation cannot extend or shorten how long a value lives. It gives the compiler a relationship to check, and if the relationship is false, the program does not compile.

Here is the contract being enforced. second lives only inside the inner block, so the overlap 'a ends there, and using winner after the block is rejected, even though on this particular input the winner happens to be first:

The compiler does not run your code to see which branch was taken. It trusts the signature, and the signature says the result might borrow from second. This is the guarantee you want: the function's author can later change the body to return b more often, and no caller can break.

&'a T is a shared reference valid for 'a; &'a mut T is a mutable one. Lifetime parameters go first in the angle brackets: fn parse<'a, T: FromStr>(s: &'a str) -> .... The name is arbitrary; Pixi mostly uses 'a, and 's or 'de where a name helps (serde uses 'de for "the deserializer's input").

Remember: 'a names a region the compiler chooses. Writing the same 'a on an input and the output means "the output borrows from that input." It never changes when anything is dropped.

Elision: when you can leave them out

If every function that returned a reference needed <'a>, Rust would be noisy. In practice most do not, because the compiler applies three lifetime elision rules to fill in the obvious cases. Elision means "left out": the lifetimes are still there, you just do not have to write them.

RuleWhat the compiler doesExample
1. InputsEvery reference parameter without a written lifetime gets its own distinct lifetimefn f(a: &str, b: &str) becomes fn f<'x, 'y>(a: &'x str, b: &'y str)
2. One inputIf there is exactly one input lifetime, every elided output lifetime is that onefn first(s: &str) -> &str means the result borrows from s
3. MethodsIf there are several input lifetimes and one is &self or &mut self, elided outputs get self's lifetimefn name(&self, key: &str) -> &str borrows from self

If, after these rules, an output lifetime is still unknown, you get E0106 and must write it yourself. That is exactly what happened with longer: two inputs, no self, so rule 2 and rule 3 do not apply.

The anonymous lifetime '_

Sometimes a type has a lifetime parameter and elision would pick the right one, but you still have to show that a borrow is involved. Write '_, the anonymous lifetime: "there is a lifetime here; apply the usual rules." You will see it constantly in Pixi:

fn parse_line(line: &str) -> Option<Entry<'_>>      // Entry borrows from `line`
impl fmt::Display for TableName<'_> { ... }          // "for any lifetime"
fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result

Writing Entry without <'_> in a return type still compiles, but the elided_lifetimes_in_paths lint and code reviewers prefer the marker, because it tells the reader at a glance that the returned value borrows from an argument.

Pixi's small shell interpreter looks up a variable and returns a borrowed &str. There are two inputs, so elision cannot decide, and the author names the one the result comes from (crates/pixi_script_shell/src/execute.rs):

fn variable<'a>(name: &str, context: &'a ShellContext) -> Result<&'a str, ShellExecutionError> {
    context
        .variables
        .get(name)
        .map(String::as_str)
        .ok_or_else(|| ShellExecutionError::UndefinedVariable {
            name: name.to_owned(),
        })
}

name has its own elided lifetime, unrelated to 'a. That is precise: the value lives in the context's map, so callers may drop the name they searched for and keep the result. Note the error path: it needs to keep the name, and it cannot borrow it for longer than the call, so it copies it with to_owned().

Remember: one reference in, or a &self method, and you rarely write lifetimes. Two or more reference inputs with a reference output, and you must say which input the output borrows from.

Returning references: E0515 and what it is telling you

A Python habit causes the most common lifetime error. In Python a function can build a new string and return it, and the caller gets a reference to it. Translated literally into Rust:

The signature compiles (rule 2 links the result to name), but the body breaks the promise. lower is a new String owned by the function. It is dropped at the closing brace, so a reference into it would dangle the moment the function returns. No annotation can fix this, because the data you want to return does not exist anywhere outside the function.

The fix is to return the owner. Ownership moves out to the caller, and nothing is dropped:

A function can return a reference only into something that outlives the call: one of its reference arguments (as in longer), data reachable through &self, or data that lives for the whole program, such as a string literal. If the value is computed inside the function, return it by value.

The error comes in two forms. "cannot return reference to local variable x" appears for a plain &x. "cannot return value referencing local variable lower", with the label "returns a value referencing data owned by the current function", appears when the borrow is hidden inside another value, such as lower.as_str() or a struct that borrows a local. Both mean the same thing.

A related trap: returning a reference to a parameter that was passed by value. In fn first(v: Vec<String>) -> &String, v is owned by the function and dropped at its end, so you get E0106 (no input lifetime to borrow from) and, if you add one, E0515. Take &[String] instead.

Remember: E0515 means "the thing you are pointing at dies when this function returns." The fix is almost always to return the owned value (String, Vec<T>, PathBuf), not to add annotations.

Structs that borrow

A struct can hold references, which lets it act as a cheap view into data someone else owns. Parsing is the classic case: you read a file into one String, then build many small structs that point into it, without copying any text. Python cannot express this, since every slice of a str is a new object.

A struct that holds a reference must declare a lifetime parameter and use it on each reference field:

Three pieces of syntax:

  • struct Entry<'a> declares the parameter; key: &'a str says the field borrows for 'a. Read the type Entry<'a> as "an entry that is valid only while whatever it borrows from is valid for 'a."
  • impl<'a> Entry<'a> introduces 'a for the block, just like impl<T> Wrapper<T>.
  • fn value(&self) -> &'a str is more generous than the elided version would be. Elision would tie the result to the borrow of self (rule 3); naming 'a ties it to the original text, so the caller may drop the Entry and keep the value.

The struct inherits the rule from its fields: it cannot outlive what it borrows. Here the text is dropped while an entry still points into it:

Same E0597 as before: the struct is just a container for the borrow. You will meet a related shape often: a function that reads a file and tries to return parsed views of it. The String holding the file is local, so the views cannot leave the function (E0515). The usual design is to have the caller own the text and pass &str in, or to make the parsed struct own its fields.

Trait impls for borrowing structs

When you implement a trait for a struct with a lifetime, you usually do not care which lifetime it is, so you write '_:

impl fmt::Display for Entry<'_> {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{} = {:?}", self.key, self.value)
    }
}

Pixi uses borrowing structs as builder and context types that gather references for one operation. TableName builds a TOML table path like feature.cuda.dependencies from pieces it borrows (crates/pixi_manifest/src/manifests/table_name.rs):

/// Struct that is used to access a table in `pixi.toml` or `pyproject.toml`.
pub struct TableName<'a> {
    prefix: Option<&'static str>,
    target: Option<TargetSelector>,
    feature_name: Option<&'a FeatureName>,
    table: Option<&'a str>,
}

impl Display for TableName<'_> {
    fn fmt(&self, f: &mut Formatter) -> fmt::Result {
        write!(f, "{}", self.to_toml_table_name())
    }
}

One struct mixes three kinds of field: an owned TargetSelector, references valid for the caller-chosen 'a, and a &'static str prefix that must be a literal such as "tool.pixi". The next section explains 'static.

Remember: a struct with a reference field needs <'a>, and a value of that struct cannot outlive the data it points into. Use borrowing structs for short-lived views; use owned fields for anything you store or return.

'static, and the bound T: 'static

'static is the one lifetime with a built-in name. It is the region "the rest of the program". It shows up in two places that look similar and mean different things.

&'static T: a reference that is valid forever

A string literal such as "conda-forge" is compiled into the program binary, so it exists for the whole run. Its type is &'static str. A function can return one without any argument to borrow from:

The result is not linked to platform, so dropping platform is fine. Statics (static NAME: &str = "pixi";) are also 'static, and so is memory you deliberately leak with Box::leak, which you will rarely need.

T: 'static: a type that contains no short-lived borrows

The bound T: 'static on a generic type does not mean "the value lives forever". It means "the type T holds no references that could expire": it is safe to keep a T for as long as you like. Every owned type meets the bound. String, Vec<u8>, PathBuf and i32 are all 'static types, even though a particular String may be dropped a microsecond later. &'a str for a local 'a, or Entry<'a>, are not.

You meet this bound whenever code hands a value to something that may outlive the current function, such as a new thread. std::thread::spawn requires its closure to be 'static, because the thread might still run after main's locals are gone:

E0373 says the closure "may outlive the current function, but it borrows packages", and its help: line gives the fix: add move, so the closure takes ownership of the vector. A closure that owns its data holds no borrows, so it is 'static:

You can write the same bound on your own functions. This helper stores anything printable for later; owned values pass, borrows of locals do not:

fn keep_for_later<T: std::fmt::Debug + Send + 'static>(value: T) -> std::thread::JoinHandle<()> {
    std::thread::spawn(move || println!("{value:?}"))
}

keep_for_later(String::from("ok"));   // String: 'static
let local = String::from("no");
keep_for_later(&local);              // error[E0597]: argument requires that `local` is borrowed for `'static`

Async tasks have the same rule. Pixi runs blocking filesystem work on a tokio thread pool, and the helper's bounds say exactly what the pool needs (crates/pixi_command_dispatcher/src/file_fingerprint.rs):

pub(crate) async fn spawn_blocking_with_io_permit<T>(
    io_semaphore: Option<Arc<Semaphore>>,
    task: impl FnOnce() -> T + Send + 'static,
) -> Result<T, tokio::task::JoinError>
where
    T: Send + 'static,
{
    // ...
    tokio::task::spawn_blocking(move || {
        let _permit = permit;
        task()
    })
    .await
}

Both the closure and its result must be Send (safe to move to another thread, M08) and 'static (no borrowed locals). This is why Pixi code clones an Arc or a PathBuf just before spawning: the task must own what it uses. Async is Level 2; for now, read + Send + 'static as "this will run somewhere else, later".

When a lifetime error suggests "consider using the 'static lifetime", treat it with suspicion. Changing &'a str to &'static str in a signature makes the error move to every caller that passes a non-literal string. The right fix is usually to own the data.

Remember: &'static T is a reference valid for the whole program (literals, statics). T: 'static means "T contains no expiring borrows": every owned type satisfies it. Threads and spawned tasks require it.

The lifetime errors you will actually meet

Lifetime problems show up as a handful of error codes. Learn to recognize each by its first line, then go straight to the usual fix.

CodeFirst lineWhat it meansUsual fix
E0106missing lifetime specifierA signature or struct field has a reference whose lifetime elision cannot work outAdd <'a> and link the output to the right input; or return an owned value
E0597x does not live long enoughA borrow is used after its owner is droppedMove the owner to an outer scope, or shorten the use
E0515cannot return reference to local variable / cannot return value referencing local variableYou return a reference into something the function ownsReturn the owned value
E0716temporary value dropped while borrowedYou borrowed from a temporary (an unnamed value) that dies at the end of the statementBind the temporary to a let first
E0373closure may outlive the current function, but it borrows xA thread or task closure borrows a localmove the data in (clone first if you still need it)
(no code)lifetime may not live long enoughThe body returns data with a different lifetime than the signature promisesFix the signature to name the input the data really comes from

E0716 deserves an example, because it looks like perfectly reasonable code:

to_uppercase() creates a new String that has no name. Rust drops unnamed temporaries at the end of the statement (the ;), so name would point into freed memory on the next line. The help line says "consider using a let binding to create a longer lived value". Give the owner a name: let upper = String::from("pixi").to_uppercase(); let name = upper.as_str();, or just keep the String.

The unnamed error, "lifetime may not live long enough", comes from a signature that names the wrong input:

The signature promises the result comes from manifest, but one branch returns fallback, which has an unrelated lifetime 'b. The compiler's help suggests adding the bound 'b: 'a ("'b outlives 'a"). That works, but the simpler fix is to use one lifetime for both, as in longer.

When you read a lifetime error, find the three spans: the borrow, the drop, and the later use. One of the three is in the wrong place. Do not start by adding annotations; annotations change only what the signature promises, and a wrong promise just moves the error to the caller.

Remember: E0597 is "owner died first", E0515 is "you returned a pointer to your own local", E0716 is "the owner never had a name", E0373 is "a thread borrowed a local".

When to stop fighting and own the data

Borrowing avoids copies. Copies cost time and memory, but usually far less than you think: cloning a package name is a small allocation and a memcpy of a few bytes. Lifetime parameters cost something too: every struct that holds one infects its users, who must carry the parameter in their own types and keep the source alive. Experienced Rust developers borrow freely in function arguments and own by default in stored data.

Borrow (&str, &[T], &T)

Function parameters you only read. Return values that are a sub-slice of an input. Short-lived views and iterators over data the caller owns. Hot loops where a copy per item would show up in a profile.

Own (String, Vec<T>, PathBuf)

Struct fields that live beyond one call. Values you return that you computed. Anything you send to a thread or task. Error types (they travel up the call stack). Values whose source is about to be dropped.

Here is the same parse written both ways. The owned version has no lifetime parameter, can be returned from a function that reads a file, stored in a Vec that outlives the text, and sent to a thread:

struct Entry<'a> {
    key: &'a str,
    value: &'a str,
}

fn parse(line: &str) -> Option<Entry<'_>> {
    let (key, value) = line.split_once('=')?;
    Some(Entry { key: key.trim(), value: value.trim() })
}
struct Entry {
    key: String,
    value: String,
}

fn parse(line: &str) -> Option<Entry> {
    let (key, value) = line.split_once('=')?;
    Some(Entry { key: key.trim().to_string(), value: value.trim().to_string() })
}

Notice that the owned version still takes &str. Borrowing the input and owning the output is the most common shape in Rust code, and in Pixi. You can convert at the edge: borrow while searching, then call .to_string(), .to_owned(), or PathBuf::from on the one value you keep.

The program below reads a "file" in a helper function and returns owned entries. Try changing Entry to hold &str fields and see which error you get.

Two more tools sit between "borrow" and "copy", and they are the subject of the next module: Cow<'_, str> (borrow when you can, own when you must) and Rc/Arc (share one owned value between many owners cheaply).

Clippy will not complain about a well-placed .clone(), and reviewers on the Pixi repository rarely do either. What they do flag is a public type that grew a lifetime parameter for no measurable gain, because every caller now pays for it. If you are fighting the borrow checker for more than a few minutes in non-hot code, own the data and move on.

Remember: borrow in parameters, own in fields and return values. A clone that removes a lifetime parameter is usually a good trade.

Reading Pixi

Two short excerpts show the module's ideas in real code: a function that returns a borrow tied to one specific input, and a borrowing "view" struct used only for formatting.

1. Reading a value out of CMakeCache.txt

Pixi's CMake build backend reads CMake's cache file to learn where the sources are and which ninja binary CMake chose (crates/pixi_build_cmake/src/inputs.rs#L106-L110):

/// Returns the value of a `KEY:TYPE=value` entry from a parsed
/// `CMakeCache.txt`, or `None` if the key isn't present.
fn read_cache_value<'a>(cache: &'a str, key: &str) -> Option<&'a str> {
    cache.lines().find_map(|l| l.strip_prefix(key))
}

And its caller (crates/pixi_build_cmake/src/inputs.rs#L52-L65):

let cache = fs_err::read_to_string(build_dir.join("CMakeCache.txt"))?;
let source_dir = read_cache_value(&cache, CMAKE_HOME_DIRECTORY_KEY)
    .map(PathBuf::from)
    .ok_or_else(|| {
        io::Error::new(
            io::ErrorKind::InvalidData,
            "CMAKE_HOME_DIRECTORY not found in CMakeCache.txt",
        )
    })?;
// ...
let ninja_binary = read_cache_value(&cache, CMAKE_MAKE_PROGRAM_KEY)
    .map(PathBuf::from)
    .unwrap_or_else(|| PathBuf::from("ninja"));
  • fn read_cache_value<'a>: two reference inputs, so elision cannot pick one; the author declares 'a.
  • cache: &'a str, key: &str: only cache carries 'a. The key gets its own anonymous lifetime, because the result never points into it.
  • Option<&'a str>: the value found is a slice of the cache text, with no copying. lines() yields &'a str slices of cache, and strip_prefix returns the rest of one of them, still borrowed from cache.
  • In the caller, cache is an owned String, local to the function. The borrowed results are immediately converted with .map(PathBuf::from): borrow to search, own what you keep. That conversion is what allows source_dir and ninja_binary to be stored in a Ninja struct and used after cache is dropped.
Question: what would change if the signature were fn read_cache_value<'a>(cache: &'a str, key: &'a str) -> Option<&'a str>?

It would still compile here, because both the cache and the constant key live long enough. But the signature would be less precise: callers would have to keep key alive as long as they keep the result, even though the result never borrows from it. A caller that built the key with format! and dropped it would get E0597 for no good reason. Give an input a lifetime only if the output can borrow from it.

Question: could read_cache_value return Option<PathBuf> directly?

Yes, and then it would need no lifetime parameter at all. The author kept the function generic and cheap (the value is just text, and not every key is a path), and let each caller decide what to own. Both are reasonable; the borrowed version avoids an allocation when the caller only needs to compare.

2. A view struct for error messages

Pixi's error messages talk about "feature 'cuda'", but a feature synthesized from an environment should be described as "environment 'cuda'". Rather than build a String eagerly, FeatureName hands out a tiny struct that borrows it and knows how to print it (crates/pixi_manifest/src/feature.rs#L104-L124):

    pub fn user_facing(&self) -> UserFacingFeatureName<'_> {
        UserFacingFeatureName(self)
    }
}

/// Helper returned by [`FeatureName::user_facing`] that renders a feature name
/// for diagnostics, describing a synthesized environment feature as an
/// environment rather than a feature.
pub struct UserFacingFeatureName<'a>(&'a FeatureName);

impl fmt::Display for UserFacingFeatureName<'_> {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self.0 {
            FeatureName::Environment(name) => write!(f, "environment '{name}'"),
            _ => write!(f, "feature '{}'", self.0.as_str()),
        }
    }
}
  • UserFacingFeatureName<'a>(&'a FeatureName) is a tuple struct with one borrowed field, accessed as self.0. It is the size of one pointer.
  • fn user_facing(&self) -> UserFacingFeatureName<'_>: rule 2 (one input) ties the view to self; '_ shows the reader that the return value borrows.
  • impl fmt::Display for UserFacingFeatureName<'_>: the impl works for any lifetime, so it uses the anonymous one.
  • Callers write format!("{} is empty", name.user_facing()) or put it in a thiserror message. The view lives for one expression, so the borrow never causes trouble.
Question: why is a borrowing struct a good fit here, when the previous section said to own stored data?

Because it is not stored. It exists only to be formatted, almost always within one expression, and owning would mean cloning the feature name for every message. Short-lived views are where lifetime parameters pay off with no cost to users.

Question: in match self.0, self.0 is a &FeatureName. Why can the arm bind name without moving anything out?

Matching on a reference uses default binding modes (match ergonomics): the pattern FeatureName::Environment(name) binds name as a reference into the borrowed enum, not as an owned value. Nothing moves, which is exactly what you want behind a &.

Five exercises, from elision to an iterator that borrows. Some ask you to change a signature; the prompt says so, and then the compiler error from the tests is your first clue.

Write name_of(spec: &str) -> &str that returns the package name part of a dependency spec: everything before the first space, =, <, >, or !, with surrounding whitespace trimmed. "numpy >=2" gives "numpy", "python==3.14" gives "python", " rich " gives "rich". The result must be a slice of the input (no allocation). The signature needs no lifetime annotations; say to yourself which elision rule makes that true.

Hint

Trim first, then find the end with s.find(|c: char| c == ' ' || "=<>!".contains(c)), and slice &s[..end]. trim returns a slice of its input, so the chain stays borrowed. Elision rule 2 links the output to the only input.

Show solution 
fn name_of(spec: &str) -> &str {
    let s = spec.trim();
    let end = s.find(|c: char| c == ' ' || "=<>!".contains(c)).unwrap_or(s.len());
    &s[..end]
}

Hint

Remove 'a from preferred (leave it as plain &str). In the body, channels.iter().find(|c| c.as_str() == preferred) and .or_else(|| channels.first()), then .map(String::as_str).

Show solution 
fn pick_channel<'a>(channels: &'a [String], preferred: &str) -> Option<&'a str> {
    channels
        .iter()
        .find(|c| c.as_str() == preferred)
        .or_else(|| channels.first())
        .map(String::as_str)
}

Define struct Entry<'a> with two &'a str fields, key and value. Write parse_entries(text: &str) -> Vec<Entry<'_>> that turns each key = value line into an entry with both sides trimmed. Skip blank lines, lines starting with # (after trimming), and lines without =. Split on the first = only, so cmd = a=b has value a=b. Then write lookup<'a>(entries: &[Entry<'a>], key: &str) -> Option<&'a str> returning the value of the last entry with that key, borrowed from the original text.

Hint

text.lines().filter_map(|line| { ... }) with let line = line.trim();, an early return None for blanks and comments, and line.split_once('=')?. For lookup, entries.iter().rev().find(...) then .map(|e| e.value); copying the &'a str out of the entry keeps the 'a lifetime.

Show solution 
struct Entry<'a> {
    key: &'a str,
    value: &'a str,
}

fn parse_entries(text: &str) -> Vec<Entry<'_>> {
    text.lines()
        .filter_map(|line| {
            let line = line.trim();
            if line.is_empty() || line.starts_with('#') {
                return None;
            }
            let (key, value) = line.split_once('=')?;
            Some(Entry { key: key.trim(), value: value.trim() })
        })
        .collect()
}

fn lookup<'a>(entries: &[Entry<'a>], key: &str) -> Option<&'a str> {
    entries.iter().rev().find(|e| e.key == key).map(|e| e.value)
}

Pixi's task shell has a Parser<'a> that walks over a borrowed command string. Build a small version: struct Args<'a> { rest: &'a str } with Args::new(line: &'a str), and implement Iterator for it with type Item = &'a str;. Each call to next skips leading whitespace and yields the next whitespace-separated word, except that a word starting with " runs to the next " and is yielded without the quotes. An unterminated quote yields the rest of the line (without the opening quote). Every item must be a slice of the original line, so items can outlive the iterator.

Hint

Start with let s = self.rest.trim_start(); and return None if it is empty. For a quote, let body = &s[1..]; and body.find('"'): on Some(end) the item is &body[..end] and the rest is &body[end + 1..]. Otherwise find the next whitespace with s.find(char::is_whitespace). Because self.rest is &'a str, every slice of it is &'a str too.

Show solution 
struct Args<'a> {
    rest: &'a str,
}

impl<'a> Args<'a> {
    fn new(line: &'a str) -> Self {
        Args { rest: line }
    }
}

impl<'a> Iterator for Args<'a> {
    type Item = &'a str;

    fn next(&mut self) -> Option<&'a str> {
        let s = self.rest.trim_start();
        if s.is_empty() {
            self.rest = s;
            return None;
        }
        if let Some(body) = s.strip_prefix('"') {
            match body.find('"') {
                Some(end) => {
                    self.rest = &body[end + 1..];
                    Some(&body[..end])
                }
                None => {
                    self.rest = "";
                    Some(body)
                }
            }
        } else {
            let end = s.find(char::is_whitespace).unwrap_or(s.len());
            self.rest = &s[end..];
            Some(&s[..end])
        }
    }
}

Quiz

Recap

  • A reference never keeps its target alive. The borrow checker proves the owner outlives every use, or rejects the program (E0597).
  • A lifetime annotation is a relationship: the same 'a on an input and the output means "the output borrows from that input". The compiler chooses the region; you never choose a duration.
  • Elision: each input gets its own lifetime; with one input it flows to the output; with &self, self's lifetime flows to the output. Otherwise write it out (E0106).
  • Only give an input a lifetime if the output can borrow from it. Precise signatures help callers.
  • You cannot return a reference to a local (E0515). Return the owned value.
  • Structs that hold references need <'a> and cannot outlive their source. Use them for short-lived views; use owned fields for stored data.
  • &'static T is valid for the whole program; T: 'static means "no expiring borrows", which every owned type satisfies. Threads and tasks need it; move provides it.
  • Borrow in parameters, own in fields and return values. A clone that removes a lifetime parameter is often the right call.
