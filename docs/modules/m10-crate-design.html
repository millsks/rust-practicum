Visibility, Features & Crate Design

Pixi is about sixty crates in one workspace. What each crate exposes, what it hides, and which optional pieces it compiles are all decided in a few places you can learn to read in minutes: pub modifiers, pub use lines in lib.rs, and the [features] and [workspace.dependencies] tables in Cargo.toml. This module teaches those places, and why a maintainer cares about every pub they add.

⏱ ~1.5 hoursPrerequisites: M01 Cargo, Crates & Modules, M06 Traits & Generics

  • Choose between pub, pub(crate), pub(super), and private for an item or a field
  • Design a crate's public surface with private modules and pub use re-exports, and recognize a prelude
  • Read and write [features], optional dependencies, and default-features = false, and explain feature unification
  • Use #[cfg(...)], cfg!, and #[cfg_attr(...)] for features, tests, and target platforms
  • Write /// and //! doc comments and build them with cargo doc
  • Apply semver to a crate's public API, including Cargo's rules for 0.x versions

Private by default

In Python, privacy is a convention. A leading underscore says "please do not use this", but from pixi_lib._internal import helper works anyway, and every attribute of every object can be read and changed. Rust reverses the default: every item is private unless marked pub, and the compiler enforces it.

"Private" in Rust means private to the module it is defined in, and that module's descendants. A function in mod manifest can be used anywhere inside manifest (and its submodules), but not from a sibling or parent module:

E0603: "function normalize_name is private". The compiler points at the private item's definition with a note, and the fix is a design decision: either make it visible, or (better, if parse_name already does the job) keep it private and call the public function.

Struct fields are private too

Marking a struct pub makes the type nameable outside its module. Each field is still private until it is also marked pub. This is how Rust protects an invariant: if code outside the module cannot touch the fields, the only way to make a value is through a constructor you control.

E0616: "field minor of struct Version is private". Reading is blocked, and so is building one by hand. Try to construct a Version with major 0 from outside:

E0451: "fields major and minor of struct Version are private". Outside the module you cannot write a Version literal at all, so the only way to get one is Version::new, which refuses major 0. The invariant in the doc comment is enforced by the type system, not by hoping callers read the comment. (Python's closest equivalent, a property without a setter plus a validating __init__, can still be bypassed with object.__setattr__.)

Enums work the other way: if an enum is pub, all its variants and their fields are public. You cannot hide a variant. To hide an enum's representation, wrap it in a struct with a private field.

Remember: private means "this module and its children". A pub struct with private fields plus a constructor is how you make invalid values unrepresentable.

pub(crate), pub(super), and friends

Between private and pub there are restricted levels. They matter most in a large codebase, because pub in a library crate means "any crate that depends on me may use this, and I promise not to break it".

ModifierVisible inUse it for
(nothing)this module and its descendantsthe default; helpers and internal state
pub(super)the parent module (and so its descendants)a submodule's helper that only its parent uses
pub(in crate::a::b)the named ancestor modulerare; precise sharing in deep trees
pub(crate)the whole current crateshared internals: used across modules but not by other crates
pubeveryone who can reach itthe crate's public API

Note the phrase "who can reach it". A pub fn inside a private module is not reachable from other crates unless something re-exports it (next section). pub is a permission, not a publication.

If main tried to call lock_file::parse::split_line directly, it would get E0603: pub(super) stops at lock_file.

Pixi uses pub(crate) about 530 times and pub(super) about 56 times at the snapshot. A typical case: the line-ending detector you met in M09 is pub(crate) enum LineEnding (pixi_manifest/src/script/block.rs). Several modules of pixi_manifest need it, but no other crate should depend on how script blocks detect \r\n. If it were pub, changing it later could break crates that started using it.

A reviewer's rule of thumb: start private, widen only when the compiler asks, and widen to the narrowest level that works. Making something less visible later is a breaking change for anyone who used it; making it more visible never is. Clippy and rustc help: an unused private item triggers the dead_code warning, which a pub item never does, so over-wide visibility also hides dead code.

Remember: pub(crate) is the workhorse for internals that cross modules. Plain pub in a library is a promise to other crates.

Re-exports and the shape of a public API

A crate's module tree is an implementation detail. Users should not have to know that GlobHash lives in a file called glob_hash.rs. The standard Rust pattern is: declare the modules private, then re-export the public types from the crate root with pub use. Users then write pixi_glob::GlobHash, and the authors can move code between files without breaking anyone.

Pixi's glob crate is a compact, complete example (crates/pixi_glob/src/lib.rs, the whole file):

#![deny(missing_docs)]
//! A crate to deal with glob patterns in Pixi.
//! And the caching thereof.

mod glob_hash;
mod glob_hash_cache;
mod glob_mtime;
mod glob_set;

pub use glob_hash::{GlobHash, GlobHashError};
pub use glob_hash_cache::{GlobHashCache, GlobHashKey};
pub use glob_mtime::{GlobModificationTime, GlobModificationTimeError};
pub use glob_set::{GlobSet, GlobSetError, Match};
  • Four mod lines without pub: nobody outside can write pixi_glob::glob_hash::....
  • Four pub use lines: the crate's entire public API is eleven names at the root, readable in one screen.
  • #![deny(missing_docs)] (an inner attribute, applying to the whole crate) makes every public item without a doc comment a compile error. //! is the crate's own doc comment. Both are covered below.

Preludes

A prelude is a module whose only job is to be glob-imported. The standard library's prelude is imported into every module automatically, which is why Vec, Option, String, Some, and traits like Iterator and Clone need no use. Some crates ship their own (use rayon::prelude::*;, use std::io::prelude::*;), mostly to bring traits into scope, because trait methods are only callable when the trait is imported (M09's use itertools::Itertools; is the one-trait version of the same idea).

A pub use of another crate's type makes that crate part of your public API. If pixi_manifest re-exports a rattler_conda_types type, a breaking upgrade of rattler becomes a breaking change of pixi_manifest. Inside a workspace whose crates are consumed by path (most of Pixi's internal crates sit at version 0.1.0 and are used only by each other) this costs little, because every user is fixed in the same pull request; for a published library it is a real decision.

Remember: private mod + pub use at the root = a flat API that does not leak your file layout. Read a crate's lib.rs first; it is the table of contents.

Cargo features

Python packages have extras: pip install requests[socks] pulls in more dependencies. Cargo features are similar, with one big difference: a feature can also switch code on and off at compile time, so a crate built without a feature contains none of that code.

Features are declared in a [features] table. Each feature is a name mapped to a list of things it turns on: other features of this crate, optional dependencies, or features of dependencies.

[dependencies]
reqwest = { version = "0.13", default-features = false }
pixi_auth = { path = "../pixi_auth", default-features = false }
serde_json = { version = "1", optional = true }   # only compiled if something enables it

[features]
default = ["rustls"]                          # enabled unless the user opts out
rustls = ["reqwest/rustls", "pixi_auth/rustls"]   # "dep/feature": enable a dependency's feature
native-tls = ["reqwest/native-tls", "pixi_auth/native-tls"]
json = ["dep:serde_json"]                     # "dep:name": enable an optional dependency
  • default is the list enabled automatically. Users opt out with default-features = false on the dependency, or --no-default-features on the command line.
  • Optional dependencies (optional = true) are not compiled unless enabled. If no feature mentions dep:serde_json, Cargo creates an implicit feature with the dependency's own name, so features = ["serde_json"] works. Writing dep: anywhere suppresses that implicit feature, which keeps the feature list deliberate.
  • "crate/feature" forwards a feature to a dependency. This is how a top-level choice (say, the TLS backend) flows down through every crate that needs it.
pixi run cargo build --features json
pixi run cargo build --no-default-features --features native-tls
pixi run cargo test --all-features
pixi run cargo tree -e features -i reqwest     # who enabled which reqwest features?

Features must be additive

Cargo builds each dependency once per build, with the union of the features every dependent asked for. This is called feature unification. If crate A wants reqwest/rustls and crate B wants reqwest/native-tls, reqwest is built with both. So a feature must only add capability; turning on a feature must never remove an API or change behavior another crate relies on. "Mutually exclusive features" fight this design, and code that supports two backends (like Pixi's two TLS stacks) has to work, or at least compile, when both are on.

Pixi's pixi_utils crate is the example above, nearly verbatim (crates/pixi_utils/Cargo.toml):

[features]
default = ["rustls"]
native-tls = [
  "pixi_auth/native-tls",
  "rattler_networking/native-tls",
  "reqwest/native-tls",
]
rustls = ["pixi_auth/rustls", "rattler_networking/rustls", "reqwest/rustls"]

And pixi_manifest uses an implicit feature: rattler_lock = { workspace = true, optional = true } (Cargo.toml) with no [features] table at all. The conversions to lock-file types are behind #[cfg(feature = "rattler_lock")], and pixi_core asks for them with pixi_manifest = { workspace = true, features = ["rattler_lock"] }.

Remember: features are additive switches, unified across the whole build. default is on unless opted out; dep:x enables an optional dependency; x/feat forwards a feature.

default-features = false and workspace dependencies

M01 introduced [workspace.dependencies]: the root Cargo.toml names each external dependency and its version once, and member crates write dep = { workspace = true }. A member can add features on top ({ workspace = true, features = ["derive"] }), but it cannot remove features that the workspace entry enables. That is why the workspace entry is the right place to say default-features = false: it starts every member from the minimum, and each member adds only what it needs.

Why would Pixi turn off a dependency's defaults? Three reasons, all visible in its manifest:

  • Choosing one backend. HTTP and networking crates often pick a TLS implementation in their default features. With defaults left on, unification could compile both TLS stacks, bloating the binary and the build. Pixi turns the defaults off everywhere, then picks rustls or native-tls once, at the top.
  • Build time. Every enabled feature is code to compile. In a 60-crate workspace that is rebuilt constantly by contributors and CI, unused features are minutes.
  • Control. When an upstream crate adds a new default feature, it does not silently appear in Pixi's build.
# Rattler crates
rattler = { version = "0.48", default-features = false }
rattler_conda_types = { version = "0.52", default-features = false, features = [
  "rayon",
] }
rattler_networking = { version = "0.30", default-features = false, features = [
  "dirs",
  "google-cloud-auth",
] }
rattler_solve = { version = "9.0", default-features = false }

A member then adds what it needs. pixi_utils asks for more networking features than the workspace entry gives (crates/pixi_utils/Cargo.toml):

rattler_networking = { workspace = true, features = [
  "gcs",
  "netrc-rs",
  "s3",
  "system-integration",
] }

pixi_cli depends on pixi_utils = { workspace = true, default-features = false }. If it did not say default-features = false, which TLS backend would pixi_utils always get, and why would that make a --no-default-features --features native-tls build of Pixi pull in both?

Remember: set default-features = false in [workspace.dependencies], add features per member, and make the final feature choices in the binary crate.

Conditional compilation with cfg

Python decides at run time: if sys.platform == "win32":. Rust can decide at compile time, so code for the wrong platform or a disabled feature is not just skipped, it is not compiled at all (and does not even need to type-check against dependencies that are missing). The tool is the cfg attribute, which takes a configuration predicate:

PredicateTrue when
feature = "rustls"that Cargo feature of this crate is on
testcompiling the crate's test harness (cargo test)
target_os = "windows", "macos", "linux"compiling for that OS
unix, windowsshorthands for families of targets
debug_assertionsdebug builds (the default profile)
all(..), any(..), not(..)combinations

There are three forms:

  • #[cfg(pred)] on an item (function, impl, mod, use, block): the item exists only when true.
  • cfg!(pred): a macro that evaluates to true or false. Both branches of an if cfg!(..) are still compiled, so both must type-check.
  • #[cfg_attr(pred, attr)]: apply attr only when the predicate is true.

Code under a false cfg is removed before name resolution, so calling it is an "it does not exist" error, not a visibility error. A helper marked #[cfg(test)] cannot be used by normal code:

E0425: "cannot find function sample_manifest in this scope", with a note that an item by that name exists but is gated behind #[cfg(test)]. This is exactly the guarantee you want: test fixtures and test-only dependencies ([dev-dependencies]) can never leak into the shipped binary.

All three forms appear in Pixi. Per-platform definitions of one function (pixi_utils/src/rlimit.rs):

#[cfg(not(target_os = "windows"))]
pub fn try_increase_rlimit_to_sensible() {
    // ... raise the open-file limit with the `rlimit` crate ...
}

#[cfg(target_os = "windows")]
pub fn try_increase_rlimit_to_sensible() {
    // On Windows, there is no need to increase the RLIMIT_NOFILE resource
    // limit.
}

Feature-gated blocks inside one function choose the TLS stack (pixi_utils/src/reqwest.rs):

#[cfg(feature = "native-tls")]
{
    builder = builder.use_native_tls();
    builder = apply_native_tls_roots(builder, tls_root_certs);
}
#[cfg(feature = "rustls")]
{
    builder = builder.use_rustls_tls();
    // ...
}

Because features are additive, both blocks may be compiled at once; then the later one wins at run time. And cfg_attr marks slow tests ignored unless a feature is on, which you will meet in M11: #[cfg_attr(not(feature = "slow_integration_tests"), ignore)].

Remember: #[cfg] removes code; cfg! keeps both branches and picks one; #[cfg_attr] adds an attribute conditionally. #[cfg(test)] mod tests is the most common cfg of all.

Doc comments and cargo doc

Python has docstrings; Rust has doc comments, written in Markdown:

  • /// documents the item that follows (a function, struct, field, variant, module).
  • //! documents the item it is inside: at the top of lib.rs it documents the whole crate; at the top of a module file, that module.
//! Parsing and validation of package names.

/// A normalized conda package name: lowercase, non-empty.
///
/// Build one with [`PackageName::new`]; the field is private so every value is valid.
///
/// # Errors
///
/// [`PackageName::new`] returns an error for empty input or characters outside `[a-z0-9-_.]`.
///
/// # Examples
///
/// ```
/// use names::PackageName;
/// let name = PackageName::new("NumPy").unwrap();
/// assert_eq!(name.as_str(), "numpy");
/// ```
pub struct PackageName(String);
  • The first paragraph is the summary shown in lists and search results; keep it to one sentence.
  • [`PackageName::new`] is an intra-doc link: rustdoc resolves the path like a use and links to it, and warns if the target does not exist, so links cannot silently rot.
  • The conventional headings are # Errors, # Panics, # Safety (for unsafe fn), and # Examples. Clippy's missing_errors_doc and missing_panics_doc lints check the first two.
  • Code blocks in doc comments are doc tests: cargo test compiles and runs them, so examples cannot drift out of date. M11 covers them.
pixi run cargo doc --open                # your crate and all dependencies, in the browser
pixi run cargo doc --no-deps -p pixi_glob # one workspace crate only
pixi run cargo doc --document-private-items   # include private items (great for learning a codebase)

When you start on an unfamiliar Pixi crate, run cargo doc --no-deps --document-private-items -p <crate> --open in Pixi's checkout. You get a browsable map of every module, type, and trait implementation, with "source" links, which is often faster than reading files in order.

Remember: /// for the next item, //! for the enclosing one. First line is the summary; use intra-doc links and # Errors/# Panics sections.

Semver for crates

Cargo assumes every crate follows semantic versioning (semver): MAJOR.MINOR.PATCH, where a breaking change bumps MAJOR. A plain version in Cargo.toml is a caret requirement: rattler = "0.48" means ^0.48, "any version compatible with 0.48". The twist is how Cargo treats 0.x versions: the leftmost non-zero component is treated as the major version.

RequirementAllowsWhy
"1.3">=1.3.0, <2.0.01 is the major
"9.0" (rattler_solve)>=9.0.0, <10.0.09 is the major
"0.48" (rattler)>=0.48.0, <0.49.0for 0.x, the minor acts as the major
"0.2.2">=0.2.2, <0.3.0same rule; the patch is a lower bound
"0.0.3"exactly 0.0.30.0.x: every release may break

So when rattler releases 0.49, Pixi does not get it automatically: someone edits the workspace entry, fixes what broke, and opens a PR. That is a large share of real maintenance work in Pixi. cargo update only moves within the allowed ranges and rewrites Cargo.lock.

What counts as breaking

For a library's public API, these require a major bump (or a minor bump in 0.x):

  • removing or renaming a pub item, or making it less visible;
  • changing a public function's signature (a new parameter, a different type, a tighter trait bound);
  • adding a public field to a struct whose fields are all public (struct literals elsewhere stop compiling);
  • adding a variant to a public enum (other crates' exhaustive matches stop compiling);
  • removing a trait implementation, or removing a Cargo feature.

The escape hatch for the last two kinds of growth is #[non_exhaustive]. On an enum it forces other crates to include a wildcard arm (_ => ...) in their match; on a struct it forbids struct literals outside the defining crate. You can then add variants or fields in a minor release. It has no effect inside the defining crate, so you cannot see it fail in a single-file example.

#[non_exhaustive]
pub enum ChannelPriority {
    Strict,
    Disabled,
}
// In another crate:
match priority {
    ChannelPriority::Strict => ..,
    ChannelPriority::Disabled => ..,
    _ => ..,   // required: future versions may add variants
}

Is adding a new pub fn to a crate breaking? Usually not. Is adding a new method to a public trait breaking? It depends: with a default implementation, existing impls keep compiling; without one, every implementor breaks. Tools like cargo-semver-checks automate these questions for published crates.

Remember: a caret requirement allows changes that keep the leftmost non-zero component. "0.48" stops before 0.49. Removing, narrowing, or exhaustively extending public API is breaking.

How Pixi splits responsibilities across crates

Why split a program into dozens of crates instead of dozens of modules? A crate is the unit of compilation, of visibility, and of dependencies, and each of those gives a benefit:

  • Build times. Cargo compiles crates in parallel and only recompiles crates whose inputs changed. Editing pixi_manifest does not rebuild pixi_glob.
  • Enforced boundaries. pub(crate) is a hard wall. A lower crate cannot call into a higher one at all (crate dependencies may not form cycles), so the layering is checked by the compiler, not by convention.
  • Lean dependencies. The manifest parser has no reason to depend on the solver or the HTTP stack, and as a separate crate it cannot accidentally start to.
  • Reuse. Build backends (pixi_build_*) and tools like pixi_docs reuse the lower crates without pulling in the CLI.
flowchart TD
  pixi["pixi (bin: main.rs only)"] --> cli["pixi_cli (argument parsing, commands)"]
  cli --> core["pixi_core (workspace, lock file, environments)"]
  cli --> manifest
  core --> manifest["pixi_manifest (pixi.toml and pyproject.toml model)"]
  core --> utils["pixi_utils (HTTP client, misc)"]
  core --> config["pixi_config"]
  manifest --> spec["pixi_spec, pixi_toml, pixi_consts"]
  manifest --> rattler["rattler_conda_types (external)"]
  utils --> config

A simplified view of the dependency edges in each crate's Cargo.toml. At the top, crates/pixi is almost nothing: its main.rs sets up a thread with a large stack and a Tokio runtime, then calls into pixi_cli. Its Cargo.toml is where the final feature decisions live (default = ["rustls"]), which is why the workspace's default-members is crates/pixi. Lower crates are libraries with lib.rs files full of pub use lines.

The Pixi codebase map lists every crate with a one-line purpose. When a change touches a type, check its crate's lib.rs to see whether the type is re-exported; if it is, other crates may depend on it, and a change ripples outward.

Remember: crates buy parallel builds, compiler-enforced layering, and lean dependencies. In Pixi, the binary crate is thin, choices about features live at the top, and libraries expose curated re-exports.

Question 1: a contributor adds pub fn helper() inside mod warning (a private module). Can pixi_core call it?

No. pub grants permission, but pixi_core cannot reach the item: warning is private to pixi_manifest and nothing re-exports helper. The contributor should make it pub(crate) (which says what they mean) or add a deliberate pub use in lib.rs if it really belongs to the API.

Question 2: why is default-features = false on the workspace entry for rattler, rather than in each member?

Members can add features to a workspace dependency but cannot subtract any the workspace entry enables. If the root left defaults on, every member would get rattler's default TLS backend, and Pixi could never build a binary with only native-tls. Turning defaults off at the root gives every member the minimum and leaves the choice to the rustls/native-tls features at the top.

Question 3: what does cargo build --features slow_integration_tests change in the shipped pixi binary?

Nothing: the feature enables no dependencies and gates only test code (through #[cfg_attr(not(feature = "slow_integration_tests"), ignore)] on tests). It changes which tests cargo test runs instead of skipping. Pixi's test-slow task passes --features slow_integration_tests,online_tests.

Practice

The checker appends its tests in a sibling module of your code (mod pp_checks at the crate root), so for the tests, "outside the module" means outside any mod you write.

The manifest module below is entirely private, so the tests cannot use it: they fail to compile with E0603 and E0624 (private method). Add visibility modifiers so the tests compile and pass. Make Manifest, new, add_channel, name, and channels visible to the crate, and leave normalize and the fields private. Do not change any function bodies.

Hint

The tests live outside mod manifest but in the same crate, so pub(crate) is the narrowest level that works for the struct and each method that the tests call. A method's visibility is separate from its type's.

Show solution 
mod manifest {
    pub(crate) struct Manifest {
        name: String,
        channels: Vec<String>,
    }

    fn normalize(channel: &str) -> String {
        channel.trim().trim_end_matches('/').to_lowercase()
    }

    impl Manifest {
        pub(crate) fn new(name: &str) -> Self {
            Manifest { name: name.to_string(), channels: Vec::new() }
        }

        pub(crate) fn add_channel(&mut self, channel: &str) {
            let channel = normalize(channel);
            if !self.channels.contains(&channel) {
                self.channels.push(channel);
            }
        }

        pub(crate) fn name(&self) -> &str {
            &self.name
        }

        pub(crate) fn channels(&self) -> &[String] {
            &self.channels
        }
    }
}

The types live deep in model::spec and model::channel, and both modules are private. Implement PackageName in mod names. mod names {
    use std::fmt;

    /// A normalized conda package name: trimmed, lowercase, `[a-z0-9-_.]` only.
    #[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord)]
    pub struct PackageName(String);

    impl PackageName {
        /// Normalizes and validates `raw`.
        ///
        /// # Errors
        ///
        /// Returns an error if the name is empty or contains other characters.
        pub fn new(raw: &str) -> Result<PackageName, String> {
            let name = raw.trim().to_lowercase();
            if name.is_empty() {
                return Err("package name is empty".to_string());
            }
            if !name.chars().all(|c| c.is_ascii_alphanumeric() || "-_.".contains(c)) {
                return Err(format!("invalid character in package name '{name}'"));
            }
            Ok(PackageName(name))
        }

        pub fn as_str(&self) -> &str {
            &self.0
        }
    }

    impl fmt::Display for PackageName {
        fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
            f.write_str(&self.0)
        }
    }
}

Model what Cargo does with a [features] table. resolve_features(table, requested, default_features) returns the set of everything enabled:

  • Start from the requested features, plus "default" if default_features is true and the table has a default entry.
  • Each enabled feature name is in the result, and so is everything it lists. An entry containing / ("reqwest/rustls") or starting with dep: is added as-is. Any other entry is a feature of this crate and is expanded recursively.
  • A requested or listed feature name not in the table is an error: Err(format!("unknown feature `{name}`")).
  • Features may refer to each other in cycles; do not loop forever.
Hint

Use a work list: let mut todo: Vec<&str> = requested.to_vec();, push "default" when appropriate, then while let Some(name) = todo.pop(). Skip names already in the result (BTreeSet::insert returns false for those), look the name up with table.get(name).ok_or_else(..)?, and for each entry either insert it directly or push it onto todo.

Show solution 
use std::collections::{BTreeMap, BTreeSet};

fn resolve_features(
    table: &BTreeMap<&str, Vec<&str>>,
    requested: &[&str],
    default_features: bool,
) -> Result<BTreeSet<String>, String> {
    let mut enabled = BTreeSet::new();
    let mut todo: Vec<&str> = requested.to_vec();
    if default_features && table.contains_key("default") {
        todo.push("default");
    }
    while let Some(name) = todo.pop() {
        if !enabled.insert(name.to_string()) {
            continue;
        }
        let entries = table.get(name).ok_or_else(|| format!("unknown feature `{name}`"))?;
        for entry in entries {
            if entry.contains('/') || entry.starts_with("dep:") {
                enabled.insert(entry.to_string());
            } else {
                todo.push(entry);
            }
        }
    }
    Ok(enabled)
}

Write caret_matches(req, version), which says whether version (always three parts, like "0.48.3") satisfies the caret requirement req (one to three parts, like "0.48", "1", or "0.2.2") using Cargo's rules: the version must be at least the requirement (missing parts count as 0), and below the upper bound made by incrementing the leftmost non-zero part of the requirement and zeroing everything after it. If every given part is zero, increment the last given part instead ("0" allows <1.0.0, "0.0" allows <0.1.0, "0.0.3" allows <0.0.4). Inputs are always well-formed.

Hint

Parse both into Vec<u64> with split('.').map(|p| p.parse().unwrap()). Build lower by padding the requirement to three parts with zeros. For the upper bound, find i = req.iter().position(|&p| p != 0).unwrap_or(req.len() - 1), copy req[..i], push req[i] + 1, pad with zeros. Arrays and Vecs compare lexicographically, so lower <= v && v < upper works directly.

Show solution 
fn caret_matches(req: &str, version: &str) -> bool {
    let parse = |s: &str| -> Vec<u64> { s.split('.').map(|p| p.parse().unwrap()).collect() };
    let req = parse(req);
    let v = parse(version);

    let mut lower = req.clone();
    lower.resize(3, 0);

    let i = req.iter().position(|&p| p != 0).unwrap_or(req.len() - 1);
    let mut upper: Vec<u64> = req[..i].to_vec();
    upper.push(req[i] + 1);
    upper.resize(3, 0);

    lower <= v && v < upper
}

Build a small Cargo workspace laid out like Pixi: a library crate that owns the logic and exposes a deliberate API, and a binary crate that only parses arguments and chooses features.

What to build

  • spec_core: private modules name, spec, and render; lib.rs re-exports PackageName, Spec, and ParseError and has a prelude. PackageName keeps its field private (exercise 3).
  • A json feature in spec_core that adds Spec::to_json(&self) -> String behind #[cfg(feature = "json")], written by hand (no serde), so the feature has no dependencies, like Pixi's test features.
  • spec_cli depends on spec_core = { path = "../spec_core", default-features = false } and declares its own json = ["spec_core/json"] feature, forwarding the choice.
  • The workspace root has [workspace.package] with edition = "2024", and both crates use edition.workspace = true.
  • //! crate docs and /// docs on every public item, enforced with #![deny(missing_docs)] in spec_core.
  • spec_core's lib.rs has only mod, pub use, and the prelude: no logic
  • spec_cli cannot construct a PackageName without PackageName::new
  • cargo build -p spec_cli works with and without --features json, and --json output appears only with it
  • Removing a doc comment from a public item makes the build fail
  • cargo doc --no-deps builds with no warnings and the intra-doc links resolve
  • pixi run cargo clippy --workspace --all-targets --all-features -- -D warnings passes

Stretch goals: move the shared version requirement of a dependency (say, itertools) into [workspace.dependencies] and use workspace = true in both crates; add a #[non_exhaustive] error enum and see the wildcard arm the binary now needs; run cargo tree -e features -p spec_cli --features json and find the forwarded feature.

Quiz

Recap

  • Everything is private by default: visible in its module and descendants. Struct fields are private separately from the struct; enum variants are public with the enum.
  • pub(super), pub(crate), and pub widen visibility step by step; prefer the narrowest that works. pub in a library is a promise.
  • Private modules plus pub use in lib.rs give a flat API independent of file layout. A prelude is a module meant for use x::prelude::*.
  • Features: [features], default, dep: for optional dependencies, crate/feature to forward. Features are unified across the build, so they must be additive.
  • default-features = false in [workspace.dependencies] starts every member from the minimum; Pixi does this for every rattler crate and picks TLS at the top.
  • #[cfg] removes code, cfg! picks a branch, #[cfg_attr] adds an attribute conditionally: for features, tests, and target platforms.
  • /// and //! are Markdown docs; cargo doc builds them. Caret requirements allow changes that keep the leftmost non-zero version component.
