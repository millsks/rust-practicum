Capstone 1: Manifest Reader

Build a small Rust crate that reads a simplified pixi.toml into typed structs, reports every mistake with the exact TOML key where it happened, works out which packages each environment installs, and orders tasks by depends-on. It is Level 1 in one program, and it is a scale model of pixi_manifest, the crate in Pixi that every command depends on.

⏱ ~8–10 hoursPrerequisites: M01 to M11 (M04, M05, M06, and M07 matter most)
  • Model a file format with structs and enums so that invalid states cannot be represented
  • Convert an untyped toml::Table into those types by hand with match, Option, and Result
  • Write an error enum that implements Display, std::error::Error, and From, so ? works and every message names the TOML key at fault
  • Return borrowed results (BTreeMap<&str, &Spec>, Vec<&str>) whose lifetimes are tied to the manifest, not to the arguments
  • Implement a deterministic depth-first task ordering with cycle detection
  • Ship a small command-line tool with correct stdout, stderr, and exit codes
  • Read the matching code in pixi_manifest and pixi_task and explain how it differs from yours

What you'll build

Every Pixi command starts the same way: find pixi.toml, read it, and turn the text into data the rest of the program can trust. If platforms lists linux-arm64 (a common typo for linux-aarch64), Pixi has to say so clearly before it tries to solve anything. If a task depends on a task that does not exist, the user should learn that from one line of output, not from a panic.

You will build manifest_reader, a library crate with a small binary called manifest-reader. Given a manifest it prints a summary; given a manifest and a task name it prints the order in which the task and its dependencies run:

The library does the real work. The tests call it directly: parse_manifest returns a Manifest or a ManifestError, and two methods answer the questions Pixi asks of a manifest all day: "what goes into this environment?" and "what runs before this task?".

The only dependency is the toml crate, and you use exactly one thing from it: parsing text into a toml::Table, a map from keys to toml::Values that could be anything. You will not use serde's #[derive(Deserialize)], which would do the conversion for you. Writing the conversion by hand is the point: it is where enums, match, ownership, Option, Result, collections, traits, and lifetimes all meet. Serde is Level 2.

Why it mirrors pixi_manifest

Pixi reads its manifest in the pixi_manifest crate. It parses with toml_span (a TOML parser that remembers where each value sat in the file, so errors can underline it) and then converts each table by hand in Deserialize impls that look a lot like the functions you are about to write. Here is how its task conversion starts, from crates/pixi_manifest/src/toml/task.rs (trimmed):

impl<'de> toml_span::Deserialize<'de> for TomlTask {
    fn deserialize(value: &mut toml_span::Value<'de>) -> Result<Self, DeserError> {
        let mut th = match value.take() {
            ValueInner::String(str) => return Ok(Task::Plain(str.into_owned().into()).into()),
            ValueInner::Table(table) => TableHelper::from((table, value.span)),
            ValueInner::Array(array) => {
                // ... an array of { task = "..." } tables becomes an alias ...
            }
            inner => return Err(expected("string or table", inner, value.span).into()),
        };
        // ... read `cmd`, `depends-on`, and the other keys from `th` ...

That is a match on the kind of TOML value, with a string becoming one variant, a table becoming a richer one, and anything else an error that says what was expected. Your task_from_value has the same shape. The table below maps each part of your crate to its counterpart in Pixi at the frozen snapshot.

Look at the topological order in Pixi once more after you finish milestone 6. Its visit is a nested fn that takes &mut HashSet and &mut Vec parameters, which is the same design as your visit_task. When you read that file during Level 3 you will already know how it works.

How the pieces fit

Reading a manifest happens in three passes, and the crate keeps them in separate modules so each can be understood alone:

  1. Syntax. src.parse::<toml::Table>() checks that the text is valid TOML. Its error becomes ManifestError::Toml through your From impl.
  2. Shape. convert.rs walks the table and builds typed structs. Every function receives the key path of the value it converts (tasks.test, workspace.platforms[2]), so any error can say exactly where it is.
  3. References. validate checks the links between parts: environments name real features, and depends-on names real tasks.
flowchart LR
  T[pixi.toml text] -->|"src.parse()"| TT[toml::Table]
  TT -->|convert.rs| M[Manifest]
  M -->|validate| V[valid Manifest]
  V --> Q1["environment_dependencies(env)"]
  V --> Q2["task_order(task)"]
  V --> S["summary()"]
  TT -. syntax error .-> E[ManifestError]
  M -. wrong shape .-> E
  V -. bad reference .-> E
  Q1 -. unknown env .-> E
  Q2 -. unknown task or cycle .-> E

The two queries return borrowed data. environment_dependencies returns BTreeMap<&str, &Spec>: the names and specs stay where they are inside the Manifest, and the map only points at them. Lifetime elision (M07) ties every reference in the return type to &self, so the compiler will make sure no result outlives the manifest, and will stop you from accidentally returning a reference to the env or task argument.

Why convert by hand when serde could derive it? Look at what the tests demand: depends-on accepts a string or a list, environments accept a list or a table, and every error names a key path. Pixi wants exactly that control (and spans for underlined errors), which is why its manifest is converted by hand-written toml_span impls rather than serde derives.

The spec

The full spec, with every error message, is in projects/c1_manifest_reader/README.md. This is the contract at a glance.

The manifest format

Five top-level keys. Only workspace is required, and any other top-level key (including Pixi's older [project]) is an UnknownKey error.

[workspace]
name = "weather-station"                   # required string
version = "0.3.0"                          # optional string
description = "Readings from the garden"   # optional string
channels = ["conda-forge", "bioconda"]     # required array of strings, order kept
platforms = ["linux-64", "osx-arm64"]      # required array of platform names, order kept

[dependencies]
python = "3.13.*"                                          # Spec::Version
pandas = { version = ">=2.2", channel = "conda-forge" }    # Spec::Detailed: version, build, channel (all optional)

[tasks]
fetch = "python -m station.fetch"                                   # Task::Command
clean = { cmd = "python -m station.clean", depends-on = "fetch" }   # Task::Execute (one name = a list of one)
plot = { cmd = "python -m station.plot", depends-on = ["clean"] }   # Task::Execute
all = { depends-on = ["plot", "fetch"] }                            # Task::Alias (no cmd)

[feature.test.dependencies]               # a feature has optional dependencies and tasks tables
pytest = ">=8"

[feature.test.tasks]
test = { cmd = "pytest", depends-on = ["fetch"] }

[environments]
test = ["test"]                                            # list shorthand
lint = { features = ["test"], solve-group = "default" }    # table form: features required, solve-group optional

The six platforms are linux-64, linux-aarch64, osx-64, osx-arm64, win-64, and noarch, spelled exactly. After conversion, validate checks that every feature an environment lists is defined, that every depends-on entry of a default task names a default task, and that every depends-on entry of a feature task names a task of the same feature or a default task. Cycles are not a parse error; task_order reports them.

The types (given in the starter)

pub struct Manifest {
    pub workspace: Workspace,
    pub dependencies: BTreeMap<String, Spec>,
    pub tasks: BTreeMap<String, Task>,
    pub features: BTreeMap<String, Feature>,
    pub environments: BTreeMap<String, Environment>,
}
pub struct Workspace {
    pub name: String,
    pub version: Option<String>,
    pub description: Option<String>,
    pub channels: Vec<String>,
    pub platforms: Vec<Platform>,
}
pub enum Platform { Linux64, LinuxAarch64, Osx64, OsxArm64, Win64, NoArch }
pub enum Spec { Version(String), Detailed(DetailedSpec) }
pub struct DetailedSpec { pub version: Option<String>, pub build: Option<String>, pub channel: Option<String> }
pub enum Task {
    Command(String),
    Execute { cmd: String, depends_on: Vec<String> },
    Alias { depends_on: Vec<String> },
}
pub struct Feature { pub dependencies: BTreeMap<String, Spec>, pub tasks: BTreeMap<String, Task> }
pub struct Environment { pub features: Vec<String>, pub solve_group: Option<String> }

Notice what the types rule out. A task cannot have a command and be an alias at the same time, because those are different variants. A platform cannot be misspelled once it is a Platform. Every BTreeMap iterates in sorted order, so output is deterministic without extra sorting. (Pixi uses IndexMap to keep the order the user wrote; sorted is enough here.)

The functions you write

pub fn parse_manifest(src: &str) -> Result<Manifest, ManifestError>;

impl Platform { pub fn as_str(self) -> &'static str; }       // plus Display and FromStr
impl Spec {
    pub fn version(&self) -> Option<&str>;
    pub fn channel(&self) -> Option<&str>;
}                                                            // plus Display: ">=2", "* py312* (conda-forge)"
impl Task {
    pub fn command(&self) -> Option<&str>;                  // None for an alias
    pub fn depends_on(&self) -> &[String];                  // empty for a plain command
}
impl Manifest {
    pub fn environment_names(&self) -> Vec<&str>;           // includes "default", sorted, no duplicates
    pub fn summary(&self) -> String;
    pub fn environment_dependencies(&self, env: &str) -> Result<BTreeMap<&str, &Spec>, ManifestError>;
    pub fn task_order(&self, task: &str) -> Result<Vec<&str>, ManifestError>;
}
  • environment_dependencies: start from the default [dependencies] and apply each feature of the environment in order; a later spec for a package replaces an earlier one. The implicit default environment (when the manifest does not define one) has only the default dependencies.
  • task_order: a depth-first walk of the default [tasks] that visits depends-on in the order written and adds each task after all of its dependencies. Each task appears once. Feature tasks are not included.
  • summary: seven label: values lines (workspace, channels, platforms, dependencies, tasks, features, environments) joined with \n, no trailing newline. Channels and platforms keep manifest order, the other lists are sorted, and an empty list is (none).

Milestones

Work in this order. Each milestone has its own slice of the tests, so you always have a short list of failures to read. The hints are there when you are stuck; try each step for a while before you open them.

Milestone 1: platforms

Start in src/platform.rs. as_str is an exhaustive match (M02); Display and FromStr are the conversion traits from M06. Once FromStr exists, "osx-arm64".parse::<Platform>() works anywhere.

  • as_str covers all six variants, with no _ arm
  • Display reuses as_str instead of repeating the names
  • FromStr searches Platform::ALL, so adding a platform later means editing one place
  • pixi run grade c1 --test parse platform passes (2 tests)
Hint: FromStr without a second match

Platform::ALL.into_iter().find(|p| p.as_str() == s) gives an Option<Platform>. .ok_or_else(|| ParsePlatformError { value: s.to_string() }) turns it into the Result that from_str returns. Use ok_or_else rather than ok_or so the String is only built on failure.

Hint: what goes in Display

f.write_str(self.as_str()) is the whole body. For ParsePlatformError, use write!(f, "unknown platform `{}`", self.value); the backticks are part of the message.

Milestone 2: model methods and the error type

Fill in the small methods in src/model.rs (Spec::version, Spec::channel, Display for Spec, Task::command, Task::depends_on) and the three impls in src/error.rs. This is M04 in practice: a Display impl with one arm per variant, source() for the wrapped error, and From<toml::de::Error> so ? can convert.

  • Spec::version uses as_deref instead of cloning
  • Task::command covers Command and Execute in one arm with |
  • Every ManifestError message matches the README exactly
  • source() returns Some only for Toml
  • pixi run grade c1 --test parse spec_display and pixi run grade c1 --test errors query_errors pass
Hint: returning &str from an Option<String>

detailed.version is an Option<String> inside &self. detailed.version.as_deref() borrows it as Option<&str> without copying. .clone() would compile only if the return type were Option<String>.

Hint: depends_on for a Command

The return type is &[String]. An empty slice literal &[] has a 'static lifetime, which is longer than &self, so it fits. For the other two variants, a &Vec<String> coerces to &[String] automatically. Pixi's Task::depends_on is written exactly this way.

Hint: joining the platforms in UnknownPlatform's message

Collect the names first: let known: Vec<&str> = Platform::ALL.iter().map(|p| p.as_str()).collect();, then known.join(", "). The same trick joins allowed and cycle (cycle.join(" -> ") works directly on a Vec<String>).

Milestone 3: converting a valid manifest

The biggest milestone. In src/convert.rs, write the small helpers first (wrong_type, check_keys, as_str, as_table, string_list, required, optional_string, optional_table), then the converters from the leaves up: spec_from_value, depends_on_from_value, task_from_value, environment_from_value, feature_from_table, workspace_from_value, and finally manifest_from_table. Leave validate as Ok(()) for now. Then parse_manifest, environment_names, and summary.

  • Every converter takes a path: &str and builds child paths with join and index
  • No unwrap or expect anywhere in convert.rs; every failure is a ManifestError
  • Helpers return borrowed data (&'a str, &'a Table) and you clone only when a struct needs to own it
  • pixi run grade c1 --test parse passes (12 tests)
Hint: the helper pattern

Each type check is one line built from Option combinators:

fn as_str<'a>(value: &'a Value, path: &str) -> Result<&'a str, ManifestError> {
    value.as_str().ok_or_else(|| wrong_type(path, "string", value))
}

The lifetime 'a says the returned &str borrows from value, not from path. Without it, elision cannot decide (there are two reference inputs and no self), and you get E0106.

Hint: optional keys and transpose

table.get(key) is Option<&Value>. Mapping it through as_str gives Option<Result<&str, ManifestError>>, but you want Result<Option<String>, ManifestError> so that ? works. That flip is exactly what Option::transpose does:

table.get(key).map(|v| as_str(v, &join(path, key)).map(str::to_string)).transpose()
Hint: collecting a table of results

dependencies_from_table maps each (name, value) to Ok((name.clone(), spec_from_value(value, &join(path, name))?)) inside a closure that returns Result, and then .collect()s into Result<BTreeMap<String, Spec>, _>. collect stops at the first Err, as you saw for Result<Vec<_>, _> in M05.

Hint: telling the three task forms apart

After reading cmd (an Option<String>) and depends-on (an Option<Vec<String>>), match on the pair: (Some(cmd), deps) is Execute with deps.unwrap_or_default(), (None, Some(deps)) is Alias, and (None, None) is MissingKey at <path>.cmd. Matching on a tuple makes all four combinations visible, and the compiler checks you covered them.

Hint: the summary's list helper

A nested function fn list<'a>(items: impl IntoIterator<Item = &'a str>) -> String that collects into a Vec<&str> and returns "(none)" when it is empty keeps the seven lines short. Build the lines as an array of String and join("\n"). environment_names is easiest with a BTreeSet<&str>, which sorts and removes the duplicate default for you.

Milestone 4: every error path

Run the error tests and fix them one at a time. Most will pass already if your helpers are right; the rest are about choosing the right expected text, the right path, and writing validate and check_task_references. Read each failing assertion: it prints the error you returned.

  • Array items report their index: workspace.channels[1]
  • Unknown keys are rejected at every level: top, workspace, spec tables, task tables, features, environments
  • validate checks environments before tasks, and default tasks before feature tasks
  • A feature task may depend on its own feature's tasks and on default tasks, but not on another feature's
  • pixi run grade c1 --test errors passes (14 tests)
Hint: check_keys in one expression

table.keys().find(|key| !allowed.contains(&key.as_str())) returns the first unexpected key (the toml crate's table is a BTreeMap, so this is the first in sorted order). Match on it: Some(key) is the error, None is Ok(()). Note &key.as_str(): contains on a &[&str] wants a &&str.

Hint: UnknownPlatform from ParsePlatformError

text.parse::<Platform>().map_err(|err| ManifestError::UnknownPlatform { path: item_path, value: err.value })?. map_err converts the low-level error into one that knows where it happened. That is the general pattern whenever a lower layer cannot know the context.

Hint: closures for "does this task exist?"

check_task_references takes exists: impl Fn(&str) -> bool, so the same function checks both default and feature tasks. For default tasks pass |name| manifest.tasks.contains_key(name); for a feature, a closure that also checks feature.tasks. The closures borrow manifest and feature (M09).

Milestone 5: environment dependencies

In src/resolve.rs, write environment_dependencies. It returns references, so you never clone a Spec; a test checks that with std::ptr::eq.

  • default works without an [environments] entry, and an explicit default wins
  • Features are applied in the order listed; the last one to name a package wins
  • No .clone() of a Spec or a String in this function
  • pixi run grade c1 --test environments passes (7 tests)
Hint: choosing the feature list

A match with a guard reads well:

let features: &[String] = match self.environments.get(env) {
    Some(environment) => &environment.features,
    None if env == "default" => &[],
    None => return Err(ManifestError::NoSuchEnvironment { name: env.to_string() }),
};
Hint: building the map

self.dependencies.iter().map(|(name, spec)| (name.as_str(), spec)).collect() gives the starting BTreeMap<&str, &Spec>. For each feature, deps.extend(...) with the same kind of iterator overwrites existing keys, which is the "later wins" rule.

Milestone 6: task order and cycles

Write task_order and its helper visit_task: a depth-first, post-order walk (dependencies first, then the task). Keep two lists: order, the tasks already scheduled, and in_progress, the chain you are currently inside. Meeting a task that is already in in_progress means you went round a loop.

  • A diamond (top needs left and right, both need base) runs base once
  • depends-on order decides ties, not alphabetical order
  • A cycle error starts and ends with the repeated task, and a self-dependency is [x, x]
  • pixi run grade c1 --test tasks passes (8 tests)
Hint: the visit_task signature 
fn visit_task<'a>(
    &'a self,
    name: &str,
    in_progress: &mut Vec<&'a str>,
    order: &mut Vec<&'a str>,
) -> Result<(), ManifestError>

name has its own, possibly short, lifetime: the very first call passes the caller's argument. Everything pushed onto the lists must live as long as 'a, the borrow of self.

Hint: lifetime may not live long enough

If you push name onto order, the compiler refuses: name is not known to live for 'a. Look the task up with self.tasks.get_key_value(name) instead. It returns Option<(&'a String, &'a Task)>; push the key, which borrows from self. The test the_order_borrows_from_the_manifest_not_the_argument passes a String that is dropped before the result is used, which only compiles because of this.

Hint: building the cycle

if let Some(start) = in_progress.iter().position(|n| *n == name) finds where the loop begins. The cycle is in_progress[start..] (as owned Strings) followed by name again. Check order before in_progress: a finished task is never part of a cycle.

Milestone 7: the command line

main is given: it matches on the argument slice, calls run, and turns its Result<String, String> into output and an ExitCode. Write run. Then run the whole suite.

  • Errors use ManifestError's Display, never {:?}
  • Nothing is printed to stdout when the run fails
  • pixi run grade c1 passes all 46 tests
  • pixi run cargo clippy --all-targets -- -D warnings and pixi run cargo fmt --check are clean in your work copy, with the starter's #![allow(...)] lines deleted
Hint: why not fn main() -> Result<(), Box<dyn Error>>?

Returning an error from main prints it with Debug, as Error: UnknownPlatform { path: "...", ... }, and exits with code 1. That is fine for a quick tool, but the spec wants a readable error: line and a separate code 2 for bad usage, so main returns ExitCode and does the printing itself.

Hint: three map_errs

std::fs::read_to_string(path).map_err(|err| format!("cannot read {path}: {err}"))?, then the same shape for parse_manifest and task_order with format!("{path}: {err}"). Converting errors into String is acceptable at the very top of a binary, where the only thing left to do with an error is show it.

The fixtures are ordinary TOML files in tests/fixtures/, loaded at compile time with include_str!("fixtures/full.toml"); the path is relative to the test file. The CLI tests run your binary through env!("CARGO_BIN_EXE_manifest-reader"), a path Cargo provides to integration tests for every [[bin]] in the package. A typical test reads like this:

#[test]
fn an_unknown_platform_names_its_position() {
    let err = error_for(include_str!("fixtures/unknown-platform.toml"));
    assert!(
        matches!(&err, ManifestError::UnknownPlatform { path, value }
            if path == "workspace.platforms[2]" && value == "linux-arm64"),
        "expected UnknownPlatform at workspace.platforms[2] with value linux-arm64, got {err:?}"
    );
    // ... and the exact Display text ...
}

A todo!() panics with not yet implemented: <message>, and the starter's messages name the function (todo!("Spec::version")). When a test fails with one of those, the panic tells you which function to write next.

Self-review checklist

Passing the tests means the behavior is right. Before you call the capstone done, review the code the way a Pixi maintainer would review a pull request.

  • There is no unwrap, expect, panic!, or indexing that can panic in library code; every failure is a ManifestError
  • No todo!() is left, and the starter's #![allow(...)] lines are gone
  • Values are cloned only where a struct must own them; helpers return borrowed &str and &Table
  • Every match on toml::Value ends with an arm that reports WrongType, never a silent default
  • Each error message names the key path a user would search for in their file
  • You can explain, without looking, why visit_task pushes the key from get_key_value and not name
  • You can explain what Option::transpose does and why optional_string needs it
  • pixi run cargo clippy --all-targets -- -D warnings and pixi run cargo fmt --check are clean
  • Public items have /// doc comments, and pixi run cargo doc --open renders a page you would be happy to read
  • You ran the binary on the real pixi.toml of this repository and understood each error it reported (the real file uses keys this capstone does not support)

Stretch goals

None of these are graded. Add your own tests for each one in a new file in your work copy, such as tests/stretch.rs, and run them with pixi run cargo test. Pick a file name the grading tests do not use: when grading, their files are copied into your tests/ directory, and your extra files run too. Some stretch goals change graded behavior on purpose (keeping the user's order changes summary), so try those on a branch or a copy.

  • No default feature. Support Pixi's no-default-feature = true in the table form of an environment, which leaves out the default [dependencies].
  • Duplicate features. Reject an environment that lists the same feature twice, as Pixi does ("Since the order of the features matters, a duplicate feature is ambiguous").
  • Commands as arrays. Accept cmd = ["cargo", "test"] and store it as a Vec<String>; decide how command() should behave.
  • Environment tasks. Add task_order_in(&self, env: &str, task: &str) that also sees the tasks of the environment's features, with feature tasks able to override default tasks.
  • Every cycle at once. Add Manifest::check_cycles that walks every task and reports all cycles, sorted, not just the first.
  • Keep the user's order. Swap BTreeMap for IndexMap (enable the toml crate's preserve_order feature too) and make summary list tasks in the order they were written, as Pixi does. Which tests change, and why?
  • Did you mean? When a platform, feature, or task name is unknown, suggest the closest known name by edit distance (linux-arm64 to linux-aarch64).
  • Preview Level 2. Rewrite ManifestError with thiserror's #[derive(Error)] and #[error("...")] attributes, and confirm that the errors.rs tests still pass unchanged.
